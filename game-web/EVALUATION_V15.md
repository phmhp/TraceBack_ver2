# TraceBack V15 다각도 냉정 평가 및 개선안

## 1. 평가 전제와 방법

이 평가는 현재 로컬 구현을 실제 화면과 코드, 자동 테스트 결과를 함께 확인한 **형성평가**다. 교육효과를 입증하는 사용자 실험, 신입사원 사전·사후검사, 현업 전이 평가가 아직 없으므로 “교육효과가 검증됐다”고 판단하지 않는다.

평가 증거의 우선순위는 다음과 같다.

1. 실제 플레이 중 관찰되는 동작과 화면
2. 상태 전이·정답·실패·복구 로직
3. 자동 테스트와 프로덕션 빌드
4. 콘텐츠의 자동차/검증 개념 구조
5. 주관적 미감이나 기획 의도

점수 해석:

- 90–100: 상용·사내 배포 후 효과 검증만 남은 수준
- 75–89: 제한적 파일럿 배포가 가능한 수준
- 60–74: 핵심 루프가 성립한 베타/버티컬 슬라이스
- 40–59: 방향성은 있으나 학습·게임 제품으로 미완성
- 0–39: 콘셉트 또는 기능 데모 수준

> 과거 요청의 “IQ 80–90 플레이어”는 교육 적합성의 객관적 기준으로 쓰기 어렵다. 여기서는 자동차·제어·검증 사전지식이 거의 없고, 긴 전문용어와 높은 작업기억 부담에 취약한 신입 학습자로 바꾸어 평가한다.

## 3. 목표별 달성도

### 3.1 게임으로서

**점수: 58/100**

좋은 점:

- 도둑 고양이·경찰 추격·고장·수리·해적선 탈출이라는 명확한 판타지가 있다.
- 주행 중 직접 증상을 겪은 뒤 추리로 이동하므로 문제 풀이의 동기가 자연스럽다.
- 메모판의 종이·실, 배선 퍼즐의 지렁이 선은 조작 자체의 개성이 있다.
- 정답 시 격차 보상, 오답 시 압박이라는 게임 상태와 학습 행동의 연결이 있다.

한계:

- 레이싱의 차량 물리, 충돌, 카메라, 교통 AI는 “게임 시스템”보다 연출 스크립트에 가깝다.
- 고장 사례가 적어 두 번째 플레이부터 정답 암기 게임이 된다.
- 메모판과 배선 퍼즐의 핵심 재미가 아직 “발견”보다 정해진 답 배치에 가깝다.
- 실패가 새로운 전략을 낳기보다 정답 해설과 복구로 수렴한다.
- 현재 3D 미술은 일관된 토이 스타일은 갖췄지만 사용자가 기대한 동물의 숲/카트라이더급 모델링 품질에는 못 미친다.

### 3.2 학습 방향

**점수: 72/100**

`차고지 학습 → 주행 증상 경험 → 증거/원인 추리 → 제어 경로 복원 → 다계층 검증 → 수리 후 재주행`은 단순 퀴즈보다 훨씬 좋은 경험학습 구조다. 특히 같은 고장을 관찰·설계·검증의 서로 다른 표현으로 반복하는 것은 학습 전이를 만들 가능성이 있다.

그러나 현재는 각 단계가 같은 개념을 정말로 재사용하게 만드는 “명시적 연결 질문”이 부족하다. 예를 들어 메모판에서 고른 관찰점이 배선 퍼즐의 입력/중간/출력 노드를 제한하고, 배선 퍼즐의 연결이 실험실의 관측점과 TC로 직접 전달돼야 한다. 지금은 서사적으로 이어지지만 데이터 구조상 학습 산출물이 충분히 이어지지 않는다.

### 3.3 신입사원 교육용

**점수: 62/100**

적합한 부분:

- 차량을 하나의 시스템으로 보고 도메인·기능·E/E·SW 경계를 오가는 큰 그림 교육
- 고장 현상과 최초 불일치 경계를 연결하는 사고방식
- 기대값과 실제값을 비교하고 가설을 수정하는 기본 검증 태도

부족한 부분:

- 각 전문용어가 등장하기 전에 쉬운 말→현업 용어의 2단계 설명이 없다.
- 한 화면에서 추상화 관점, 도메인, 기능, 하드웨어, SW 블록을 동시에 읽어야 한다.
- 교육목표가 “설명할 수 있다/구분할 수 있다/설계할 수 있다/판정할 수 있다” 중 무엇인지 단계별로 명시되지 않는다.
- 사전진단, 난이도 분기, 보충 설명, 마무리 회상이 없다.

### 3.4 실무교육용·검증 역량

**점수: 47/100**

현재 실험실은 SW/ECU 통합/시스템/차량 경계를 보여주는 **검증 개념 시각화**로는 유용하다. 하지만 플레이어가 테스트케이스를 설계하지 않고 기법·값 버튼을 고른 뒤 실행하므로 다음 실무 역량을 측정하지 못한다.

- 요구사항에서 검증 가능한 조건과 허용오차를 추출하는 능력
- 정상·경계·비정상 등가 클래스를 만드는 능력
- 상태·전이·시간 조건을 식별하는 능력
- 적절한 입력 인가 지점과 관측 지점을 선택하는 능력
- 기대결과/오라클과 PASS/FAIL 기준을 정의하는 능력
- 고장 주입 위치·지속시간·복구 조건을 정의하는 능력
- 요구사항–TC–결과–결함의 추적성을 설명하는 능력

따라서 현 상태를 “실무 검증 교육”이라고 부르기보다는 **자동차 SW 검증 사고방식 입문 게임**이라고 부르는 것이 정확하다.

### 3.5 자동차 도메인

**점수: 65/100**

구동·제동·조향·전원·기어·열관리·현가를 핵심 도메인으로 묶고 운전자 입력–제어–액추에이터–물리 거동을 연결한 방향은 타당하다. EV 배터리·인버터·모터와 다중 하네스를 한 줄 직렬이 아닌 분기 구조로 바꾼 것도 개선이다.

한계는 콘텐츠가 구동 페달 변환, 열관리 팬, 제동 블렌딩에 집중되어 있다는 점이다. 도메인 통합의 실제 난점인 토크 중재, 에너지/열 제한, 진단 폴백, 네트워크 지연, 센서 다중화, 액추에이터 포화, 기능 간 우선순위가 사례로 충분히 등장하지 않는다.

### 3.6 시스템적 관점

**점수: 74/100**

현재의 올바른 분류는 다음과 같다.

- 최상위 대상: 차량 시스템
- 기능 분해: 도메인 → 기능
- 구현/관찰 관점: Vehicle/System, E/E Architecture, Control Software
- 제어 대상 경계: Physical Plant
- 검증 경계: SW → ECU 통합 → 차량 시스템 → 차량 시나리오

도메인 아래에 E/E와 SW가 단순 종속된다고 가르치면 잘못된 정신모형을 만들 수 있다. 현재처럼 도메인과 관점을 직교축으로 취급하는 방향이 맞다. 다만 UI에서 여전히 좌측 세로 단계로 보이므로 초보자는 계층으로 오해할 수 있다. 향후에는 `도메인 선택`과 `관점 렌즈 선택`을 시각적으로 완전히 분리해야 한다.

### 3.7 레이어 관점

**점수: 70/100**

강점은 같은 기능 슬라이스를 서로 다른 경계에서 보는 경험이다. 약점은 레이어마다 입력·출력의 의미가 바뀐다는 사실을 플레이어가 직접 설명하거나 선택하지 않는다는 점이다. 레이어별로 다음 질문을 반복해야 한다.

- 이 경계 밖에서 들어오는 것은 무엇인가?
- 이 경계 안에서 책임지는 것은 무엇인가?
- 관측 가능한 출력은 무엇인가?
- 이 경계에서 검출 가능한 고장은 무엇인가?
- 다음 상위 경계에서만 발견되는 문제는 무엇인가?

## 4. 3D 통합 실험실 검수 결과

### 수정 완료

- 이전 단계 버튼을 실험실 제목/탭과 분리된 상단 스트립으로 이동
- 우측 상단 추격 격차 박스의 텍스트와 수치 가시성 복원
- SW 화면의 상속된 중앙 정렬 때문에 플로차트가 축소되던 문제 수정
- SW 플로차트를 비교 보드 전체 폭으로 확장하고 8개 블록·분기·피드백 노출
- 정상/사용자 설계에 새 칠판형 3D 비교 프레임 적용
- VS 배지를 평면 원형에서 눌린 실험 라벨 형태로 수정
- ECU 통합·시스템·차량 뷰가 비교 프레임 안에서 잘리지 않도록 영역 고정
- TC 콘솔과 실행 버튼의 텍스트 넘침을 제한
- 공통 주요 버튼에 동일한 3D 버튼 에셋과 눌림 상태 적용

### 아직 근본적으로 부족한 점

- ECU·센서·액추에이터 모델은 교육용 아이콘형 3D이며 실제 부품 디지털 트윈 수준이 아니다.
- 정상 설계와 사용자 설계의 차이를 눈으로 찾는 시각적 강조가 더 필요하다.
- 시험 실행 전 플레이어가 스스로 TC를 설계하지 않는다.
- 동일 TC가 네 레이어에서 어떻게 매핑되는지 표 또는 애니메이션으로 추적되지 않는다.

## 5. 검증 학습 개편 제안 — 검토 후 반영 권장

### 5.1 핵심 규칙

실험실의 목표를 `네 탭을 모두 실행하기`에서 `요구사항으로부터 최소 충분 TC 세트를 설계하고, 어느 경계에서 최초 불일치가 생기는지 찾기`로 바꾼다.

플레이어가 매 TC마다 직접 정해야 할 항목:

1. 요구사항/검증목적
2. 사전조건
3. 시험기법
4. 입력 인가 지점
5. 입력값 또는 시간 시퀀스
6. 관측 지점
7. 기대결과와 허용오차
8. 종료/복구 조건

### 5.2 정상 시나리오 미션

예: `D단·READY 상태에서 APS 60% 입력 시 허용 토크 범위 안의 명령이 출력된다.`

플레이어가 구성할 최소 TC:

- 대표 정상값: APS 60%, D, READY
- 정상 하한/상한: APS 0%, 100%
- 인터록: P/N 또는 READY 아님
- 시간 응답: 입력 후 명령 형성 시간

점수는 단순 TC 개수가 아니라 요구사항 조건 커버리지, 불필요한 중복, 기대값 정확성으로 계산한다.

### 5.3 고장 시나리오 미션

예: `APS A/B 차이가 임계값을 일정 시간 초과하면 토크를 차단하고 진단 상태로 전이한다.`

플레이어가 선택:

- 고장 유형: stuck-at, 범위 초과, A/B 불일치, timeout, noisy signal
- 고장 위치: 센서, I/O 변환, CAN, SW 블록, 액추에이터 피드백
- 크기/지속시간: 임계값 바로 아래, 바로 위, 시간 한계 전/후
- 기대 반응: 검출, 디바운스, 안전 출력, DTC/상태, 복구

고장 주입은 “고장 주입” 버튼 하나가 아니라 **어디에·무엇을·얼마나·언제** 넣는지 설계해야 한다.

### 5.4 시험기법을 문제에 맞게 고르게 하기

| 요구사항 형태 | 적절한 기법 | 게임 조작 |
|---|---|---|
| 연속 입력 범위 | 등가분할·경계값 | 정상/비정상 구간을 자르고 대표값 배치 |
| 여러 조건 조합 | 결정 테이블 | D/READY/고장 조건 조합에서 필요한 행 선택 |
| 상태와 순서 | 상태전이 | OFF→READY→DRIVE→FAULT 전이 경로 연결 |
| 원인–결과 조합 | 원인결과 그래프 | 조건 핀과 기대 반응 핀 연결 |
| 시간·통신 | 타이밍/timeout | 타임라인에 입력·응답·한계 마커 배치 |
| 센서/부품 고장 | 고장 주입 | 주입 위치·값·지속시간 카드 배치 |

기법 이름을 먼저 외우게 하지 말고, 요구사항 문장 구조를 보고 적절한 도구를 선택하게 해야 한다.

### 5.5 레이어별 같은 TC의 매핑

한 TC를 네 번 따로 만들지 않는다. 하나의 TC가 경계마다 다음과 같이 변환돼 보이게 한다.

- SW: 변수 입력 → 함수/상태 출력
- ECU 통합: 핀/버스 입력 → 실제 ECU 출력과 Plant 피드백
- 시스템: 여러 ECU·네트워크·기능 상호작용
- 차량: 운전자 조작·환경 → 가속/감속/온도 등 차량 성능

플레이어는 각 레이어의 인가점·관측점만 선택하고, 게임은 같은 요구사항 ID와 TC ID를 유지한다. 그러면 추적성을 별도 문서 공부가 아니라 게임 조작으로 이해할 수 있다.

### 5.6 초보/실무 모드 분리

- 초보 모드: Given–When–Then 문장, 추천 후보, 허용오차 제공
- 기본 모드: 기법과 입력/오라클을 플레이어가 선택
- 실무 모드: 불완전·모호 요구사항을 먼저 찾아 수정하고 TC 설계

## 7. 이전 해적선 엔딩 요구사항 재정리 및 현재 상태

사용자가 반복해서 요구한 엔딩 조건:

- 결승은 일반 F1 결승선이 아니라 해적선 갑판
- 해적선 옆 바닥이나 물로 빠지면 안 됨
- 부두 연결 나무판자가 지렛대처럼 위로 들려야 함
- 붉은 EV가 경사판을 타고 실제로 도약해야 함
- 도약 순간 측면 카메라로 전환
- 경찰차는 함께 떨어지거나 겹치지 않고 부두 끝에 멈춤
- 자동차와 고양이는 해적선 갑판에 착지
- 착지 후에만 탈출 성공 엔딩으로 전환
- 마지막 접근 중 경찰차 0m 판정이 엔딩을 가로채지 않아야 함

현재 구현은 최종 도로 1050m부터 램프 진입을 확정하고, 1110m에서 독립 도약 시퀀스로 원자적으로 전환한다. 브라우저 QA에서 `SHIP_ESCAPE → SHIP_BOARDING → ENDING` 전환, 공중 도약 장면, 최종 `탈출 성공 (ESCAPED: YES)` 화면까지 확인했다.
