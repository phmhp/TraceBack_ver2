# PART 0. 작업 전제 및 최우선 지시사항

## 0-1. 프로젝트 현황

현재 자동차 SW 검증 교육용 웹 게임 프로젝트가 이미 로컬 환경에 존재하며, 이전까지 Codex를 통해 개발을 진행해 왔다.

이번 작업은 신규 프로젝트 생성이 아니다.

**현재 로컬에 존재하는 프로젝트를 그대로 이어서 리팩토링하고 확장하는 작업이다.**

다음 행위를 금지한다.

- 새로운 프로젝트를 별도로 생성하는 행위
- 기존 소스코드를 무시하고 전면 재작성하는 행위
- 기존 게임의 스토리와 진행 흐름을 임의로 변경하는 행위
- 기존 UI의 역할과 레이아웃을 임의로 변경하는 행위
- 기존에 완성된 기능을 삭제하거나 단순화하는 행위
- 기존 3D 에셋을 검토하지 않고 무조건 교체하는 행위
- 구현되지 않은 기능을 구현 완료했다고 표시하는 행위
- 근거가 불분명한 자동차 기술을 실제 업계 표준처럼 표현하는 행위

기존 프로젝트의 구현 상태를 존중하되, 기술적으로 잘못된 부분과 시각적으로 개선이 필요한 부분은 근거를 제시하고 수정한다.

## 0-2. 현재 작업 디렉터리 확인

먼저 Codex가 현재 열어둔 로컬 프로젝트의 작업 경로를 확인한다.

다음 사항을 점검한다.

1. 프로젝트 루트 디렉터리
2. Git 저장소 및 현재 브랜치
3. 최근 커밋 내역
4. 미커밋 변경 사항
5. 현재 실행 가능한 프로젝트인지
6. 사용 중인 프레임워크 및 라이브러리
7. 기존 게임의 화면 및 기능 구성
8. 3D 모델링 및 이미지 에셋의 위치
9. 이전 개발에서 미완성으로 남은 기능
10. 현재까지 구현된 게임의 실제 작동 상태

기존 코드와 현재 Git 변경 사항을 보존한다.

작업 전 복구 가능한 커밋 또는 별도 브랜치를 확보하되, 미커밋 변경 사항을 무조건 초기화하거나 덮어쓰지 않는다.

## 0-3. 작업 진행 원칙

기존 프로젝트를 처음부터 다시 분석하는 것이 아니라, 현재 상태를 기준으로 변경이 필요한 부분을 확인한다.

기존에 이미 구현된 기능과 재사용 가능한 코드는 유지한다.

코드를 수정하기 전 다음을 정리한다.

- 현재 구현 상태
- 기존 기능 중 재사용할 부분
- 수정할 부분
- 새로 추가할 부분
- 기존 기능에 영향을 줄 수 있는 부분
- 6일 이내 구현 가능한 범위
- 6일 이후 확장할 범위

분석 결과를 먼저 보고한 후 구현에 착수한다.

단, 분석 과정에서 불필요하게 사용자에게 이미 결정된 사항을 반복 질문하지 않는다. 기존 코드와 본 문서에 정의된 내용을 우선 적용한다.

# PART 1. 프로젝트의 정체성과 최종 목표

## 1-1. 프로젝트 정의

이 프로젝트는 EV를 기반으로 차량공학과 자동차 SW 검증을 학습하는 인터랙티브 웹 게임이다.

궁극적인 목표는 차량의 실제 부품과 시스템을 이해하고, SW 제어로직이 HW를 작동시키며, 그 결과가 차량 거동으로 이어지는 전체 과정을 직접 체험하고 검증할 수 있도록 하는 것이다.

단순한 자동차 레이싱 게임도 아니고, 3D 부품 전시 사이트도 아니며, 단순한 Flowchart 에디터도 아니다.

**차량의 기계적 구조, 전기적 연결, SW 제어로직, ECU 통신, 시스템 통합 및 차량 거동을 하나의 연속된 환경에서 학습하는 교육용 플랫폼**이다.

## 1-2. 최종적으로 구축할 네 가지 환경

1. 차량 주행 및 레이싱 환경
2. 차량 도메인 및 기계부품 학습 환경
3. SW/HW 동작원리 및 시뮬레이션 검증 환경
4. E/E 아키텍처 및 전체 차량 시스템 통합 환경

이 네 가지 환경은 별도의 독립 콘텐츠가 아니라 동일한 차량 시스템 모델과 데이터를 공유해야 한다.

## 1-3. 최우선 설계 원칙

- 레이싱 환경은 가볍고 자연스러운 차량 외형에 집중한다.
- 학습 환경은 실제 기계부품과 유사한 고품질 3D 모델을 사용한다.
- 검증 환경은 학습 환경과 동일한 고품질 3D 에셋을 재사용한다.
- 부품별 고유 ID와 입출력 포트를 정의한다.
- SW 출력과 HW 작동을 연동한다.
- HW 상태 변화가 SW 입력으로 돌아오는 피드백을 구현한다.
- 실제 시뮬레이션 값과 시각화 결과가 일치해야 한다.
- 사용자가 원하는 부품만 선택하여 가상 시스템을 구성할 수 있어야 한다.
- 향후 E/E 아키텍처 및 도메인 간 의존성 분석으로 확장할 수 있어야 한다.

# PART 2. 기존 게임의 스토리 및 진행 흐름 보존

기존 게임의 스토리, 캐릭터, 사건, 퀘스트, 게임 진행 방식은 유지한다.

화면이나 콘텐츠를 임의로 새로 구성하지 않는다.

기존 프로젝트의 실제 구현을 기준으로 세부 화면 명칭과 순서를 확인한다.

현재 정의된 주요 진행 흐름은 다음과 같다.

## 2-1. 차고지

- 차량 및 자동차 도메인 학습
- 주요 부품과 기능 확인
- 차량 시스템 구성 이해
- 개별 부품 탐색 및 관찰

## 2-2. 메모판

- 고장 단서 확인
- 원인 후보 선택 및 취소
- 관찰한 현상과 원인 가설 연결
- 추론 과정 관리

## 2-3. SW 로직 작업대

- 요구사항 확인
- Flowchart 구성
- SW 로직 퍼즐
- 입력·출력 신호 연결
- 제어 조건 및 상태 전환 확인

## 2-4. E/E 아키텍처 및 HW/SW 배선 연결

- ECU 추상화
- HW 부품 및 포트 연결
- 센서와 액추에이터 관계
- 통신 및 신호 경로 확인
- 시스템 구성 이해

## 2-5. 쌍둥이 실험대

- 정상 차량과 고장 차량 비교
- SW 로직 비교
- HW 작동 비교
- 시스템 수준의 결과 비교
- 고장 주입 및 검증

## 2-6. 레이싱

- 실제 차량을 조작하는 주행 환경
- 체크포인트 및 레이싱
- 주행 중 고장 단서 수집
- 가설에 따른 차량 거동 변화 확인
- 실패 시 체크포인트 재시도

기존에 정의한 게임 스토리와 캐릭터 관계도 유지한다.

기존 스토리의 세부 설정은 현재 프로젝트의 스토리 원본을 기준으로 하며, Codex가 임의로 각색하거나 새로운 스토리로 교체하지 않는다.

# PART 3. 3D 그래픽 개선 방향

현재 프로젝트의 주요 문제는 다음과 같다.

- 기본 도형을 조합한 것 같은 모델링
- 실제 차량과 다른 부품 비율
- 재질과 표면 표현의 부족
- 일관성 없는 알록달록한 색상
- 부품 간 크기 및 비율의 불일치
- 시각적으로 실제 기계부품이라는 신뢰감 부족

이를 해결하기 위해 용도별로 3D 에셋을 구분한다.

## 3-1. 레이싱 전용 모델

레이싱에서는 차체 외형만 보이면 된다.

차량 내부 기계부품까지 구현할 필요가 없다.

필수 요구사항:

- 실제 자동차와 유사한 차체 비율
- 자연스러운 전면·측면·후면 형상
- 적절한 휠베이스와 윤거
- 현실적인 휠과 타이어 비율
- 유리, 램프, 범퍼, 도어, 루프 등 외형 구성
- 자연스러운 차량 회전 및 주행 애니메이션
- 기존 레이싱 조작 기능 유지
- 운전자 시점과 외부 카메라 시점 지원

Low/Mid-poly 모델을 사용하여 웹게임의 성능을 확보한다.

불필요한 내부 부품 및 고해상도 형상을 포함하지 않는다.

## 3-2. 운전자 입력장치

운전자가 실제로 자동차를 조작하는 것처럼 보이도록 구현한다.

필수 모델:

- Steering Wheel
- Accelerator Pedal
- Brake Pedal
- Gear Selector
- Start/Stop Button
- Dashboard / Instrument Cluster

각 요소는 정적인 장식물이 아니라 실제 사용자 입력과 연결되어야 한다.

## 3-3. 학습 및 검증용 고품질 모델

실제 차량의 기계부품과 유사한 형상을 구현한다.

필수 기준:

- 실제 부품의 형상과 비율을 참고
- PBR 기반 재질
- 금속, 알루미늄, 고무, 플라스틱, 유리 등 재질 구분
- 부품별 독립적인 모델 관리
- 확대 및 회전에 견딜 수 있는 표면 품질
- 부품별 연결 포트 표현
- 배선 및 기계적 연결 구조 표현
- 분해도 및 작동 애니메이션을 고려한 구조

무작위적인 색상 사용을 금지한다.

기능과 재질을 구분하는 일관된 색상 체계를 사용한다.

예시:

- 금속: 알루미늄, 건메탈, 스테인리스
- 고무: 무광 블랙
- 플라스틱: 다크 그레이
- 고전압 케이블: 일반적으로 사용하는 오렌지색 식별
- 냉각수 경로: 기능 구분용 보조 색상
- 유리: 적절한 투명도 및 반사

색상만으로 기능을 전달하지 않고 라벨과 범례를 병행한다.

# PART 5. 3D 에셋 확보 및 제작 방법

## 5-1. 사용자 환경 및 제약

사용자는 Blender 등 전문 3D 모델링 도구를 이용해 직접 모델링할 수 있는 숙련자가 아니다.

따라서 모든 부품을 직접 제작하는 방식을 전제로 하지 않는다.

공개 CAD 및 3D 모델을 우선 활용한다.

## 5-2. 에셋 탐색 대상

다음 사이트를 우선 탐색한다.

1. Sketchfab
2. Poly Haven
3. BlenderKit / Blendkit
4. GrabCAD
5. 제조사에서 공개한 CAD 자료
6. 기타 적법하게 사용할 수 있는 3D 라이브러리

각 사이트의 모델을 실제로 검색할 수 있는지, 다운로드할 수 있는지, 라이선스 확인이 가능한지 먼저 확인한다.

인터넷 검색이나 다운로드 도구에 접근할 수 없는 경우 해당 기능이 없는 사실을 명확하게 보고한다.

실제로 검색하지 않은 모델을 검색했다고 주장하거나 존재하지 않는 URL을 생성하지 않는다.

## 5-3. 에셋별 라이선스 확인

모든 외부 에셋에 대해 다음 항목을 확인한다.

- 원본 URL
- 제작자
- 라이선스 종류 및 버전
- 상업적 이용 허용 여부
- 수정 및 2차 가공 허용 여부
- 웹게임 내 포함 및 배포 가능 여부
- 출처 표기 의무
- 원본 파일 보관 여부

무료 다운로드와 자유로운 재배포를 동일하게 취급하지 않는다.

라이선스가 불분명한 모델은 공모전 제출물에 사용하지 않는다.

향후 사업화와 저작권 확보 가능성을 고려하여 CC0 또는 상업적 이용과 수정·재배포가 명확하게 허용되는 에셋을 우선한다.

## 5-4. 모델 탐색 결과 형식

부품별로 2~3개 후보를 제시한다.

각 후보에 대해 다음을 정리한다.

- 부품명
- 원본 URL
- 미리보기 이미지
- 제작자
- 파일 형식
- 라이선스
- 상업적 이용 및 재배포 가능 여부
- 부품 분리 여부
- 애니메이션 지원 여부
- 실제 프로젝트 활용 적합성
- 추가 가공 필요성

가능하면 모델을 다운로드하기 전에 사용자에게 후보를 보여주고 승인을 받는다.

## 5-5. 에셋 제작 및 가공

기존 에셋을 우선 활용하되 필요하다면 다음을 수행한다.

- Blender Python을 통한 자동화
- 모델 크기 및 비율 조정
- 불필요한 형상 제거
- 재질 및 색상 통일
- 부품별 Mesh 분리
- 포트 위치 표시
- 애니메이션용 피벗 설정
- GLB 변환 및 최적화

정확한 모델을 확보하지 못한 경우 임의의 단순 도형을 실제 기계부품처럼 표현하지 않는다.

교육용 단순화 모델을 사용할 경우 단순화된 형상이라는 사실을 구분한다.

## 5-6. 모델 종류 구분

부품별로 다음 모델 유형을 구분한다.

- Static Model: 외형 관찰
- Separated Assembly: 분해 및 조립
- Animated/Rigged Model: 작동원리 시각화

360도 관찰만 필요한 모델과 실제 회전·이동이 필요한 모델을 구분해 에셋을 확보한다.

# PART 7. 운전자 입력장치와 레이싱 인터랙션

운전자가 실제로 자동차를 조작하는 듯한 경험을 구현한다.

## 7-1. 입력장치와 키보드 매핑

기본 매핑:

| 운전자 입력 | 장치 | 키보드 |
|---|---|---|
| 시동 | Start/Stop Button | Enter |
| 가속 | Accelerator Pedal | W |
| 제동 | Brake Pedal | S |
| 좌회전 | Steering Wheel | A |
| 우회전 | Steering Wheel | D |
| 보조 제동 | 설정 가능한 보조 입력 | Space |

기존에 사용 중인 조작 방식과 충돌하는 경우 기존 기능을 보존하면서 조정한다.

## 7-2. 실제 입력 신호 생성

키보드 이벤트를 곧바로 차량 속도에 연결하지 않는다.

입력장치의 물리적 입력값을 생성한다.

예시:

- StartRequest
- APP_Position
- BPP_Position
- Steering_Angle
- Gear_Request

입력값은 제어 SW의 입력으로 전달되어야 한다.

## 7-3. 물리적 동작

사용자 입력에 따라 다음이 함께 움직여야 한다.

- 가속 페달
- 브레이크 페달
- 스티어링 휠
- 시동 버튼
- 앞바퀴 조향각
- 차량의 진행 방향
- 계기판 표시

운전자 입력과 실제 차량의 거동이 자연스럽게 연결되어야 한다.

# PART 8. SW/HW 양방향 시뮬레이션

이 프로젝트의 장기적인 핵심 기능이다.

단순한 3D 애니메이션이 아니라 SW와 HW가 공통된 시뮬레이션 상태를 공유해야 한다.

## 8-1. 기본 계층

1. Driver Input Layer
2. Sensor/Input Signal Layer
3. Control Software Layer
4. Communication Layer
5. Hardware/Plant Layer
6. Vehicle Dynamics Layer
7. Monitoring and Feedback Layer

각 계층의 역할과 입출력을 정의한다.

## 8-2. SW Flowchart

Simulink와 유사한 블록 기반 구조를 지향한다.

필수 블록:

- Input
- Output
- Constant
- Gain
- Sum
- Product
- Compare
- Switch
- Logic Gate
- Unit Delay
- Filter
- Saturation
- Lookup Table
- State Machine
- Function
- Signal Routing

각 블록은 입력 및 출력 포트를 가져야 한다.

블록 사이의 선은 실제 신호 연결을 나타낸다.

시뮬레이션 중 실행 중인 블록과 신호 흐름을 강조한다.

## 8-3. HW와의 연결

SW 출력이 HW 부품의 입력 포트로 전달되어야 한다.

예시:

- VCU Torque Request → MCU
- MCU Control Command → Inverter
- Inverter Output → Motor
- Motor Torque → Reduction Gear
- Reduction Gear Output → Drive Shaft
- Drive Shaft → Wheel

반대 방향의 피드백도 표현한다.

- Wheel Speed Sensor → ECU
- Motor Position Sensor → MCU
- Battery Voltage Sensor → BMS
- Temperature Sensor → BMS 또는 관련 ECU

## 8-4. 물리적 흐름과 데이터 흐름 구분

다음 유형을 별도로 표현한다.

- Electrical Power
- Mechanical Torque
- Rotational Speed
- Hydraulic Pressure
- Thermal Energy
- Digital Signal
- Analog Signal
- Communication Message

전력, 기계적 동력, 유체, 데이터 신호를 동일한 종류의 선으로 표현하지 않는다.

각 흐름에는 방향, 단위, 전달 대상, 상태를 표시한다.

## 8-5. Step-by-step Simulation

필수 기능:

- Step Forward
- Step Backward
- Play
- Pause
- Reset
- 반복 재생
- 특정 단계 선택
- 실행 속도 조절

각 단계에서 다음 정보를 보여준다.

- 현재 실행 블록
- 입력값
- 출력값
- 단위
- 처리 결과
- 신호 전달 방향
- HW에서 발생한 변화
- 시뮬레이션 시간

3D 부품의 동작과 Flowchart의 실행 위치를 동기화한다.

# PART 17. 사용자와 AI 간 기존 질문·답변 및 확정 요구사항

이 항목은 이번 프로젝트와 관련하여 사용자가 질문한 내용과 논의 과정에서 정리된 답변을 요구사항으로 보존하기 위한 것이다.

아래 내용을 새로운 구현 요구사항의 근거로 활용한다.

## Q1. 자동차 동역학 연구실이나 차량 구동원리, 도메인 구성 등을 시뮬레이션하려면 어떻게 해야 하는가?

**A.**

단순한 3D 모델링이 아니라 물리 모델, 제어 SW, HW 모델, 시스템 연결, 시각화 계층을 분리해야 한다.

권장 구조:

- 3D 시각화: 차량 및 부품 모델
- SW 엔진: 제어로직과 Flowchart
- Plant 엔진: 배터리, 모터, 구동계, 제동계 등의 물리 모델
- 통신 엔진: ECU 및 신호 전달
- 시스템 엔진: 도메인 간 상호작용
- 검증 엔진: 테스트, 고장 주입, 결과 비교

MATLAB/Simulink와 유사한 개념을 독립적인 웹 기반 구조로 구현할 수 있다.

## Q2. 운전자 입력요소는 액추에이터인가?

**A.**

일반적으로 운전자 입력요소는 액추에이터가 아니라 입력장치 또는 HMI로 분류한다.

예시:

- 가속 페달
- 브레이크 페달
- 스티어링 휠
- 기어 셀렉터
- 각종 스위치

이들은 운전자의 의도를 차량에 전달한다.

액추에이터는 제어기의 명령을 받아 실제 물리적인 동작을 발생시키는 장치다.

예시:

- 구동모터
- EPS 모터
- 브레이크 액추에이터
- 냉각 펌프
- 냉각 팬
- 밸브 액추에이터

브레이크 페달과 전자식 브레이크 구동장치는 서로 다른 역할을 한다.

## Q3. 운전자 입력요소가 아니면 모두 액추에이터인가?

**A.**

아니다.

차량 부품은 다음과 같이 구분한다.

1. 운전자 입력장치
2. 센서
3. ECU 및 제어기
4. 액추에이터
5. 수동 기계부품
6. 전력 및 에너지 부품
7. 통신 및 연결 부품

예를 들어:

- 휠 속도 센서: 센서
- VCU: 제어기
- 구동모터: 액추에이터이자 전기기계적 에너지 변환 장치
- 감속기: 수동 기계부품
- 배터리: 에너지 저장장치
- 인버터: 전력변환 장치

부품 분류는 기능과 시스템 내 역할을 기준으로 한다.

하나의 부품이 복수의 관점에서 분류될 수 있다는 점도 고려한다.

## Q4. 게임에서 사용자가 직접 운전자 입력장치를 작동하고 차량을 움직일 수 있는가?

**A.**

가능하며 필수 구현 방향이다.

키보드 입력을 실제 입력장치의 신호로 변환한다.

예를 들어 가속 페달을 40% 밟으면:

1. 가속 페달 3D 모델이 움직인다.
2. APP_Position 신호가 생성된다.
3. 제어 SW에 입력된다.
4. 토크 요구량을 계산한다.
5. MCU 및 인버터로 명령이 전달된다.
6. 모터 토크가 발생한다.
7. 감속기와 구동축을 통해 휠이 회전한다.
8. 차량 속도와 가속도가 변한다.
9. 센서 피드백이 다시 SW로 전달된다.

이 흐름이 실제 게임 조작과 연동되어야 한다.

## Q5. 레이싱용 모델과 학습·검증용 모델을 분리해야 하는가?

**A.**

그렇다.

레이싱에서는 차량 외형만 보여주므로 Low/Mid-poly 모델을 사용한다.

학습 및 검증 환경에서는 실제 기계부품에 가까운 고품질 모델을 사용한다.

단, 학습 환경과 검증 환경은 반드시 동일한 고품질 에셋을 공유한다.

이렇게 하면 레이싱 성능과 부품 학습의 시각적 품질을 동시에 확보할 수 있다.

## Q6. 고품질 3D 모델을 사용하면 웹게임이 느려지지 않는가?

**A.**

최적화 없이 사용하면 느려질 수 있다.

다음 기법을 적용한다.

- LOD
- Meshopt / Draco
- KTX2/Basis
- Lazy Loading
- Instancing
- Draw Call 최적화
- 텍스처 최적화
- 씬별 에셋 로딩 및 해제

레이싱 씬에서는 경량 모델만 로딩하고, 학습·검증 환경에서 필요한 고품질 모델을 사용한다.

## Q7. 3D 부품의 360도 뷰와 작동원리 확인이 가능한가?

**A.**

가능하다.

부품별 독립 모델을 사용하고 다음 기능을 구현한다.

- 회전
- 확대 및 축소
- 부품 선택
- 분해도
- 단면
- 내부 구조
- 작동 애니메이션
- 연결 포트 표시

예를 들어 모터는 하우징, 스테이터, 로터, 샤프트를 분리하고 로터 회전 애니메이션을 구현한다.

배터리는 하우징, 모듈, 셀, 냉각판을 구분하여 내부 구조를 보여준다.

## Q8. SW의 제어로직과 HW 부품의 실제 작동을 연결할 수 있는가?

**A.**

가능하며 프로젝트의 핵심 목표다.

SW의 입력·연산·출력과 HW의 상태 변화를 공통 시뮬레이션 상태로 연결한다.

SW Flowchart에서 실행된 블록이 3D 부품의 동작으로 이어져야 한다.

반대로 센서 및 부품 상태 변화도 SW 입력으로 전달되어야 한다.

단순한 장식용 애니메이션과 실제 시뮬레이션 결과를 구분한다.

## Q9. Simulink처럼 SW Flowchart를 구성하고 값을 확인할 수 있는가?

**A.**

가능하다.

블록 기반 구조를 사용한다.

Input, Output, Gain, Sum, Compare, Switch, Unit Delay, Filter, State Machine 등 일반적인 제어 블록을 제공한다.

각 블록의 입출력 값과 실행 상태를 표시한다.

시뮬레이션을 단계별로 진행하거나 자동 재생할 수 있어야 한다.

## Q10. SW/HW 연결을 부품 간 시뮬레이션과 E/E 아키텍처 관점으로 모두 보여줄 수 있는가?

**A.**

가능하다.

다음 관점을 지원하도록 설계한다.

- 개별 부품 관점
- 기계적·전기적 연결 관점
- ECU 추상화 관점
- 도메인 통합 관점
- 전체 차량 관점

ECU를 추상화된 노드로 표시하고 각 노드의 입출력 신호와 통신 관계를 연결한다.

## Q11. 특정 도메인에서 원하는 부품만 선택해 시뮬레이션할 수 있는가?

**A.**

가능하다.

다만 단순히 화면에서 숨기는 기능과 시뮬레이션에서 실제로 제외하는 기능은 구분해야 한다.

Visibility, Selection, Inclusion, Connection, Dependency를 각각 관리한다.

예를 들어 배터리를 제외하면 전력 공급 경로와 BMS 관련 기능이 영향을 받는지 분석할 수 있어야 한다.

추후에는 부품 의존성 및 대체 경로 분석으로 확장한다.

## Q12. MATLAB/Simulink를 연동하는 것이 좋은가?

**A.**

구현 편의성 측면에서는 장점이 있지만, 현재 프로젝트에서는 라이선스와 예제 저작권, 배포 가능성을 고려해 독립적인 웹 기반 시뮬레이션 엔진을 우선한다.

기존 MATLAB/Simulink 모델을 무조건 복제하거나 예제를 무단으로 가져오지 않는다.

공개적으로 이용할 수 있는 기술과 독립적으로 구현한 교육용 모델을 사용한다.

## Q13. 특정 OEM의 기술이나 용어를 사용하지 않고 업계 공통 기술만 사용할 수 있는가?

**A.**

가능하다.

특정 OEM의 비공개 양산 로직과 독자적인 명칭을 사용하지 않는다.

AUTOSAR, ASAM, ISO, SAE 등 공개 표준 체계와 업계 공통 기술을 기반으로 한다.

기술적으로 실제 사용되는 명칭과 교육용 단순화 모델을 구분한다.

## Q14. 6일 안에 모든 기능을 완성할 수 있는가?

**A.**

전체 차량 시스템의 완전한 디지털 트윈을 6일 안에 구현하는 것은 현실적이지 않다.

따라서 이번 제출에서는 다음에 집중한다.

- 기존 게임 보존

- 핵심 부품 고품질 모델 확보
- 학습 및 검증 환경의 에셋 공유
- 부품 360도 뷰
- 핵심 부품 포트 및 연결 시각화
- 핵심 입력→SW→HW→차량 반응 경로 구현
- Step-by-step 시각화
- 향후 확장 가능한 데이터 구조

부품 의존성 전체 분석과 모든 도메인의 완전한 물리 모델링은 후속 개발 범위로 분리한다.

## Q15. 3D 모델링을 사용자가 직접 해야 하는가?

**A.**

아니다.

사용자는 3D 모델링 숙련자가 아니므로 처음부터 직접 제작하는 방식을 전제로 하지 않는다.

공개 CAD 및 3D 에셋을 우선 확보한다.

Codex는 실제로 접근할 수 있는 검색·다운로드 도구가 있다면 에셋 탐색을 수행하고, 그렇지 않다면 검색 키워드와 후보 목록을 작성한다.

확보한 모델은 Blender 또는 자동화 스크립트를 통해 정리하고 GLB로 변환한다.

Codex는 에셋의 웹게임 통합, 로딩, 애니메이션, 포트 연결 및 상호작용을 담당한다.

# PART 19. 최종 실행 지시

이 문서를 현재 로컬 프로젝트의 최종 리팩토링 요구사항으로 사용한다.

먼저 현재 작업 디렉터리의 상태를 확인하고 기존 구현과 이번 요구사항을 비교한다.

기존 프로젝트의 구조, 기능, 에셋을 보존하면서 변경할 부분만 명확하게 구분한다.

특히 다음 사항을 최우선으로 지킨다.

1. 기존 프로젝트를 새로 만들지 않는다.
2. 기존 게임의 스토리와 흐름을 변경하지 않는다.
3. 기존 UI를 임의로 재설계하지 않는다.
4. 기존에 구현한 코드를 충분히 재사용한다.
5. 3D 에셋은 공개 자료를 우선 탐색한다.
6. 라이선스가 확인되지 않은 에셋은 사용하지 않는다.
7. 실제 부품과 교육용 단순화 모델을 구분한다.
8. 학습과 검증 환경의 3D 에셋을 공유한다.
9. 레이싱은 경량화된 외형 모델을 사용한다.
10. SW/HW 동작을 동일한 시뮬레이션 상태에 연결한다.
11. 업계 공통 기술과 공개 자료만 근거로 한다.
12. 6일 내 제출 가능한 기능부터 우선 구현한다.

**최종적으로 지향하는 것은 차량의 물리적 구성부터 SW 제어, ECU 통신, HW 동작, 시스템 통합, 차량 거동까지 하나의 연속된 환경에서 이해하고 실험할 수 있는 EV Vehicle Logic Lab이다.**

기존 프로젝트의 정체성을 유지하면서 이 방향으로 발전시킨다.

## 작업 시작 순서

1. 현재 로컬 프로젝트 및 Git 상태 확인
2. 기존 기능과 미완성 기능 확인
3. 기존 에셋 인벤토리 작성
4. 요구사항별 현재 구현 상태 비교
5. 6일 MVP 작업 계획 제시
6. 공개 에셋 탐색 및 라이선스 확인
7. 승인된 범위부터 구현
8. 테스트 및 회귀 검증
9. 최종 제출물 정리

분석 결과와 구현 계획을 먼저 제시한 후 작업을 시작한다.

기존 파일을 삭제하거나 대규모로 변경하기 전에는 복구 가능성을 확보한다.

작업이 끝날 때마다 실제 구현 상태와 미완성 항목을 구분하여 보고한다.

# 추가 확정 요구사항: 3D 에셋 품질 정책

## 1. 최우선 원칙

레이싱 환경과 학습·검증 환경의 3D 에셋 품질 정책을 명확하게 구분한다.

### A. 레이싱 환경
- 차량 차체 외형만 모델링한다.
- Low/Mid-poly 모델을 사용한다.
- 내부 기계부품은 모델링하지 않는다.
- 주행 성능과 프레임 유지에 집중한다.

### B. 학습 및 검증 환경
- 시각화 대상에 포함되는 모든 부품은 고품질 3D 에셋을 사용한다.
- 액추에이터뿐 아니라 센서, ECU, 전력변환 장치, 에너지 저장장치, 수동 기계부품, 배관, 배선 및 커넥터까지 포함한다.
- 특정 도메인 또는 특정 부품만 저품질 기본 도형으로 표현하는 것을 금지한다.
- 도메인 단위로 여러 부품을 함께 시각화하거나 전체 차량 시스템을 통합했을 때도 모든 부품의 시각적 품질이 일관되어야 한다.

## 2. 고품질 에셋의 정의

고품질은 단순히 폴리곤 수가 많다는 의미가 아니다.

다음 조건을 만족해야 한다.

- 실제 부품과 유사한 형상 및 비율
- 부품별 구조적 특징 반영
- 재질 특성에 맞는 PBR
- 금속, 플라스틱, 고무 등 표면 특성 구분
- 커넥터, 체결부, 하우징 등 주요 구조 표현
- 확대 및 회전 관찰에 적합한 품질
- 전체 프로젝트에서 통일된 시각적 완성도

기본 도형을 조합한 임시 모델을 실제 기계부품처럼 표현하지 않는다.

## 3. 품질과 성능의 분리

학습 및 검증 환경의 모든 시각화 대상은 고품질 에셋으로 통일하되, 성능은 별도의 최적화 계층에서 관리한다.

- LOD
- Meshopt / Draco
- KTX2/Basis
- Lazy Loading
- Instancing
- 적절한 텍스처 해상도
- 씬별 로딩 및 해제
- 카메라 거리 기반 디테일 관리

성능 최적화를 이유로 학습·검증 화면의 일부 부품을 기본 도형이나 저품질 임시 모델로 대체하지 않는다.

## 4. 에셋 확보 기준

모든 부품은 공개 CAD 및 3D 에셋을 우선 탐색한다.

에셋이 없는 경우 다음 순서로 대안을 검토한다.

1. 다른 공개 라이브러리 탐색
2. 제조사 공개 CAD 자료 탐색
3. 기존 모델의 수정 및 재가공 가능성 확인
4. Blender Python 등을 활용한 보조 모델링
5. 최후의 경우 교육용 단순화 모델을 제작하고 해당 사실을 명시

품질이 기준에 미달하는 모델은 최종 에셋으로 확정하지 않는다.

## 5. 동일 에셋 재사용

학습 환경과 검증 환경은 동일한 원본 고품질 에셋을 참조해야 한다.

도메인별 화면, 전체 차량 시스템 화면, 개별 부품 화면에서 같은 부품의 형상과 재질이 일치해야 한다.

표시 크기나 성능 최적화에 따라 LOD를 사용할 수 있지만, 서로 다른 디자인의 모델을 사용해서는 안 된다.

## 6. 최종 검수

도메인 단위로 모든 부품을 한 화면에 배치했을 때 품질 차이가 눈에 띄지 않아야 한다.

다음 항목을 확인한다.

- 모델링 품질의 일관성
- 재질과 색상 통일
- 부품별 크기 및 비율
- 실제 부품과의 형상 유사성
- 확대 및 360도 관찰 품질
- 부품 간 연결 구조
- 웹 렌더링 성능

최종적으로 학습 및 검증 환경에서는 모든 시각화 대상 부품이 동일한 고품질 에셋 정책을 따라야 한다.
