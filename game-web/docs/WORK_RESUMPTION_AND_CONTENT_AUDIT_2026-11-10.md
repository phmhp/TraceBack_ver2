### STEP03 및 중복 판정

STEP03은 빈 블록 배치→연결 확인→예시 입력의 블록별 값 확인→정상 기준 확정→`VerificationContract` 저장 순서다. STEP02의 가설 정리는 “관찰만으로 가를 수 있는가”, STEP03은 “정상 기준·시험 계약을 만들 수 있는가”이므로 삭제 대상의 완전 중복은 아니다. 다만 STEP02 마지막 가설 버튼과 STEP03 헤더의 `가려낼 가설`은 같은 결론을 되풀이하며, 전자가 실제 선택을 보존하지도 않으므로 다음 설계에서 STEP02는 **관찰 사실·경쟁 가설의 상태만**, STEP03은 **계약에 명시된 검증 질문만** 보여 주도록 합친다.

### STEP04

| 순서 | 실제 질문/행동 | 데이터·판정 | 다음 단계 |
|---|---|---|---|
| 1 | 운전자 질문마다 시험 환경 선택 | `QA_LEVELS`로 SW/제어기 I/O/부품·차량 중 선택 | `pickTest`가 화면 탭·기본 파생 입력을 설정 |
| 2 | 입력 조건 하나 선택 | `CASE_DERIVS`의 `tech` 선택; 정상·고장 모델에는 같은 `tech`가 전달 | 실행 가능 |
| 3 | “기준선·사건 결과 비교 실행” | `simulate(caseId, tech.tech, fixed)`; 현 시험 수준의 **모든** 신호 관측 | PASS/FAIL/INCONCLUSIVE와 표/그래프 표시 |

| 5 | 수리 조치 선택 | 올바른 카드만 `fixed` 상태로 진행; 틀린 카드는 설명만 표시 | 차량 수준 재시험 |
| 6 | “동일 조건 기준선 비교 실행” | 같은 `tech`로 `fixed=true`; 정상 기준과 수정 후 결과 비교 | 통과 시 수리 적용·주행 복귀 |

정상 모델은 각 `simulate` 안에서 고장/수리 모델과 함께 계산되므로 **정상 기준선 사전 확보와 고장 실행은 하나의 실행에서 자동 생성**된다. 이는 플레이어에게 정상 모델을 별도 시험으로 강제하지 않는 권고 구조에 맞는다. 수리 후 재시험은 선택한 `tech`를 유지하므로 동일한 기술 선택은 보존된다.

그러나 계약의 `preconditions`, `stimulus.sequence`, `expected`는 표시·레이블에 쓰일 뿐 `simulate`의 초기 상태·램프·시간축을 구동하지 않는다(T-24). 따라서 “동일 조건”은 현재 `tech`와 `fixed`에 한정된 코드상 주장이고, STEP03 계약 전체의 실제 실행 보증은 아니다. 수리 선택도 정답 카드의 `ok`로만 상태를 전환하며 서로 다른 수리 모델을 실행하지 않는다(T-22).
