# STEP02·STEP04 플레이 흐름 기준선

2026-11-11. 이 문서는 다음 UI/흐름 설계 승인 전의 **읽기 전용 기준선**이다. 현재 구현을 설명할 뿐, STEP02 도미노·STEP04 검증 작업대 또는 판정 로직을 바꾸지 않는다. 근거: `EeTrace.tsx`, `VerificationLab.tsx`, `content-audit-by-claude/B_PLAY_FLOW_INDEX.md`, `D1_STEP02_TRACE.md`, `D1_STEP04_VERIFICATION.md`.

## STEP02 — 원인 역추적 (`BOARD`, `EeTraceV2`)

| 현재 상태/행동 | 실제 질문·선택지·피드백 | 다음 조건·전달 데이터 | 분류 | 연결 ID | 설계 처리 |
|---|---|---|---|---|---|
| `evidence` | 실제 관찰 폴라로이드(운전자 체감·계기판·기록 등)를 열고, E/E 출력 조사로 얻은 폴라로이드를 증거판에 부착한다. | 증거/부착/탭 상태는 `tb-step02-progress-<case>`에 보존. | 선택 탐색 + 메인 작업대 조작 | K-5.1~3, L-4.2, FB-P0-01 | 유지. 질문 번호로 세지 않음. |
| `output` → `trace` | 출력에서 상류로 경로를 보고, 입력 재생 뒤 노드를 측정한다. 현재 사례의 실제 기준·사건 값과 `처음 어긋난 곳`만 표시한다. | 측정·경로·도장 상태 보존. | 메인 게임 조작 | K-5.1~4, M-03 | 유지. 역방향/최초 편차와 근본 원인은 분리. |
| `section` | “처음 어긋난 곳: {실제 노드} · 의심 구간은 어디일까요?”와 사건별 선택지. 오답은 도장·말풍선·별 감소, 정답은 `tb-section-<case>` 저장. | 의심 구간을 저장하고 가설 정리로 이동. | 필수 판단 | K-5.3~4, L-4.2 | 유지. 질문/선택지는 사건 데이터로 분리. |
| `done` 가설 정리 | 각 실제 후보에 `반박` / `보류`. “측정으로 반박되면 반박, 아직 모르면 보류.” | 전체 후보 정리 후 `OPEN_WIRING`; `tb-impact-<case>`와 붙인 실제 증거를 다음 단계로 전달. | 필수 판단 | K-5.3, L-4.2~3, L-6.3 | 유지. 시스템이 플레이어 가설을 정답으로 덮어쓰는 T-25/N-TECH-01은 별도 P0. |

**통합 검토안(미구현):** 증거 탐색·경로 측정·의심 구간·가설 정리를 하나의 도미노 작업대의 연속 상태로 유지한다. 탭 이동·폴라로이드 확대는 Q 번호가 아니며, 별도 페이지를 추가하지 않는다. 우측 증거/추리 보드는 FB-P0-01 보존 대상이다.

## STEP04 — 시뮬레이션 검증 (`TWIN_BENCH`, `TwinBenchExperience`)

| 현재 상태/행동 | 실제 질문·선택지·피드백 | 다음 조건·전달 데이터 | 분류 | 연결 ID | 설계 처리 |
|---|---|---|---|---|---|
| `pick` | 사건별 `QUESTIONS`의 질문(구동 2개, 열관리/제동 3개)과 판단 기준을 읽고 시험을 선택한다: `SW 계산만 PC`, `실제 제어기에 올려 핀 신호`, `실제 부품을 붙여`. | 선택한 시험 수준 → `lab`. | 필수 판단 | K-7.1~2, H-5, L-5.2 | 유지. 시험 선택은 메인 작업대 첫 행동. |
| `lab` | STEP03 설계서의 목적·초기 조건·입력·관찰을 확인하고, 필요한 사건에서는 입력 조건을 선택한 뒤 실행한다. 탭: `SW 로직` / `제어기·I/O` / `부품·차량` / `모니터링`. | `lastRun`(관찰·PASS/FAIL/INCONCLUSIVE·값), level, input, 탭을 보존. | 메인 게임 조작 + 선택 탐색 | K-6.5, K-7.1~7, M-05, M-09~11 | 유지. 네 관점 탭 삭제 금지; 탭 이동은 Q 번호가 아님. |
| `lab` 판정 | 질문마다 `가능성 높음` / `가능성 낮음` / `아직 모름`. 틀리면 판단 기준을 다시 안내하고, `아직 모름`이면 다른 시험을 고르게 한다. | 모든 질문의 `answers` 후 `report`. | 필수 판단 | K-7.7, L-5.2, M-11 | 유지. 시험 결과와 가설 판단은 별도 상태. |
| `report` | 실제 답·근거를 보고하고 사건별 수리 조치를 선택한다. 오답은 설명과 별 감소, 정답은 고장 SW 프로그램을 수정한다. | `fix`와 수정된 프로그램 → `retest`. | 필수 판단 | FB-P1-07, H-7 | 유지. 수정 성공을 검증 없이 확정하지 않음. |
| `retest` → `done` | “동일 조건 기준선 비교 검증”: 같은 STEP03 입력·초기 조건에서 정상 기준선과 수정 후 신호·제어 출력·차량 반응을 비교한다. | 정상 범위 충족 시 `done`; 완료 CTA는 `BENCH_RESULT(pass)` → 수리·주행 복귀. | 필수 판단 + 메인 게임 조작 | FB-P1-07, K-7, M-11 | 유지. ‘백투백 테스트’로 표기하지 않음. |

**통합 검토안(미구현):** `pick → lab → report → retest → done`을 한 검증 작업대의 상태로 유지한다. 설계서·시험 조건·네 관점·관찰/판정·같은 조건 비교를 화면 전환이 아닌 단계별 공개로 정리한다. 공통 질문 구조(`QUESTIONS`, 답 라벨, 상태 전이)와 사건 데이터(가설·판단 기준·입력·신호·수리)는 분리한다.

## 확정 전 판단이 필요한 항목

| 항목 | 현재 사실 | 승인 전 제안 |
|---|---|---|
| STEP02 가설 소유권 | 완료 시 `EeTrace.finish()`가 레거시 정답 키를 캠페인 가설로 자동 설정한다. | T-25/N-TECH-01을 먼저 해결하고, 플레이어의 보류/반박 기록과 시스템 정답을 분리한다. |
| STEP04 계약의 모델 입력 | STEP03 계약은 표시·저장되지만, 현재 일부 모델 선택은 `CASE_DERIVS`에 남아 있다. | T-24/N-TECH-02에서 계약→실행 입력 계약을 확정한 뒤 UI 흐름을 바꾼다. |

| 신규 사건 | `CaseId`와 화면 데이터가 여러 `Record<CaseId,…>`에 분산되어 있다. | 데이터 스키마/검증기를 먼저 설계하고 이번 작업에서는 구현하지 않는다. |
