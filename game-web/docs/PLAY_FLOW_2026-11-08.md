# 추리 단계 플레이 흐름 · 해답지 (2026-11-08)

## 0. 한 줄 흐름 = 스토리 = 실무

| 게임(스토리) | 실무(검증 엔지니어) |
|---|---|
| 볼트(드라이버): "페달 밟았는데 차가 안 나가!" | 고객사 문의 접수 |
| 1단계 원인 역추적: 어디서부터 이상해졌나 | 증상 → 의심 구간 좁히기 |
| 2단계 로직 퍼즐: 정상이라면 어떻게 돼야 하나 | 요구사항으로 기대값(판정 기준) 세우기 |
| 3단계 검증: 시험으로 범인 밝히기 → 볼트에게 설명 | 시험 → 원인 확정 → 고객사에 근거 설명 |
| 수리 요청 → 재시험 → 다시 주행 | 개발팀 조치 요청 → 재검증 → 회귀 |

- 너트(엔지니어)는 직접 고치지 않는다. **무엇이 고장이고 무엇은 멀쩡한지 근거로 밝혀** 볼트에게 설명하고, 수리를 요청한다.

## 1. 숫자 원칙 (머리 아프지 않게)
- 화면에 계속 보이는 숫자는 **요구사항 값 한두 개**뿐이다. 예: 페달 60% → 204 Nm, 65°C에서 팬 켜짐.
- 측정값은 **"기준 ○ / 지금 ○" 한 쌍 + 막대 + 한 단어(정상·낮음·멈춤)**로만 보여 준다.
- 소수점, 단위가 다른 여러 값, 시간축 숫자는 기본으로 숨긴다. 필요하면 카드를 눌렀을 때만 보인다.
- 숫자가 꼭 필요한 곳은 **결론의 근거가 되는 값**뿐이다. 예: "팬 0 rpm (기준 1850)".
- 상태: [바꿀 것] 신호 모니터·판정 노트의 숫자를 이 원칙으로 줄인다.

## 2. 사건 1 — 구동: "페달을 밟아도 차가 안 나가"

### 1단계 · 원인 역추적
- **미션:** "차량 가속이 기준보다 낮아요. 왜 달라졌나요?" 같은 질문을 한 칸씩 거꾸로 반복한다.
- **선택지(매 칸 후보 사진 3장)**

  | 지금 칸 | 후보 | 결과 |
  |---|---|---|
  | 차량 가속 (기준 2.8 / 지금 1.2) | 모터 힘 · 계기판 게이지 · 회생 제동 | 모터 힘 = 먼저 달라짐(원인 쪽) / 계기판 = 나중에 달라짐(함정) / 회생 = 정상 |
  | 모터 힘 (204 / 91 Nm) | 배터리 전류 · CAN 토크 명령 · 모터 온도 | CAN 명령 = 원인 쪽 / 배터리 전류 = 함정 / 모터 온도 = 정상 |
  | CAN 토크 명령 (204 / 92) | 인버터 전류 · 게이트웨이 전달 · VCU 페달 처리값 | VCU 처리값 = 원인 쪽 / 인버터 전류 = 함정 / 게이트웨이 = 정상 |
  | VCU 페달 처리값 (60 / 27%) | 페달 센서 · 브레이크 스위치 · 기어 · BMS 허용 · 온도 보호 | 모두 정상 → 여기가 처음 어긋난 곳 |

- **보이는 정보:** 후보 사진(측정 전 "?"), 측정 후 기준/지금 막대, 먼저/나중 시간축, 전체 지도(센서 → 제어기 → CAN → 부품 → 차량).
- **판단 규칙(두 개뿐):**
  1. 원인은 결과보다 먼저 달라진다.
  2. 들어오는 값이 모두 정상인데 나가는 값만 다르면, 원인은 그 안쪽이다.
- **마지막 선택(의심 구간 3지선다):**
  - 정답: VCU 안 페달 처리·토크 계산
  - 오답: 페달 센서·배선 / 인버터·모터
- **넘기는 가설:**
  - 판단 보류: VCU 처리 SW, VCU 입력 회로(HW)
  - 반박됨: 페달 센서(값이 정상), 인버터·모터(명령부터 낮음)
- **얻는 것:** 구동 신호 경로(페달 → VCU → CAN → 인버터·모터 → 차량)를 거꾸로 따라가는 법, 원인과 결과(함정)를 구분하는 법.
- **출처:** 차고 › 구동 › "운전자 토크 요청" › E/E 관점(APS 이중 센서 → VCU → CAN Torque → 인버터·모터). 값은 `DominoTrace.tsx` CASES.propulsion.
- **[바꿀 것]:** 측정 결과로 가설을 지우는 것도 플레이어가 직접 한다(판정 노트, 3단계와 같은 방식).

### 2단계 · 요구사항 기반 로직 퍼즐
- **미션:** "정상이라면 페달 60%가 어떻게 모터 204 Nm가 되나요?" 퍼즐판 빈칸 3개 채우기.
- **선택지(남은 조각 5개)**
  - 정답: 페달 맵 표 A(60% → 204 Nm), 가용 토크 MIN, 램프율
  - 함정: 페달 맵 표 B(60% → 92 Nm). 블록 이름은 같고 표 값이 다르다.
  - 함정: 토크 추정. 인버터 안 블록이라 이 경로에 없다.
- **보이는 정보:** 요구사항 8줄(오른쪽), 블록 "?" 버튼(표 값), 옆 입력 "BMS 한계 260 Nm", 차고 노트(오픈북).
- **결과:** 실행하면 칸마다 값이 흐르고, 요구사항 줄에 ✓ 표시가 붙는다.
- **얻는 것:**
  - 핵심 제어: 상관성 확인 → 필터 → 페달 맵(표) → 구동 허용 → 가용 토크 MIN → 램프 → 출력.
  - **3단계 판정 기준(기대값) 204 Nm.**
- **출처:** 차고 › 구동 › "운전자 토크 요청" › Control SW(입력 상관성 → 페달 맵 → 가용 토크 MIN → 출력 제한). 값은 `RefPuzzle.tsx` REF.propulsion.
- **[바꿀 것]:** 완성하면 "이 로직이 검증의 기대값이 됩니다" 카드(60% → 204 Nm)를 보여 주고, 3단계 모니터 점선을 이 카드로 표시한다.

### 3단계 · 시뮬레이션 검증
- **미션 흐름(스토리형 이름)**
  1. **SW 무죄 확인**(정상 시나리오): "요구사항 입력을 넣으면 SW가 요구사항대로 동작하나요?"
  2. **현장 재현**(고장 재현): "사건 조건을 넣으면 같은 증상이 나오나요?"
  3. **판정 노트:** 결과가 각 가설을 지지 / 반박 / 판단 불가 중 무엇으로 만드는지 플레이어가 고른다.
  4. **범인 지목:** 처음 갈라진 신호에 깃발.
  5. **볼트에게 설명(보고서)** → 수리 요청 → 같은 시험으로 재확인 → 회귀.
- **선택지**
  - 레벨 4개: SW 단위 / SW 통합 / 통합 SW·제어기 I/O / 시스템 통합
  - 입력 3개: 페달 60%(요구사항 값) / 페달 100%(경계값) / 추월 구간 주행 기록
  - 관측점: 레벨마다 4개 신호 중 3개
- **보이는 정보:** 왼쪽 탭(SW 로직 · 제어기·I/O · 부품·차량, 실물/모델 표시), 오른쪽 신호 모니터(점선 = 정상 설계, 실선 = 시험 대상), 판정 도장(PASS / FAIL / 판단 불가).
- **정답 경로(가장 싼 길)**
  1. SW 단위 · 페달 60% · 관측 [페달 · 처리값 · 토크 요청] → **FAIL**
     - 처리값 27% (기준 60), 토크 92 Nm (기준 204)
  2. 판정:
     - VCU 처리 SW **지지**: SW만 실행해도 차이가 난다.
     - VCU 입력 회로 **반박**: 입력 회로가 없는 시험에서도 차이가 난다.
  3. 현장 재현(주행 기록) → 처리값에 깃발 → 원인 확정
  4. 수리 요청: "보정 계수 ×0.45 블록 제거" → 재시험 PASS → 회귀
- **볼트에게 하는 설명(보고서)**
  - 페달 센서는 정상이에요. 근거: 1단계 페달 값 60%.
  - 인버터·모터는 정상이에요. 근거: VCU가 보낸 명령부터 이미 낮았어요.
  - 원인은 VCU SW예요. 설계에 없는 보정 계수가 페달 값을 0.45배로 줄였어요. 근거: SW 단위 시험에서 처리값 27%.
- **얻는 것:** 레벨 선택(가장 싸게 원인을 가르는 시험), 입력 회로(HW)와 SW를 시험으로 분리하는 법, 근거를 붙여 설명하는 법.
- **출처:**
  - 수치: `simModel.ts` propulsion(60% × 0.45 = 27%, 3.4 Nm/% → 204/92 Nm)
  - 판정 규칙: `scenarios.ts` SCENARIO_META.propulsion
  - 레이스: `vehicleSim.ts` pedalScale 0.45

## 3. 사건 2 — 열관리: "오래 달리니 힘이 빠지고 경고등이 켜져"

### 1단계 · 원인 역추적
- **선택지 흐름**

  | 지금 칸 | 원인 쪽 | 함정(나중) | 정상 |
  |---|---|---|---|
  | 차량 가속 (2.8 / 1.9) | 출력 허용 | 파워다운 표시등 | 회생 제동 |
  | 출력 허용 (100 / 62%) | 모터 온도 | 배터리 출력 | BMS 제한 요청 |
  | 모터 온도 (70 / 96°C) | 냉각수 온도 | 인버터 온도 | 펌프 유량 |
  | 냉각수 온도 (65 / 78°C) | 냉각 팬 회전 | 배터리 온도 | 냉각수 양 |
  | 냉각 팬 회전 (1850 / 0 rpm) | 없음(팬 명령 100% 정상) | | 바깥 기온, 펌프 |

- **의심 구간:** 정답은 "팬 명령 이후 구동 경로(ECU 출력단·배선·전원·팬 모터)". 오답은 팬 제어 SW, 출력 제한 로직.
- **넘기는 가설:**
  - 판단 보류: ECU 출력단·배선·전원, 냉각 팬 모터
  - 반박됨: 팬 제어 SW(명령 100% 정상)
- **얻는 것:** 열관리 사슬(팬 → 냉각수 → 모터 온도 → 출력 제한 → 가속). 경고등·출력 제한은 결과이지 원인이 아니라는 것.
- **출처:** 차고 › 열관리 › "온도 상태 추정", "펌프·팬 제어", "열 한계 출력 제한". 값은 `DominoTrace.tsx` CASES.thermal.

### 2단계 · 로직 퍼즐
- **미션:** "정상이라면 냉각수가 78°C일 때 팬이 어떻게 1850 rpm으로 도나요?" 빈칸 3개.
- **선택지:**
  - 정답: 범위 검사, 히스테리시스 표 A(65°C 켜짐 / 60°C 꺼짐), 팬 구동 출력단·전원
  - 함정: 히스테리시스 표 B(95 / 90°C)
  - 함정: 단계 임계(출력 제한 경로라 이 경로에 없다)
- **얻는 것:**
  - 핵심 제어: 히스테리시스(켜고 끄는 기준이 다름) + PI(실제 회전을 보며 PWM 조절, 되돌아오는 피드백)
  - 기대값: 팬 1850 rpm
- **출처:** 차고 › 열관리 › "펌프·팬 제어" Control SW. 값은 `RefPuzzle.tsx` REF.thermal.

### 3단계 · 검증
- **정답 경로**
  1. SW 단위 · 열 부하 높임 → 낮춤 · 관측 [냉각수 온도 · PWM 비율] → **PASS**
     - 판정: 출력단·배선 = 판단 불가, 팬 모터 = 판단 불가. 이 레벨에서는 팬이 모델이라 고장이 안 보인다.
  2. 시스템 통합 · 장거리 고속 열 부하 · 관측 [커넥터 PWM · 커넥터 전압 · 팬 회전] → **FAIL**
     - PWM 100% (기준 65), 12 V (기준 12), 0 rpm (기준 1779)
  3. 판정:
     - 출력단·배선·전원 **반박**: 명령과 전원이 커넥터까지 도착한다.
     - 팬 모터 **지지**: 도착했는데 돌지 않는다.
  4. 팬 회전에 깃발 → 보고서 → 수리 요청 "냉각 팬 교체" → 재시험 → 회귀
- **볼트에게 하는 설명:**
  - SW는 정상이에요. 근거: 팬 명령 100%, SW 단위 시험 PASS.
  - 배선·전원도 정상이에요. 근거: 커넥터에 PWM·12 V 도착.
  - 원인은 팬 모터 고착이에요. 근거: 회전 0 rpm.
- **얻는 것:**
  - SW 레벨 PASS가 "부품도 정상"이라는 뜻은 아니다(모델로 대체됨).
  - 실부품 시험에서 "명령 도착 vs 실제 반응"으로 HW를 가른다.
  - PWM이 기준보다 높은 건 결과다. 팬이 안 돌아서 제어기가 명령을 끝까지 올린 것이다.
- **출처:** `simModel.ts` thermal(fault: rpm = 0), `scenarios.ts` SCENARIO_META.thermal, `vehicleSim.ts` fanStuck.
