# TraceBack — Claude 전달용 마스터 프롬프트 (설계 검토 전용)

## 0. 최상위 지시: 지금은 구현하지 말 것

너는 현재 개발 중인 TraceBack(PC 웹 16:9, React + Three.js/R3F 기반 EV 레이싱·고장 추리·검증 교육 게임)의 **기존 구현을 존중하는 게임 디렉터 + UX 설계자 + 자동차 E/E·Control SW 검증 전문가 + 프론트엔드 기술 리뷰어**다.

**이번 요청의 산출물은 코드가 아니다.** 먼저 프로젝트 파일, 현재 화면, 기존 컴포넌트, 라우팅, 게임 상태, 시나리오 데이터, 에셋, 이전 디자인을 직접 조사한 다음, 사용자가 검토할 **구조화된 설계 명세서**를 만들어라. 사용자가 명시적으로 승인하기 전까지 코드 수정, 파일 삭제, 패키지 추가, UI 재배치, 에셋 교체, 리팩터링, 커밋을 하지 마라. 읽기 전용 조사만 허용한다. 접근할 수 없는 자료는 접근했다고 주장하지 말고 필요한 파일·스크린샷을 요청하라.

마감이 2026-11-12로 임박했으므로 **최소 변경, 기존 에셋/기능 재사용, 실제로 동작하는 핵심 연결성**이 최우선이다. 교육 목적을 핑계로 정보전달형 웹, 기술 대시보드, 단순 객관식 퀴즈로 만들지 말 것. 3D·그래픽·물성·상호작용을 통해 배우는 **추리 게임**이어야 한다. 스타일은 기존의 밝고 귀여운 파스텔, 동물의 숲·치이카와 계열 감각을 참고하되 직접 복제하지 않는다. 금지: AI 티 나는 UI, 음악 앱형, 과도한 텍스트, 빈티지·어두운 분위기, 과도한 콜라주·기울기, 기존 캐릭터의 불필요한 움직임. 실제 PC 웹 16:9의 공간과 3D 씬을 우선 존중한다.

### 지시 우선순위 및 충돌 처리
1. **사용자 최신 재질문/확정사항**이 이전 ChatGPT 제안보다 우선한다. 실제 내부 신호명 대신 이해하기 쉬운 한글 표현, REAR MIRROR 상단 정중앙 고정, 현재 단일 검증 화면 유지 검토, 판정 용어 `통과/실패/판정 불가`.
2. 아래 **'원문 요청 1~5'의 모든 항목은 삭제·축약·누락 금지**. 제안 단계에서 모두 다루되, 승인되지 않은 항목은 임의 구현 금지.
3. 첨부파일1(이전 ChatGPT의 장문 피드백)과 후속 답변은 **검토 자료/설계 후보**이지, 확정 구현 명령이 아니다. 원문과 상충하는 제안은 반드시 표시하고 최신 사용자 의도를 우선한다.
4. 기술적으로 부정확하거나 상충하는 지시는 조용히 고치지 말고 `원문 의도 / 기술적 쟁점 / 권장 대안 / 사용자 결정 필요`로 나눠 설명한다.
5. 실차 아키텍처·신호 배분·수치·고장 빈도를 근거 없이 단정하지 말고 `게임용 단순화 모델`과 `실차 공통 원리`를 구분한다.

### 반드시 먼저 제출할 산출물
A. **기존 구현 조사표**: 화면별 현재 경로·컴포넌트·상태·에셋·기능·문제·재사용 가능 여부·증거(파일 경로/코드 위치). 확인 불가 사항 별도 표기.
B. **전체 게임 흐름 및 교육 범위 명세**: 도메인→기능→세 관점(3D/System·E/E·Control SW), 정상 학습→첫 사건 튜토리얼→레이싱→증거/도미노/메모판→검증 준비→시뮬레이션→재주행. 각 단계의 목표·행동·입력·출력·성공 조건·실패/재시도·다음 단계 조건.
C. **화면별 상세 명세서**: 반드시 아래의 `1)~5)` 원문 번호 및 `ㄴ` 하위 구조를 유지. 각 화면에 `현행 유지 / 문구 교체 / 기능 수정 / 레이아웃 최소 수정 / 신규 제안 / 미결정` 구분. 정확한 텍스트·버튼·팝업·좌표/영역·우선순위·조작·피드백·모션·효과음·접근성·반응형 제약까지 기재.
D. **화면별 시각 와이어프레임**: 텍스트 목록만 금지. 현재 스크린샷 위 변경 주석(가능한 경우), 16:9 영역별 도식, 3D와 오버레이의 관계, 전후 비교. 시각 자료 제작이 불가능하면 영역 비율/앵커/레이어 순서와 ASCII 와이어프레임을 제공하고 이미지가 없음을 명시. **기존 화면과 달라지는 지점을 반드시 표시**.
E. **상태·시뮬레이션·콘텐츠 스키마**: 하나의 입력/상태를 3D, E/E, Control SW, 주행, 추리, 검증이 공유하는 구조. 기능ID·도메인ID·노드ID·한글 표시명·입출력·정상 조건·관측 가능 신호·시나리오별 증거/가설/실험/판정 연결. 기술 검증과 시각 표현 분리.
F. **첫 사건 플레이스루**: 실제 버튼·행동·피드백·공개되는 정보·숨기는 정보·정답 유출 방지·오픈북 사용·실패/힌트·다음 화면 진입까지 장면별 시나리오. 고장 원인을 미리 암시하지 않는 조작 튜토리얼.
G. **사건 유형별 퍼즐/검증 적용표**: 센서·SW 로직·통신/인터페이스·액추에이터·시스템·전원/보호·기계/유체 등에서 어떤 퍼즐을 유지/변형/생략하는지, 해당 유형의 요구사항·시험 입력·관측값·기대 동작·가설 구분 능력.
H. **변경 영향도/우선순위/리스크**: P0/P1/P2, 예상 작업량, 기존 파일 영향, 성능·3D 렌더링 위험, 11월 12일까지 가능한 범위, 이후 확장. '현재 구현 확인 전 추정'을 명시.
I. **요구사항 추적 매트릭스**: 아래 모든 원문 세부 요청과 질문을 한 행씩 빠짐없이 기록하여 `원문 ID / 사용자 요구 / 설계 답변 위치 / 변경 유형 / 검증 방법 / 결정 상태` 표시. 누락이 0인지 자가 검증.
J. **승인 요청 질문**: 정말 결정이 필요한 3~7개만, 권장안과 대안의 장단점 제시. 답변 전 구현 금지.

**그래픽 우선 원칙**: 기능 설명은 긴 문단보다 3D 조작, 부품 반응, 신호 하이라이트, 움직이는 화살표, 입력→판단→출력 값 변화, 실물-논리 레이어 전환, 폴라로이드, 게이지, 연결 실, 블록 조립, 겹친 그래프 등으로 보여줄 것. 그래픽은 장식이 아니라 입력·인과관계·판단을 이해시키는 수단이다. 글은 짧은 한글 문장, 필요할 때만 오픈북/도움말로 상세 제공. 오버쿡드의 조건·순서, Human Resource Machine의 블록 조립·실행, while True: learn()의 데이터 흐름, 리듬게임/청기백기의 반응·타이밍, 고군분투의 즉각적 피드백·빠른 재시도, Papers Please의 모순 찾기, Keep Talking and Nobody Explodes의 오픈북 활용을 **기법으로만** 검토하고 실제 UI를 복제하지 말 것. 시간 제한은 주로 레이싱에 적용하고 깊은 추리·검증에는 강제하지 않는다.

## 1. 사용자 원문 요청 — 화면별 구조를 반드시 유지하여 검토·설계할 것

### 공통 학습·추리 흐름
차량 도메인 동작 원리는 **미니게임으로 정상 흐름을 직접 작동시키며 학습**한다. **첫 고장 사건에서는 게임 흐름과 조작법을 안내하는 튜토리얼을 반드시 제공**하되 원인/정답은 공개하지 않는다. 이후 원인 추리부터 검증까지 **오픈북**을 제공한다. 정상 기능·부품·E/E 연결·Control SW 판단·요구사항·용어는 공개할 수 있지만 사건의 실제 원인, 아직 확보하지 않은 사건 기록, 정답 실험은 공개하지 않는다. 모든 기능을 한꺼번에 암기시키지 말고 범위를 제한한다.

### 1) 차량 도메인 동작 원리 화면

#### ㄴ 팝업 — 기존 문구와 수정
기존 팝업:
> 처음 해 보는 단계 / 차량 도메인 동작 원리 / 차가 운전자 입력을 어떻게 차량 동작으로 바꾸는지 미리 살펴보는 곳이에요. 뒤의 고장 추리에 그대로 쓰여요. / 1 위 탭에서 도메인 하나를 고르세요. (예: 구동) / 2 오른쪽에서 그 도메인의 주요 기능 하나를 고르세요. (예: 운전자 토크 요청) / 3 왼쪽에서 보는 관점을 바꿔요: 차량 기능 → E/E(부품·배선) → Control SW(제어기 안 계산). 아래 흐름 칸에서 단계를 넘겨 보세요. / 시작하기 (Enter)

**수정 확정**: `차가 운전자 입력을 어떻게 차량 동작으로 바꾸는지 미리 살펴보는 곳이에요. 뒤의 고장 추리에 그대로 쓰여요.` → `차량 동작 원리를 파악하고 작동시켜보아요.` 나머지 단계 설명도 수동 조작형 미니게임과 맞도록 최소 수정안을 제시하고 기존 팝업 구조를 유지할 것.

#### 1-1. 정상 동작 미니게임과 공통 상태
현재는 신호가 무한정 흐르는 수동 시각화이다. **입력을 실제로 인가할 때만 동작·흐름·애니메이션이 활성화**되도록 바꾸는 방안을 설계. 기존 화면의 `[학습모드]`와 기존 3D/논리도/흐름도를 활용하며 별도의 복잡한 입력 폼이나 거대한 신규 UI를 만들지 않는다. 3D HMI를 직접 조작(페달 꾹 누르기, 핸들 클릭·드래그 회전, 시동 스위치 클릭, 기어 선택 등), E/E 논리 노드 또는 입력 소프트웨어 조작으로 값을 인가할 수 있게 한다. 최종 액추에이터까지 연결되어 실제 출력 반응이 보여야 한다. 각 기능은 활성화 조건을 플레이어가 조합해 성공시키며, 오버쿡드식 짧은 조건·순서 미션을 검토한다. 단, 실제 안전 조건/인터록은 기술적으로 검토하고 단순화를 표시한다.

세 단계는 **동일 시뮬레이션 상태와 시각화 자산을 재사용**한다: 학습=정상 작동을 직접 만들기, 추리=사건에서 실제 이상 관찰, 검증=조건을 바꿔 가설 시험. 입력값 변경→센서 측정→제어 판단→전달→액추에이터 반응의 단방향 이벤트/상태 동기화 설계를 제시. 서로 다른 뷰가 독립 계산해서 모순되는 것을 금지.

#### 1-2. 세 시각화의 분명한 역할
- **3D 차량 모델 = 어디에서 동작하는가?** 차량 내 부품 위치·기능·애니메이션; 부품 클릭 시 관련 기능/로직 하이라이트 가능성 검토. 기존 구현 최대 재사용.
- **E/E 아키텍처 = 무엇과 연결되는가?** 센서·제어기·통신·액추에이터 연결, 실제 조작에 따른 신호 전달. 논리 뷰/동일 위치의 3D 부품 뷰/혼합 뷰를 불투명도 레이어처럼 전환. **논리적 배치가 실제 차량 내 물리적 위치를 뜻하지 않음**을 분명히 함.
- **Control SW = 왜 그렇게 동작하는가?** 기능 필요성, 입력을 받아 조건·계산·제한·상태 전이를 거쳐 출력하는 과정, 어느 요소에서 받아 어디로 전달하는지. 단순 `입력/출력` 라벨이나 직선 한 줄짜리 흐름도 금지. 값이 블록마다 변하는 실행 경로·조건 분기·지연·주기·피드백을 필요에 맞게 시각화. Simulink형 의미 있는 블록·서브시스템 표현을 검토하되 실재하지 않는 로직을 지어내지 말 것. **실제 프로젝트 신호명·내부 변수명은 사용하지 않고 `가속페달을 밟은 정도`, `운전자가 원하는 구동력`, `최종적으로 허용된 구동력` 등 이해하기 쉬운 한글 기능명으로 표시**. 단위·범위는 필요할 때만, 수치는 검증된 모델에서만.

**질문 필수 답변**: 오른쪽 `도메인의 주요 기능` 목록은 E/E 기준인가, Control SW 기준인가? 권장: 기능은 도메인 아래 공통 기능 ID로 정의하고 세 뷰가 각기 표현하는 구조인지 기술적 타당성 검토. `위치 → 연결 → 판단`이라는 세 관점이 같은 기능의 서로 다른 깊이임을 드러내는 화면 명세 제시.

#### 1-3. 계층/레이아웃 개념 검토
`System > E/E Architecture / Domain(구동/제동/조향/전원/변속 및 주차/열관리/현가) > Control SW`의 단순 서열이 타당한지 검토. E/E는 연결 구조, 도메인은 기능 분류, Control SW는 구현 관점이므로 반드시 단일 트리로 강제하지 말고 대안 정보구조를 제시. 상위 차량/시스템→도메인→기능 선택, 그 아래 3D·E/E·Control SW 관점 전환을 우선 검토. 도메인별 주요 기능의 범위와 학습 우선순위를 제시하되 모든 도메인을 정밀 구현한다고 약속하지 말 것.

#### 1-4. E/E 레이어·정보 팝업 구체화
현재 E/E `흐름 따라가기`와 `부품 소개`가 본문을 많이 차지함. E/E의 논리 블록 클릭 시 **`수신값 / 수행 역할 / 발신값`**을 해당 노드의 팝업/인스펙터로 표시. 3D 부품 레이어를 클릭했을 때만 **Vehicle/System 화면의 기존 360도 회전+부품 설명 컴포넌트**를 재사용해 부품 설명. 기존 E/E 부품 소개는 내용 품질이 낮으므로 교체하되 기존 좋은 컴포넌트는 보존. 공간을 회수해 본문 시각화 영역을 넓힌다. 레이어 불투명도 전환·연결선 가독성·포커스·부품 이름 라벨의 색상/텍스트 넘침·기능 전환 시 시뮬레이션 깜빡임/로딩 플래시 제거도 반드시 설계.

### 3) 원인 역추적 화면

#### 3-1. 명칭·기술성
`ROOT CAUSE TRACE / 원인 역추적`의 적절성 검토. **`도미노`를 반드시 포함**하는 한국어 명칭 후보(예: `도미노 역추적`) 제시. 기술적으로 `고장 영향 전파 경로의 역방향 추론`과 연관되며 FMEA·FTA·RCA·영향도 분석과 동일하다고 오인시키지 않도록 차이 설명.

#### 3-2. 폴라로이드 메모판의 복원과 물성
이미 제작한 **폴라로이드 증거 이미지/프레임 에셋을 반드시 찾아 재사용**. 폴라로이드 클릭 시 증거 설명·원본 기록·관련 시각화 접근. 메모판은 단순 목록이 아니라 실제 종이를 드래그해 붙이고 압정을 꽂고 실로 연결하는 **촉각적 추리 공간**: 종이 살짝 흔들림, 압정 클릭음, 실의 장력, 가설 카드 연결, 게이지/기록과 증거의 결합. 물성·애니메이션·효과음은 가볍게 구현하고 3D 성능에 악영향을 주지 말 것. **연결 직후 정답/오답을 색으로 노출하지 말 것**. 기존 메모판 에셋·컴포넌트 확인 후 복원 범위 명시.

#### 3-3. 도미노와 메모판의 역할 분리
도미노=신호/기능/통신/서브시스템의 **인과 경로 조사**, 메모판=증거를 붙이고 **가설을 구성·비교**하는 공간. 택1로 버리지 말고 **양립 가능성·전환 동선·중복 제거**를 검토. 예: 주행 기록/계기판/HMI/출력/경고등/시계열/현장 사진에서 증거 확보→도미노에서 추가 관찰 지점 선택→메모판에 증거/원인 후보 연결→검증 준비로 전달.

#### 3-4. 자동 정답 지목 방식 폐기
현재 E/E 요소 블록 클릭만으로 증상이 등록되고, 화살표를 따라가면 원인을 알 수 있는 문제를 고친다. **클릭=증상 확정** 금지. 관찰 가능한 정보와 추가 측정 가능한 정보를 구분. 플레이어가 입력을 인가하고, **어디서 정상 기준과 달라지는지 / 어떤 관찰을 더 하면 후보를 구분할 수 있는지** 선택하게 한다. 단순 `첫 빨간 블록 찾기` 금지. 선택한 관찰에 따라 기록/게이지/파형/폴라로이드 증거를 공개하고, 신호의 수신·처리·발신 관계를 조사한다. Simulink 서브시스템처럼 기능 단위로 확대해 센서/통신/제어/출력의 이상 가능성을 탐색할 수 있게 설계하되, 추리 단계에서 결함을 무조건 확정하지 말 것. 관측 범위와 추가 시험의 필요성을 명확히 표현.

#### 3-5. 다각도 증거와 사건 범위
증거는 사진만이 아니라 **운전자 체감, HMI 입력 기록, 계기판/경고등, 제어기 입력·출력, 통신 송수신, 액추에이터 명령·피드백, 시간 변화, 환경/도로 조건** 등 서로 다른 관점에서 제공. 이미지·게이지·그래프·폴라로이드·3D 반응을 섞어 표시. 원인 범위 후보를 전부 조사·분류: 센서/입력, SW 로직/상태 전이/타이밍, 통신·인터페이스, 액추에이터, 전원/보호, 기계·유체, 복합 고장. 이번 마감의 권장 범위와 제외 이유, 실제 발생 빈도 주장에 필요한 근거를 분리 제시. **SW 외 원인도 포함**해 정답이 늘 SW인 패턴을 피할 것.

#### 3-6. 플레이어 친절도와 튜토리얼
`무엇을 클릭해야 하는지`, `무엇을 증거로 얻는지`, `다음에 어떤 판단을 해야 하는지`를 단계별 짧은 행동 안내와 시각 하이라이트로 알려주되 정답 공개 금지. **첫 사건 튜토리얼이 현재 없는 문제를 필수 수정 대상으로 지정**. 처음에는 조작·메모판·도미노·검증 준비·시험 비교를 순서대로 안내하고 이후 사건에서는 간소화. 힌트는 `다음에 확인할 정보의 종류`까지만 제공하고 범인/원인 노드/정답 실험을 바로 공개하지 말 것.

**중요**: 화면 자체를 `검증 준비 작업대`로 바꾸는 안은 **제안일 뿐 미승인**. 화면명·팝업명 변경 전 기존 UI를 유지하는 안과 이름/역할만 바꾸는 안을 비교하고 승인을 요청. 기존 퍼즐을 무조건 제거하지 말 것.

#### 4-1. 존재 이유와 추리 적합성 검토
차량 고장 원인이 SW 로직이 아닐 수도 있는데 매번 SW 블록을 조립하게 하는 게 적절한지, 추리게임·차량 도메인 학습·검증 사고에 기여하는지 **유지/조건부/삭제** 세 안을 비교. **레이아웃 변경 최소화**를 우선. 블록 배치 자체는 논리 퍼즐이고, 어떤 실험으로 가설을 구별할지 고르는 것은 진단적 추론이라는 차이를 명시.

#### 4-2. 권장 후보: `실험 장치 조립`이라는 게임적 의미
플레이어 목표를 `테스트 케이스 문서 작성`이 아니라 **`의심한 두 원인을 구별할 실험 장치를 완성하자`**로 표현. 기존 Simulink형 블록 퍼즐 UI를 재사용해 카드/블록 조합·연결·실행·실패 피드백 제공. 사건별로 동일한 조작 문법을 쓰되 퍼즐 재료·규칙이 달라짐:
- SW 로직: 요구사항에 맞춰 조건·비교·지연·상태 전이 블록을 연결하고 예상 반응 확인.
- 센서: 운전자 실제 조작, 센서 측정값, ECU 수신값의 관찰 지점을 연결.
- 통신: 송신·수신·갱신 주기·지연/누락 관찰 경로를 구성.
- 액추에이터: 명령·실제 움직임·피드백 관찰 지점을 연결.
- 시스템: 사전 상태·운전자 입력·보호 조건·차량 출력의 조합을 준비.
- 전원/열관리 등: 해당 수준의 **정상 요구사항**에 근거해 시험을 구성.

모든 유형에 로직 조립을 강제하지 않는다. 사건에 따라 이미 준비된 실험 장치를 선택하거나 일부만 연결하는 대안을 허용. 퍼즐의 **성공은 실험 준비 성공**이지 고장 원인 확정이 아니다. 뒤의 시뮬레이션 검증으로 연결될 데이터(가설, 시험 입력, 관찰값, 요구사항에서 유도한 정상 기대 동작)를 내부적으로 보관. 플레이어에게 TC 용어·양식·문서 작성 강요 금지.

#### 4-3. 일반 운전자도 이해할 이유 설명과 연출
`구동 페달 → 토크 요청` 같은 기술 흐름에 **왜 이 단계가 필요한지 한글 한 문장**을 표시: 예를 들어 `페달을 얼마나 밟았는지에 맞춰 차가 낼 힘을 정하기 위해서예요.` 기술적 정확성 확인. 각 블록에 `무엇을 받는지 / 무엇을 하는지 / 다음으로 무엇을 보내는지`를 그래픽·값 변화로 제시. 올바르게 연결하면 **최종 3D 액추에이터가 실제로 작동**하는 피드백. 잘못 구성하면 기술적으로 가능한 이상 반응(출력 제한, 펌프 미작동, 경고, 조건 미충족)을 표현. **로직 오류만으로 무조건 폭발·화재가 난다고 과장하지 말 것**. 화재 등은 물리적 조건과 안전성 검토가 충족될 때만 허용. 퍼즐 자체의 잘못된 시험 설정과 사건 모델의 실제 로직 결함은 구분.

#### 4-4. 기술적 핵심 질문
요구사항 기반 퍼즐의 최종 목적은 무엇인가? 정상 동작 기준·시험 입력·관측값을 어떻게 준비하는가? 요구사항은 SW뿐 아니라 센서/통신/액추에이터/시스템 수준에서 어떻게 정의하는가? 정상 기대값을 플레이어가 임의로 만들지 않고 **사전에 정의된 요구사항에서 도출**하도록 하는가? 퍼즐을 마쳤을 때 다음 단계의 시험 대상·가설·조건·관찰 지점이 실제로 준비되는가? 기존 코드가 이를 지원하는지 확인. SW 이외 원인에 대응하는 대체 퍼즐의 정확한 화면/조작 설계 제시.

### 5) 시뮬레이션 검증 화면

#### ㄴ 팝업 — 문구 수정
기존:

**기술 검토**: 반례=고장이 아님. 정상 기준 모델 vs 사건 모델 비교를 기본으로 하고, 정상 요구사항의 경계/예외 조건을 별도로 다루는 명칭/문구 대안을 제시. 사용자 문구를 임의 변경·확정하지 말고 권장안과 이유를 제시해 승인받을 것.

#### 5-1. 무엇을 검증하는가
메모판에서 세운 **가설**을 검증 준비에서 만든 **시험 조건/관찰 지점/정상 기대 동작**으로 시험한다. `어떤 시험으로 확인할까요?`를 단순 시험 카드 퀴즈로 만들지 말고 플레이어가 입력값·조건을 조작하고 신호·3D 반응을 관찰하게 설계. 정상/사건 모델은 같은 초기 상태·입력·실행 시간으로 비교. 숨겨진 사건 원인을 선택하는 메뉴를 플레이어에게 노출하지 말 것. 정상/사건의 차이가 특정 조건에서만 나타나면 그 조건을 플레이어가 찾아내는 재미를 제공.

#### 5-2. 기존 단일 화면 유지 vs 쌍둥이 화면
현재 UI는 **쌍둥이 실험대가 아니라 단일 시뮬레이션 화면**으로 변경된 상태. 두 개의 3D 화면을 억지로 나누지 말 것. 세 대안을 비교하되 **권장 기본안은 기존 한 화면 유지 + 정상/사건 결과의 신호 그래프 겹쳐 보기 + 필요 시 3D 정상/사건 토글**. 동일 조건에서 순차 실행해 저장 결과를 겹쳐 비교해도 된다. 좌우 동시 3D 렌더링은 성능·레이아웃 비용이 크므로 승인 전 금지. 기존 화면 배치와 각 영역에 들어갈 값·그래프·3D·조작 요소를 정확히 설계.

#### 5-3. 판정의 기술적 구분
모든 수준의 시험에서 실패할 수 있고 일부 원인을 찾을 수 있다. **시험 수준 자체가 원인 특정 가능 여부를 결정하는 것이 아니라 시험 범위·입력 조건·계측 신호·관찰 가능성이 결론의 깊이를 결정**한다. SW 단위 시험에서 특정 로직 오류를 관찰할 수 있어도 물리 액추에이터의 고장을 직접 확인할 수 없을 수 있고, 시스템 시험에서 동작 실패가 확인되어도 내부 계측이 부족하면 원인을 특정하지 못할 수 있다. `어떤 단계는 Fail이어도 원인을 찾을 수 없다` 식의 고정 규칙 금지.

**두 가지 판단을 분리**:
1. **시험 결과(요구사항 대비)** = `통과 / 실패 / 판정 불가`.
2. **가설에 대한 해석** = `지지 / 배제 / 판단 보류` 또는 사용자에게 이해 쉬운 `가능성 높음 / 가능성 낮음 / 아직 모름` (어느 세트가 적절한지 제안).

시험 결과가 통과/실패로 판정되어도 그 시험만으로 특정 가설을 구별할 수 없다면 **가설 판단 보류**가 가능하다. `판정 불가`는 관측 부족, 시험 무효, 기준 미정 등으로 시험 자체를 판정할 수 없을 때만. **INCONCLUSIVE, PASS, FAIL 등 영어 라벨은 UI에서 사용하지 말 것**.

#### 5-4. 도움말과 게임성
검증 도움말 버튼에 다음 취지를 **일반인도 이해하는 짧은 카드**로 넣어라:
> 모든 단계에서 실패가 발생할 수 있고, 그 단계에서도 원인을 일부 찾아낼 수 있어요. 다만 무엇을 관찰할 수 있는지와 시험 범위에 따라 결론의 구체성이 달라져요. 제어 로직 시험은 내부 판단 오류를 확인하는 데 유용하지만 실제 부품 고장을 직접 보여주지는 못할 수 있어요. 시스템 시험은 차량 동작 이상을 보여주지만 내부 측정이 부족하면 원인을 특정하기 어려워요. 같은 시험 수준이라도 어떤 신호를 측정하는지가 중요해요.

긴 본문을 화면에 상시 노출하지 말고 `?` 도움말과 상황별 팁으로 제공. 결과는 숫자 표만이 아니라 3D 출력 반응·신호 그래프·게이지·정상/사건 겹침·조건 변화의 즉각적 시각 피드백으로 보여줄 것. 시험 실행→관찰→가설 지지/배제/보류→추가 시험 또는 재주행 흐름을 구체화.

## 2. 화면 간 연결·콘텐츠·교육 범위 추가 요구

### 2-1. 도메인과 기능 범위
구동/가속·열관리를 필수 중심으로 하고 제동은 선택 우선순위로 검토하되, 조향/전원·배터리/변속·주차/현가 및 통신/ECU 등은 **기존 구현과 학습 가치**를 조사하여 `이번 마감에 플레이 가능 / 시각화·오픈북만 / 후속 확장`으로 구분. **모든 차량 동작 원리를 다 가르치려 하지 말 것**. 학습 목표는 `운전자 입력→센서→제어기 판단→통신→액추에이터→차량 반응`의 공통 구조, 도메인별 주요 기능, 고장 추리와 시험으로 이어지는 사고방식이다. 첫 정상 미니게임은 사건의 원인을 예고하지 않도록 다양한 정상 기능 중 기본 조작을 가르치고, 이후 오픈북으로 세부 내용을 찾아보게 한다.

### 2-2. 주행 미션·고장 시나리오 전수 조사
**현재 구현된 모든 주행 미션과 고장 시나리오를 빠짐없이 조사**하고, 주행 중 가능한 조작(시동, READY, 기어, 가속, 제동, 조향, 보호 상태 해제/복귀 등)의 기술적 타당성·현재 지원 여부·추가 가능성을 제시. 사건별 `도메인/기능/실제 원인 범주/발생 조건/증상/경고등/HMI/로그/폴라로이드 증거/오인 가능 가설/추가 관찰/검증 준비 퍼즐/정상 기준/사건 결과/가설 판정/복구·재주행` 연결표를 작성. **고장 시나리오 다양화·구체화·검토**, 센서/SW/통신/액추에이터/시스템 균형, 사건마다 다른 단서·검증 조작, 랜덤 사건 선택 시 튜토리얼·정답·데이터 일관성 보장. 실무 발생 빈도에 관한 객관적 근거가 없으면 빈번하다고 주장하지 말고 `교육적 우선순위`로 분리.

### 2-3. 단계별 게임성
- 정상 학습: 오버쿡드식 `조건을 맞춰 기능 활성화`, 입력을 직접 클릭/누르기/드래그, 성공 시 3D 반응·효과음.
- E/E: 실물-논리 레이어 전환, 신호 전달 경로 조작, 필요한 노드 선택.
- Control SW: Human Resource Machine식 실행/일시정지/한 단계씩 보기, 값 변화·분기·주기, 필요 시 순서 재배치·타이밍 퍼즐.
- 레이싱: 기존 조작감·속도감·커브·장애물·추격, 상태 관련 미션. 고장 발생 후 실패/재도전 흐름.
- 메모판: 폴라로이드 드래그·압정·실·종이 흔들림·사운드, 가설 조합.
- 도미노: 어떤 관찰을 추가할지 선택, 원인 후보 좁히기, 무조건 자동 정답 표시 금지.
- 검증 준비: 기존 블록을 사용해 실험 장치 연결/완성, 시각적인 실행 피드백, 사건별 블록 내용 변화.
- 시뮬레이션: 입력 조건 직접 변경, 같은 조건의 정상/사건 비교, 그래프·3D·게이지의 반응과 차이 발견.

**각 단계에 별도의 신규 미니게임을 무리하게 추가하지 말고 기존 시각화 자산을 조작 가능하게 만들어 게임화**하는 것이 기본 원칙. 추리 단계에 무조건 제한 시간/반사신경을 강제하지 말 것.

### 2-4. 공통 기술·UX 체크
- 기능 전환 시 3D/시뮬레이션 화면 깜빡임과 로딩 플래시 제거(원인 조사 후 최소 수정 제안).
- 부품 이름 오버레이의 색·대비·긴 텍스트 넘침 수정.
- 조작에 따른 신호/3D 출력이 일관되게 반응하도록 단일 상태 소스·이벤트 전파 설계.
- 3D 고품질 에셋 재사용, 기존 로직/아키텍처/폴라로이드/360도 부품 뷰 재사용. 새 에셋을 임의 생성·교체하지 말 것.
- 첫 사건 튜토리얼, 단계별 `무엇을 해야 하는지`를 짧은 그래픽 하이라이트로 제공. 정답 미리 공개 금지.
- 오픈북은 학습 화면의 정상 자료를 재사용, 현재 도메인/부품/기능에 맞는 내용으로 바로 이동. 실제 사건 증거는 별도 권한/진행 상태로 관리.
- UI 전체 한국어 중심. 실제 사내 신호명/차종 특정 비공개 설계명은 쓰지 않는다. 약어(E/E, Control SW, HMI, READY 등)는 꼭 필요하면 첫 등장에 풀어 설명.
- 모든 수치·주기·조건·차량 반응은 모델 근거와 단순화 가정을 명시. 정확하지 않은 물리 연출·폭발/화재 과장 금지.

## 3. 첨부파일 및 이전 대화 피드백의 사용법

첨부파일1의 이전 피드백은 다음 사항을 반드시 검토 대상으로 포함한다: `System/Domain/Feature/3D·E/E·Control SW`의 교차 관계, 단일 상태 소스, E/E 논리/3D/혼합 레이어, 기존 360도 부품 뷰 재사용, 도미노 역추적과 메모판의 분리, 고장 범위(센서·SW·통신·액추에이터 우선), 추리 단계의 관찰 정보 점진 공개, 로직 퍼즐을 가설 구별용 검증 준비로 재해석, 시험의 결과와 가설 결론 분리, 정상 기준과 사건 모델 비교, 첫 사건 튜토리얼, 오픈북, P0/P1/P2 우선순위.

**단, 이전 피드백의 `실제 영어 신호명 사용`, `쌍둥이 실험대 두 화면`, `PASS/FAIL/INCONCLUSIVE`, `TC 작성이 핵심 목표` 등은 최신 사용자 지시와 충돌하므로 그대로 구현하지 말 것.** 각각 `한글 기능명`, `기존 단일 화면 기반 비교`, `통과/실패/판정 불가`, `플레이어에게는 실험 장치 퍼즐·내부적으로만 TC 수준 데이터`로 검토한다.

첨부파일에 없는 사실이나 코드의 현재 상태를 추측해 확정적으로 말하지 말고 직접 확인한 사실과 설계 제안을 구분한다.

## 4. 결과 문서의 필수 화면별 형식 (원문 구조 보존)

각 `1)~5)`의 `ㄴ` 구조와 위 모든 세부 항목을 유지하고, **아래 템플릿을 매 화면마다 작성**:

1. **화면의 목적/학습 목표/추리상 역할** — 플레이어가 왜 이 화면에 오는가.
2. **현행 화면 분석** — 실제 확인한 레이아웃과 코드 위치, 이미 구현된 기능, 문제, 유지할 요소.
3. **16:9 레이아웃 명세** — 상단/중앙/좌측/우측/하단의 각 영역, 기존 앵커/크기/우선순위, 정확히 배치할 텍스트·버튼·3D·이미지·그래프·카드·팝업·HUD, 이동 금지 요소, 가림/겹침 방지. 최소 수정 전후 와이어프레임.
4. **그래픽/애니메이션/물성 명세** — 실제 조작, 신호 강조, 액추에이터 애니메이션, 사진·압정·실, 사운드·반응 시간·상태별 시각 변화. 장식이 아니라 이해/판단에 주는 효과.
5. **플레이어 행동 시퀀스** — `진입→행동→시스템 반응→얻는 정보→다음 선택→완료 조건→실패/재시도`를 버튼/상호작용 단위로.
6. **화면에 노출할 정보 vs 숨길 정보** — 정답 스포일러 방지, 정상 오픈북과 사건 증거 구분.
7. **문구 변경표** — `기존 원문 / 사용자 지정 새 문구 / 추가 제안(별도) / 적용 사건·조건`.
8. **데이터·기술 검증** — 기능·신호·상태·시나리오 ID 매핑, 요구사항, 기대 동작, 관찰 신호, 기술적 가정.
9. **기존 자산 재사용/구현 영향** — 파일·컴포넌트, 유지/수정/신규, 성능 영향, 변경 위험.
10. **승인 필요 항목** — 여러 대안을 비교한 뒤 추천 이유, 아직 미결정인 질문.

문서 마지막에 **원문 1~5의 모든 문장/질문을 확인한 추적표**를 넣고, `누락 0건`인지 확인하라. 확인할 수 없으면 누락 후보를 그대로 명시하라. **기술적으로 좋은 대안이라도 승인 전 기존 구조·레이아웃·문구를 멋대로 바꾸지 말 것.**
