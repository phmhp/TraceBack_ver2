# 구현 전 승인 요약

## 승인 요청안

1. 큰 흐름은 `차량 도메인 원리 → 도미노 원인 역추적 → 요구사항 기반 로직·실험 퍼즐 → 시뮬레이션 검증`의 기존 4단계를 유지한다.
2. 표준은 검증 대상·목적·추적성의 근거로만 사용한다. 4단계 순서, 팝업, 버튼, 메모판, 단계적 공개는 교육 효과와 플레이 경험을 근거로 설계하며 표준 요구라고 쓰지 않는다.
3. STEP 01은 세 관점의 외부 프레임을 동일하게 하고, 대표 구동 도메인부터 OFF→READY→입력→반응을 실제 공유 상태에 연결한 뒤 다른 도메인으로 확장한다.
4. STEP 02는 현재 live `EeTrace`를 기반으로 기존 폴라로이드·도미노·메모판 상호작용을 필요한 만큼 이식한다. 증거는 오른쪽, 탐색은 중앙, 메모판은 하단/별도 보드에 둔다.
5. STEP 03은 삭제하지 않고 사건 유형에 따라 계산·경계·전이·인터페이스·시스템 실험으로 의미를 바꾼다.
6. STEP 04는 기존 단일 화면과 탭을 유지하고 STEP 03 계획을 실제로 실행한다. 시험 기법명 객관식은 만들지 않으며 복수의 유효한 시험 경로를 허용한다.
7. 별도 Hardware Verification 트랙은 만들지 않는다. 부품은 시스템 관찰 대상으로 남기되 HW 자체 검증이라고 표현하지 않는다.
8. Chrome 1054×723을 필수 QA 뷰포트로 삼고, 주요 큰 화면도 회귀 확인한다.

## 구현 전에 필요한 한 가지 처리

현재 작업 트리에 기존 미커밋 소스·빌드 캐시·QA 산출물이 있다. 이는 사용자 작업으로 보존한다. 승인 후 첫 구현 파일과 겹치는 변경은 diff를 먼저 확인하고, 사용자 변경을 포함해 기준 커밋으로 묶을지 또는 그대로 둔 채 우리 변경만 분리할지 확인한 뒤 진행한다. `git reset --hard`, 강제 푸시, 무단 되돌리기는 사용하지 않는다.

## 승인 후 첫 작업

공통 레이아웃과 버튼/레이어 토큰만 한 작업군으로 수정한다. 실행, 핵심 상호작용, 콘솔, Chrome 1054×723 캡처, 회귀 테스트를 통과한 뒤 별도 커밋하고 다음 단계로 이동한다.

## 승인 문구

`V4 설계안 승인. 기존 미커밋 변경은 보존하고, 구현 계획의 단계 1부터 진행.`
