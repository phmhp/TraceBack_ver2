### 1.3 STEP02 → STEP03 전달 구조 제안 (읽기 전용 결과, 구현 아님)
- STEP02 출력: `{ 의심 구간(section), 선택된 가설 id(플레이어 선택), 최초 편차 신호 id, 근거 증거 id[], 반박한 가설 id[] }`.
- STEP03 입력: 위 가설 id로 **시험 준비 퍼즐 유형·요구사항 후보**를 선택(§5).
- 선택 가설이 오답이어도 STEP03에서 시험해 **지지/반박**되는 구조(가설 판정의 학습 가치). 현재는 STEP02에서 자동 정답화되므로 이 가치가 사라진다.

### 2.1 사건별 원본·문제·개선·시험 입력·기대·오라클 (나란히)

범례: 개선 문장은 **제안**이며 괄호 `⟨…⟩` 값은 모델 실행 또는 사양 근거가 필요해 확정하지 않았다.

#### (A) propulsion — STEP02 `req`
| 항목 | 내용 |
|---|---|
| 원본 | "요구사항: 가속 페달을 60% 밟으면 모터가 204 Nm를 내야 한다." |
| 문제 | ① 전제조건(READY·D단·차속)·주체(VCU인가 모터인가) 없음 ② 시간 조건 없음(정상상태? 과도?) ③ 허용오차 없음 ④ 60%→204 Nm는 **맵의 한 점**(3.4 Nm/%)인데 일반 규칙처럼 쓰임 ⑤ "모터가 낸다"는 시스템 응답과 VCU SW 요구가 섞임 |
| EARS 개선(When+While) | "READY이고 기어가 D인 **동안**, 가속 페달 위치가 P %일 때, VCU는 토크 요청 **T_req = min(3.4 Nm/% × P, T_avail)** 를 CAN으로 송신해야 한다. 정상상태에서 모터 토크는 T_req ±⟨허용 오차⟩ 이내여야 한다." (`T_avail`=가용 토크 260 Nm [코드]) |
| 시험 입력 | READY=1, D=1, 차속 60 km/h, 브레이크 해제, 페달 0→60 % (계단 또는 0.3 s 램프) [코드 `BASE.propulsion`] |
| 기대 결과 | 정상상태 모터 토크 204 Nm ±5 [코드 `expectedOutputs`] |
| 오라클 | 식(`3.4·P`, 260 제한) **또는** 골든 모델. 현재는 **골든 모델 값 + 고정 204/±5**(`contractForInput`이 다른 입력에선 모델에서 기대값 생성) |
| 수치 근거 평가 | 3.4 Nm/%·260 Nm·40 ms는 **[게임] 교육용 모델 상수**이며 실차 사양 근거 없음. 고정 수치 자체는 허용하나 **"교육용 가정값"임을 근거 칸에 기재**해야 함 |

#### (B) thermal — STEP02 `req` + STEP03 `req[]`
| 항목 | 내용 |
|---|---|
| 원본 ① | "냉각수가 65°C를 넘으면 냉각 팬을 100%로 돌려야 한다." |
| 원본 ② | "65°C 이상이면 팬을 켜고 60°C 이하가 되면 끈다" / "실제 회전수를 피드백 받아 목표 1850 rpm이 되도록 PWM을 계속 조절한다" |
| 문제 | **①과 ②가 서로 다른 요구**(100% 고정 vs 1850 rpm 폐루프, PI 듀티 ≈65~68 %, `simModel`·`REF.pi.out:"PWM 68%"`). ① "100%"는 팬 *요청(ON)*과 PWM *듀티* 혼동(F-05). ② 한 줄에 상태 전이(히스테리시스)와 폐루프 제어가 합쳐짐(단일성 위반). 시간 조건(몇 초 안에 ON?) 없음 |
| EARS 개선(분해) | R1 (When): "냉각수 온도가 상승해 65 °C 이상이 되면 Thermal ECU는 팬 요청을 ON으로 설정해야 한다." R2 (While): "팬 요청이 ON인 동안 Thermal ECU는 팬 회전 속도 목표 1850 rpm으로 PWM 듀티를 제어해야 한다." R3 (When): "냉각수 온도가 60 °C 이하가 되면 팬 요청을 OFF로 해야 한다." R4 (인터페이스): "PWM 출력 어댑터는 R2의 듀티를 팬 커넥터에 ⟨주기⟩ 이내에 출력해야 한다." |
| 시험 입력 | 냉각수 60→70 °C(4 s) [재현 `usecase`: 65.1→78.4 °C(8 s)] |
| 기대 결과 | 팬 요청 ON, PWM 출력 > 0, 팬 회전 1850 rpm ±120 [코드] |
| 오라클 | R1: 이벤트 시각·상태(요청 ON); R2: 연속량 허용오차; R4: 요청↔출력 **일치 비교**(결함 위치를 가리는 핵심 오라클). 현재는 최종 rpm만 기대값(`expectedOutputs`) |
| 문제 심화 | **출력 어댑터 요구(R4)가 어디에도 명시 안 됨** — 결함이 R4 위반인데 요구사항 줄에는 "ECU 출력단이 PWM과 12V를 공급한다"는 HW식 표현(`REF.thermal.req[5]`)뿐 |
| 수치 근거 | 65/60 °C·1850 rpm은 [게임] 모델 상수. 히스테리시스의 목적(깜빡임 방지)은 문장에 설명되어 우수 |

#### (C) brake — STEP02 `req` + STEP03 `req[]`
| 항목 | 내용 |
|---|---|
| 원본 | "브레이크를 55% 밟으면 3.2 m/s²로 감속해야 한다." / "회생은 배터리가 받을 수 있는 만큼만(1.1 m/s²)…" "부족분은 마찰이 채운다(3.2−1.1=2.1)" "마찰 몫 2.1을 42 bar로" |
| 문제 | ① 주체 불명(차량? Brake ECU?) ② 전제(차속 72 km/h [계약], 회생 가용량, ABS 비활성)가 요구문에 없음 ③ 3.2 m/s²는 **차량 수준 결과**이고 SW 요구는 "압력 명령 = 20 bar × 마찰 몫" ④ 구현 방식("회생 먼저, 부족분 마찰")이 요구사항에 섞임(요구 vs 설계 혼동) ⑤ **차속 72 km/h와 정지거리 32 m 모순**(T-03, 손계산 62.5 m) |
| EARS 개선 | R1(When+While): "브레이크 페달 위치 P %이고 회생 가용 감속도가 A_r일 때, Brake ECU는 총 목표 감속도 a_t = 3.2 × P/55 m/s²를 산정해야 한다." R2: "Brake ECU는 마찰 제동 몫 a_f = max(0, a_t − min(a_t, A_r))에 대해 압력 명령 20 bar/(m/s²) × a_f를 출력해야 한다." R3(인터페이스): "압력 명령 출력은 R2 값과 같아야 한다(⟨허용 오차⟩ 이내)." |
| 시험 입력 | 페달 0→55 %(0.6 s), 회생 1.1 m/s², 차속 72 km/h [코드] |
| 기대 결과 | 마찰 압력 명령 42 bar, 출력 42 bar, 감속 3.2 ±0.15 m/s² [코드: 감속만 `expectedOutputs`] |
| 오라클 | R3(요청↔출력 일치)가 결함을 직접 잡음. 현재는 최종 `dec`만 기대값이며 원인 위치를 알려 주는 **중간 오라클 없음** |

## 3. 요구사항 판정 vs 가설 판정 (혼동 방지) [코드]

| 구분 | 요구사항 판정 | 가설 판정 |
|---|---|---|
| 함수 | `assessContractRun` (`simModel.ts:211`) | `judgeRun`/`hypothesisStatus` (`scenarios.ts:199~220`) |
| 값 | PASS / FAIL / **INCONCLUSIVE** | 지지 / 반박 / **open(판단 보류)** |
| 질문 | "요구사항을 만족했나?" | "이 가설이 이 시험으로 가려졌나?" |
| 입력 | 계약이 정한 수준별 관찰 신호 + 기대 출력 | 수준 + 신호 방향(same/lower…) 규칙표 |
| 모순 사례 | propulsion SW 단위: 요구사항 INCONCLUSIVE(기대 출력 `mot`이 그 수준에 없음)인데 가설은 지지 | UX_AUDIT §6.3-2 |

- **분리 구조는 코드에서 올바르다.** 문제는 **화면에서 병기되는 방식**이다. 권장: 두 판정을 항상 다른 칸에 표시하고 INCONCLUSIVE 사유를 "기대 출력 미관찰"로 명시.
- 가설 판정은 **모델에 가설이 입력되지 않고 규칙표 일치 채점**이다(UX_AUDIT §9.4(8)). "가설을 시험했다"기보다 "정답 결함 1개를 실행하고 해석을 채점"하는 구조임을 알고 UI 문구를 정해야 한다.

### 4.1 A/B 비교와 재시험 중복 분석 [코드 `VerificationLab.tsx:1509·1512`]
- `sim = simulate(case, tech, fixed, execution)`(재시험·표시용), `abSim = simulate(case, tech, causeOk, execution)`(A/B 비교용). **둘 다 같은 함수, 같은 `execution`**이며 `fixed`/`causeOk`만 다르다.
- 원인이 정답이면 A/B(`causeOk=true`)와 재시험(`fixed=true`)은 **동일한 정상=수정 후 시리즈**를 계산·표시한다(계산 중복, 표·버튼 구조 거의 동일 — UX_AUDIT·CAPTURE_INDEX `ab-comparison-*` vs `retest-*`).
- 목적 분리 제안 [게임]: **A/B = "이 원인만 제거하면 증상이 사라지는가"(원인 확정 증명, 다른 후보 제거는 오답 처리 시 결함 잔존)**, **재시험 = "수정(수리 조치) 적용 후 같은 입력으로 FAIL→PASS와 영향 범위 요구사항 확인"**. 오답 수리를 모델에 반영하지 않으면 두 단계의 차이는 여전히 UI 상태뿐이다(T-22).

## 5. STEP03 — 시험 준비대 범용화: 퍼즐 유형 평가

공통 흐름 후보: 요구사항 해석 → 전제조건·시험 입력 설정 → 기대 결과·오라클 정의 → 관측·시험 환경 구성 → 시험 계약 확정. 현재 `RefPuzzle`은 "요구사항 해석 → 정상 로직 조립 → 계약 확정"이며 입력·오라클·환경은 **플레이어가 정하지 않고 계약 상수(`BASE`)**다.

| 퍼즐 유형(**공식 분류 아님**) | 기존 UI 재사용 | 신규 UI | 데이터 요구 | 모델 연결 | 판정 |
|---|---|---|---|---|---|
| 제어 로직 조립 | `RefPuzzle` 그대로 | 없음 | `REF` | 계약 문자열만(모델 불연결) | **지원** |
| 인터페이스·신호 매핑 | 조각 드래그·슬롯 재사용 가능(블록 대신 신호 이름·단위 조각) | 단위·범위 표시, 오배선 피드백 | 신호 목록, 정답 매핑 | thermal·brake의 I/O 어댑터 결함과 **직접 대응** | **우선 후보(재사용 가능)** |
| 상태 전이 구성 | 슬롯 재사용 불가에 가까움(상태·전이 간선 편집) | 상태도 편집기 | 상태·전이·조건 | 히스테리시스 모델은 있음(`on`) | 신규 중규모 |
| 이벤트·타이밍 조건 | 퍼즐 슬롯 일부 재사용(순서) | 타임라인 편집 | 주기·순서·지연 | thermal "실행 순서"와 대응, 모델엔 주기 개념 없음 | 신규 + 모델 확장 |
| 진단·고장 대응 조건 | 블록 조립 재사용 | DTC·상태 표시 | 진단 조건·반응 | **모델 `diag` 상수 0 → 신규 모델** | 신규 모델 필요 |
| 설정·캘리브레이션 비교 | 기존 표 A/B 함정 **이미 있음** | 파라미터 diff 표 | 표 값 쌍 | 표 B가 모델에 연결되지 않음(F-02) | **부분 지원** |
| 데이터 유효성·범위 검사 | "범위 검사" 블록 이미 있음(thermal `range`) | 범위·경계 입력 UI | 범위·경계값 | 모델에 범위 검사 단계 없음 | 신규 소규모+모델 |
| 기능 간 상호작용 | `side`(BMS 한계 조각 등) | 다도메인 흐름 | 도메인 간 신호 | 구동↔전원(MIN)·열관리→구동(derate)이 부분 존재 | 신규 중규모 |

- 판단: **STEP03을 "유형 선택식 준비대"로 일반화하는 최소 구현은 (로직 조립 + 신호 매핑 + 표 A/B 비교) 3유형**이며 모두 기존 조각/슬롯/표 UI 재사용 가능. 나머지 5유형은 신규 UI와 모델 확장이 필요해 **2일 범위를 넘는다**.
- STEP03에서 **시험 입력·기대 결과·오라클을 플레이어가 선택/정의**하게 하려면 현재 STEP04의 `CASE_DERIVS`(입력 선택)와 STEP03의 위치가 겹치므로 **입력 선택을 STEP03으로 옮길지** 결정 필요(구조 변경, 기술 제약 §8).

## 8. UI 재설계 시 반드시 반영할 기술 제약 (STEP02~04)
1. 가설은 STEP02에서 **자동 정답화하지 말고** 플레이어 선택을 STEP03/04 입력으로 전달한다(가설 판정의 의미가 여기에 달려 있음).
2. 요구사항 판정과 가설 판정을 **항상 별도 칸**에 표시한다.
3. 요청(Request)·출력(Output)·피드백을 **별도 신호 id**로 정의하고 요구사항·퍼즐·모델·증거가 같은 id를 쓴다.
4. 수치 표시는 요구사항 줄·퍼즐·모델 상수가 **일치 테스트로 보장**되어야 한다(현재 `SCENARIO_META.review` 메모뿐).
5. 오라클 종류(식/골든 모델)를 표시하고, **원인 위치를 가리는 중간 오라클**(요청↔출력)을 최소 1개 포함한다.
6. 새로운 관측 표현은 **새 탭 없이** 기존 신호 그래프 관점 안에 레인/패널로 넣는다.
7. 3D·`RefPuzzleTrack`은 계산 결과가 아니라 불리언 `works`로 구동된다(UX_AUDIT §9.2 ④). "시뮬레이션 결과"로 서술하지 않는다.
