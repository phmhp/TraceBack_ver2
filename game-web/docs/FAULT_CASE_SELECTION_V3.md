# 고장 사건 선정 기준과 후보 골조 (설계 단계, 구현 전)

목적: 새 고장 사건을 "무턱대고" 만들지 않고, 선정 기준 → 분류 체계 → 후보 목록 → 1차 선정 순으로 정합니다. 이 문서는 후보 골조이며 **게임 데이터(화면·수치·문구)는 만들지 않았습니다.** 사건 하나를 구현하려면 8절의 사건 시트가 먼저 승인돼야 합니다.
관련: `DESIGN_DECISIONS_V3.md`(7절 사건 추가 가이드, 5.4 정답 힌트 방지), `CROSSCHECK_STEP01.md`(GPT 교차 검토).

## 1. 선정 기준 (게이트 + 균형)
### 1.1 필수 게이트 (하나라도 못 지키면 후보에서 제외)
| # | 게이트 | 설명 |
|---|---|---|
| G1 | 운전자 체감 | 운전자가 느끼거나 보게 되는 증상이 있다 (가속, 제동, 조향, 소리, 경고등, 계기판, 시동, 충전, 표시값 등). 내부 로그에서만 보이는 문제는 제외 |
| G2 | SW 검증으로 발견·구분 가능 | SW 단위, SW 통합, 임베디드, 시스템 통합 중 **최소 한 수준**에서 신호로 구분된다. 다른 수준에서는 "판단 보류"가 나올 수 있어야 한다(수준 선택 학습) |
| G3 | 요구사항 위반이 명확 | 정상 기준(요구사항 한 문장 + 수치/조건)이 있고, 이탈이 측정 가능하다 |
| G4 | 수치 모델로 재현 | `simModel`에서 정상/고장/수정 3회 계산이 가능하고, 화면마다 숫자가 서로 모순되지 않는다 |
| G5 | 한 사건에 한 가지 새 학습 | 이미 다룬 개념(경계 곱셈 오류 등)의 반복이 아니라, 사건마다 새 검증 개념 하나를 가르친다 |
| G6 | 안전한 표현 | 실제 브랜드·실제 사고 묘사 없음. 위험한 고장은 "경고와 안전 상태 전환"까지만 |
| G7 | **도주 상황에 어울리는 차량 거동 영향** (2026-11-14 추가) | 고장이 주행·제동·조향·출력·시동 등 **차량 거동**을 바꿔 도주를 방해해야 한다. 표시만 틀리고 달리는 데 지장이 없는 사건(예: 속도계 오표시)은 게임 흐름에 맞지 않아 제외. 단, 같은 고장 범주(구성·수치 등)는 거동에 영향을 주는 다른 사건으로 대체한다 |
### 1.2 하드웨어 고장의 취급 (2026-11-14 확정)
- **진짜 원인은 SW(또는 SW 설정·통신·시퀀스)**입니다. 게임은 "고장을 수리하고 다시 달리는" 이야기이고, 실무에서도 검증은 개발 단계에서 고장을 예방하기 위한 활동이므로 HW 원인 사건은 만들지 않습니다.
- HW 가설은 "SW 시험으로 무죄를 증명(반박)하거나 이 수준에서는 판단 보류"가 되는 **오답 후보로만** 사건당 0~1개 둡니다. (실무의 "SW는 정상임을 증명하라"가 이 형태로 남습니다.)
- 따라서 후보 C15(휠속 센서 소실, HW 증명형)는 **제외**합니다.
### 1.3 균형 축 (후보 묶음 전체에서 고르게)
1. 도메인: 11도메인 중 최대한 고르게(파워트레인 / 섀시 / 차량 제어 묶음 각각)
2. 고장 범주: 3절의 분류를 섞기
3. 빈도 × 심각도: 4사분면을 모두 채우기 (빈번+경미 / 빈번+중대 / 드묾+경미 / 드묾+치명)
4. 발생 시점·트리거: 4절의 분류를 섞기 (시동 전, 정차, 출발, 순항, 제동, 연속 부하, 시간 경과, 무작위, 항상 등)
5. 발견 수준: 사건마다 "결정적으로 가르는 수준"이 서로 다르게 분포
6. 퍼즐 UI 종류: SW 블록 조립 / 신호 경로 선택 / (추가 시) 상태 전이도 채우기 등
7. 난이도: 쉬운 증상 → 헷갈리는 증상 순서
8. 비용: 새 에셋·새 레이싱 연출이 필요한 정도(싼 것부터)
### 1.4 추가로 점검할 것 (사용자 질문 "또 뭘 고려할까"에 대한 답)
- **ISO 26262 관점**: 치명 사건은 안전 목표 위반과 FTTI(고장 허용 시간)를 사건 시트에 적고, 사건이 요구하는 안전 메커니즘(진단, 폴백)이 게임에 나오는 장면과 맞는지 본다.
- **가설 구성 규칙**: 사건당 가설 3~4개, HW 가설 1개 포함(반박 또는 판단 보류), 함정 노드(원인보다 늦게 달라지는 결과) 포함, 참 가설 위치·길이·구체성 섞기(5.4).
- **정답 요령 방지**: 세 사건이 모두 "제어기 SW 경계"가 답이면 안 됨. 답이 되는 구간의 형태(입력 / 계산 / 상태 전이 / 통신 / 출력 / 설정)를 사건마다 다르게.
- **사건 분량**: 한 사건 약 5~8분. 필수 사건 수와 선택 사건 풀 크기(예: 풀 8개 중 세션마다 3개)를 정해야 한다.
- **저장 호환**: `CaseId` 합집합이 늘면 저장 키·진행 상태 구조에 영향. 사건별 상태를 `Record<CaseId, ...>`로 일관 유지.
- **에셋 재사용**: 새 부품 이미지가 필요한 사건은 뒤로. 이미 있는 부품(VCU, BMS, 브레이크, 팬 등) 중심으로 먼저.
- **교육 목표의 표준 연결**: ASPICE SWE.4/5, SYS.4/5, ISO 26262-6/-4 중 어느 시험 수준 개념을 가르치는지 사건마다 한 줄.

## 2. 사건 선정 점수표 (후보 평가용, 0/1/2)

## 4. 시점·트리거 분류 (편견 없이)
고장은 "추월 구간에서 가속하면"처럼 하나의 모양만 있지 않습니다. 레이싱에서 다음을 모두 표현할 수 있어야 합니다.
| 시점 (phase) | 예 | 비고 |
|---|---|---|
| 시동 전 / 준비 | READY가 안 켜짐, 계기판 점검 후 멈춤 | 출발 전에 증상, 레이스 시작 자체가 막힘 |
| 정차·대기 | 신호 대기 중 시동 꺼짐, P에서 안 풀림 | 속도 0에서 발생 |
| 출발·가속 | 울컥임, 출발 지연 | 페달 전개 순간 |
| 순항 | 일정 시간 뒤 힘 빠짐, 간헐 | 아무 조작 없이 발생 |
| 감속·제동 | 제동 중 끊김, 정지 직전 울컥 | 조작에 반응 |
| 조향·선회 | 조향 무거움/쏠림 | 특정 속도·각도 |
| 연속 부하 | 오래 달린 뒤 출력 제한 | 누적(열) |
| 환경 | 저마찰, 저온, 터널 | 맵의 구간으로 |
| 시간 경과 | 몇 분 뒤 카운터 롤오버 | 타이머 |
| 이벤트 연쇄 | 변속 + 제동 순서가 특정 조합일 때 | 상태 전이 |
| 무작위 / 간헐 | 가끔 발생, 재현률 낮음 | 재현 입력 선택이 학습 요소 |
| 트리거 없음 | 처음부터 항상 이상 | 설정·구성 오류 |
지속성: **영구(항상)** / **래치(한 번 생기면 유지)** / **간헐(조건 맞을 때만)**.
### 레이싱 구현에 필요한 확장 (설계만)
- 현재 레이싱은 "거리 구간(OVERTAKE_ZONE 등)"에 맞춰 고장을 켭니다. 이를 **고장 스케줄**로 일반화합니다: `{ phase, condition(조작·속도·시간·환경), delay/확률, persistence, 증상 연출 }`.
- 필요한 새 연출: (1) 시동 전 단계 증상 장면, (2) 정차 중 발생 장면, (3) 갑작스런 시동 꺼짐/계기판 정전, (4) 트리거 없음(처음부터), (5) 간헐 발생. 연출 비용이 크므로 1차 선정에서는 기존 연출로 가능한 것 + 시동 전/정차 연출 1종부터.
- 사건 시트에 "운전자가 보는 것(화면·소리·경고등)"을 한 문장으로 적고, 레이싱 코드는 그 문장을 구현합니다.

## 5.1 균형 확인 (후보 15 + 기존 3 기준)
- 도메인: 구동 3, 제동 4, 조향 1, 전원 2, 변속 2, 열관리 2, 통합 1, 통신 1, ADAS 1, 충전 1 → **현가·충전·클러스터 쪽이 부족**. 현가는 센서 기반 후보를 추가하거나(예: 댐퍼 폴백 오작동) 이번 라운드에서 의도적으로 제외한다고 기록.

- 빈도·심각: ◎경(C03, C10, C14), ◎중(C01, C09), ◎경~중(C05), ○중(C08), ○치명(C04, C11), △치명(C02, C06, C12), ○경(C13), △중(C15). 4사분면 모두 있음.

## 7. 사건 데이터에 들어가는 "노출 정보" 전수 (검수 대상 목록)
사건 하나의 정보는 아래 모든 화면에 퍼집니다. 이 중 하나라도 어긋나면 안 되므로 사건 시트로 한 곳에서 정하고, 구현 뒤 화면별로 대조합니다.
1. 사건 이름·장 제목·요약 증상 (`SCENARIOS`)
2. 레이싱: 시점·트리거·고장 스케줄, 운전자가 보는 연출(팝업 대사, 경고등, 소리), 이후 정차 흐름
3. 컷신·대화 문구
4. STEP02: 운전자 진술(`QUOTE`), 계기판(`LAMP`), 관찰 요약(`OBSERVED`), 증거 폴라로이드(이미지 포함), 노드 목록(`doms`: 구역·라벨·기준·이번·단위·상태·달라진 시점·원인 후보), 증상 카드, 의심 구간 선택지, 구간 들여다보기(`SUBSYS`), 가설(문구·반박 근거·참/거짓)
5. STEP01 연결: 오픈북 노트(`BOOK`), 관련 도메인·기능 번호
6. STEP03: 요구사항 문장(`req`), 블록·빈칸·남은 조각·옆 입력·표 값, 함정 조각(표 B 등), "왜 필요한가"(`WHY`), 목표(`RIG_GOAL`), 시험 설계서 기대값·허용 오차·입력 조건·관측 신호
7. STEP04: 가설별 질문(`QUESTIONS`), 수준별 신호(`SIGNALS`), 판단 규칙(`rules`, `hold`, `decideAt`), 원인 카드(`CAUSES`: 이름·유형·위치·설명·이미지), 수리 선택지(`FIXES`), 회귀 목록, 시험 계약(`verificationContract`), 수치 모델(`simModel`, `vehicleSim` 훅)
8. 엔딩: 사건 그림(`CASE_VISUAL`), 교훈 한 줄, 안전 관점 토글(`CASE_SAFETY`)
9. 이미지 프롬프트: 새 부품·증거 사진
10. DEV 메뉴 이동 항목, 테스트(수치 일관성 테스트)

## 8. 사건 시트 양식 (사건 1개당 1문서, 구현 전에 승인)
`docs/cases/<id>.md`에 아래를 먼저 씁니다. 숫자는 한 번만 정의합니다.
```
# <사건 ID> <이름>
1. 개요: 도메인 / 범주(3절) / 빈도·심각 / 가르는 수준 / 새 학습 / 표준 연결
2. 운전자가 보는 것: 한 문장(시점·트리거·지속성), 연출 요소(경고등·소리·계기판)
3. 정상 기준: 요구사항 한 문장 + 수치(입력→출력, 허용 오차)
4. 고장 모델: 주입 지점, 정상 vs 고장 값 표, 영향 신호와 달라진 시점
5. 노드 목록(STEP02): 구역·라벨·기준·이번·시점, 함정 노드, 최초 편차
6. 가설: 3~4개(HW 1개), 반박 근거, 참 가설, 판정 수준별 결과(지지/반박/보류)
7. 의심 구간 선택지 3개(형식·길이 균일, 정답 위치)
8. 퍼즐: UI 종류, 블록 흐름, 빈칸, 남은 조각(함정 포함), 요구사항 문장, 시험 설계서 입력·기대값
9. 실험대: 수준별 관측 신호 표, 질문, 수리 선택지, 회귀 대상
10. 위험·안전: 치명 사건이면 안전 목표, FTTI, 표현 제한
11. 필요한 에셋·연출·모델 변경 목록과 비용
12. 교차 검토 결과(GPT/사람) 기록
```
승인 후 구현하고, 구현 뒤에는 시트와 화면 숫자를 대조하는 일관성 점검(자동 스크립트 + 수동 순회)을 거칩니다.

## 8.5 규칙·템플릿 위치
이 문서의 기준은 `docs/fault-cases/RULES.md`(R1~R15)와 `TEMPLATE_CASE_SHEET.md`로 일반화돼 있습니다. 선지 규칙(R1: 정답 외 선택지는 확실히 틀려야 하고 엉뚱하면 안 됨), 진단 채널(R11), 확장 필드(R12)를 포함합니다.

## 9. 진행 순서 제안
1. (이 문서) 기준·후보 승인, 1차 선정안 조정
