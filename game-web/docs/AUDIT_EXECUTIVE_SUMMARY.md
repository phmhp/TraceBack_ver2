## 1. 핵심 판단

1. 구조는 **교육용으로 타당하나 "정합성"은 수치·표현 불일치로 훼손**돼 있다. 3사건 중 propulsion만 STEP02~04 수치가 일치하고, thermal·brake는 모순이 남아 있다.
2. **가장 큰 기술 문제는 thermal**: (a) 요청(ON)과 PWM 출력이 같은 "100%"로 표기, (b) STEP03 현장 값이 PWM 100%로 표시되어 실제 결함(PWM 쓰기 생략)을 가리거나 HW 결함처럼 보임, (c) STEP02에서 정상으로 표시된 커넥터 PWM이 STEP04에서 이상으로 판정, (d) 열 사슬 미재현.
3. **분류체계 관점에서 3사건은 14축 중 A6·A8·A12가 모두 같은 값**(연속량 편차·로직 조립·연속 그래프)이라 신규 결함 유형(상태·이벤트·진단·통신)은 UI·모델이 모두 새로 필요하다.
4. 요구사항 판정(PASS/FAIL)과 가설 판정(지지/반박)은 코드에서 **올바르게 분리**되어 있다. 화면 병기와 **STEP02 가설 자동 정답화**(`EeTrace.tsx:401`)가 문제다.
5. 시험 수준(`LV`)과 환경(`env`)을 별개 축으로 둔 설계, 결함 주입이 SW 경계 안이고 하류로 전파되는 점은 **유지할 강점**이다.

## 4. UI 재설계 시 반드시 반영할 기술 제약

1. 한 화면에서 같은 이름의 값은 **같은 신호 id**를 가리켜야 한다(요청/출력/피드백 분리).
2. 요구사항 판정과 가설 판정을 같은 칸에 합치지 않는다.
3. 오답 가설도 STEP03에서 시험 대상이 되도록 STEP02 → STEP03 전달 구조를 유지한다(자동 정답화 금지).
4. 3D·`RefPuzzleTrack`은 계산 결과가 아니라 연출(`works` 불리언)이다. "계산 결과"처럼 표현하지 않는다.
5. 새 관측 도구는 **새 탭이 아니라 기존 4관점 안**에서 상황별 패널·레인으로 표시한다.
6. 신호 이름·단위는 STEP01~04에서 하나의 목록을 공유한다(STEP01 SW 블록 ↔ STEP03 블록 ↔ `simModel` 신호가 현재 서로 다른 분해).
7. 시험 수준 이름은 한 가지로(`제어기 I/O 통합 시험` vs `통합 SW·제어기 I/O 시험`)와 환경 칩은 "수준=무엇, 환경=어디서"를 유지.
8. 사건 순서가 고정(thermal이 propulsion 수리 뒤에만 시작)이고 brake는 일반 플레이로 진입 불가임을 가정해 흐름 화면을 설계한다.
9. 무스크롤·고정 비율을 적용해도 STEP04의 다섯 단계·네 관점·A/B 비교·재시험은 **보존**한다(기존 요구).
10. 수치 표시 단위·시간축이 화면 간 일치해야 한다(thermal "초" vs "분(압축)").
