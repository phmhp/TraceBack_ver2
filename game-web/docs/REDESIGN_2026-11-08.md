# 재설계안: 차고 · 원인 역추적 · 시뮬레이션 검증 (2026-11-08)

기준 문서 `VERIFICATION_FLOW_STANDARD.md`의 단계 순서는 유지한다. 이 문서는 세 화면의 **플레이 방식**을 다시 정한다.

## 1. 검증 레벨 체계 (용어 확정)

**두 축은 따로 쓴다.**

**축 1. 시험 레벨 (무엇을 시험하나)** — 이름은 모두 "시험"으로 통일한다.

| 구분 | 표준 | 레벨 | 대상 |
|---|---|---|---|
| SW 레벨 | ISO 26262-6 9절 | SW 단위 시험 | SW 단위 하나 |
| | ISO 26262-6 10절 | SW 통합 시험 | SW 컴포넌트(SWC) 사이 |
| | ISO 26262-6 11절 | 임베디드 SW 시험 | 실제 ECU에서 도는 SW |
| 시스템 레벨 | ISO 26262-4 7절 | HW·SW 통합 → 시스템 통합 → 차량 통합 | 실부품·여러 ECU·차량 |

**축 2. 시험 환경 (어디서 돌리나)**: MIL / SIL / PIL / HIL / 차량. 같은 레벨도 여러 환경에서 할 수 있다.

- **게임 탭은 4개로 둔다:** SW 단위 시험 / SW 통합 시험 / 임베디드 SW 시험 / 시스템 통합 시험. 마지막 탭은 Part 4의 세 단계를 하나로 묶은 것이고, 탭 설명에 그렇게 적는다.
- **용어:** "자극"이 아니라 **입력값 인가**로 쓴다.
- **시험 방법(표준):** 요구사항 기반 / 인터페이스 / 고장 주입. 게임에서 실제로 수행할 수 없는 방법(모델-코드 비교)은 넣지 않는다.

## 2. 시뮬레이션 검증 재설계

### 2-1. 무엇을 하는 단계인지부터 명확히: 미션 두 개를 차례로
| 순서 | 미션 | 질문 | 판정 |
|---|---|---|---|
| A | **정상 시나리오 확인** | 요구사항 입력을 넣으면 요구사항대로 동작하나? (= 개발이 요구사항대로 됐나) | PASS면 그 레벨 안은 요구사항대로 만들어진 것 |
| B | **고장 재현** | 현장 조건(또는 고장 가설)을 넣으면 같은 증상이 나오나? 처음 갈라지는 곳은? | 같은 증상이 재현되고 첫 불일치가 원인 구간이면 원인 확정 |

- **구동:** A를 SW 단위 시험에서 하면 바로 FAIL이 나요. 원인은 SW예요.
- **열관리·제동:** SW 레벨에서 A는 PASS예요. 그러니 "SW는 요구사항대로 만들어졌다 → 원인은 HW 쪽"이라고 추리하고, 시스템 통합 시험에서 B로 확정해요.

이 흐름 자체가 검증적 추리가 된다.

### 2-2. 정답 맞히기 → "어느 것이 적절할까요?" (선택이 실제 시험에 반영)
- 레벨과 방법은 **아무거나 골라도 시험이 실제로 돌아간다.** 정답을 외우게 하지 않는다.
- 부적절한 선택은 결과로 드러난다. 예: 열관리를 SW 단위 시험에서 돌리면 PASS가 나오고, 엔지니어가 이렇게 짚어 준다: "이 레벨에서는 팬이 모델이라 고장이 안 보입니다."
- 별점은 **시험 횟수와 비용**(레벨이 올라갈수록 비쌈)으로 매긴다. 정답 하나를 강제하지 않으면서도 효율적인 순서를 배우게 된다.
- 질문은 문장 대신 **카드 그래픽**으로 보여 준다.
  - 레벨: 환경 그림 + 보이는 신호 미리보기
  - 방법: 입력 그래프 미리보기

### 2-3. 화면을 두 가지 보기로 분리
| 보기 | 내용 |
|---|---|
| **로직 흐름** (SW 레벨) | 시뮬링크식 블록도. 블록 사이 선 위에 실시간 값 표시창, 오른쪽에 스코프. 퍼즐에서 맞춘 블록이 그대로 "정상 설계"가 된다. |
| **하드웨어 시뮬레이션** (임베디드·시스템) | **임베디드:** ECU 상자와 시뮬레이터(센서·부하 모델)를 배선으로 연결하고, 핀 LED와 PWM 파형을 보여 준다.<br>**시스템:** 실제 팬·유압·모터 3D 모델이 수치 모델대로 움직인다. 멈춘 곳에는 빨간 표시와 "명령은 도착, 회전 0 rpm" 같은 설명이 붙는다. CAN 메시지가 버스 위로 흐른다. |

**SW 통합 시험은 아키텍처 배치로 그린다.**
- SWC를 한 줄로 늘어놓지 않는다. 포트와 신호선이 있는 **구조도**로 그린다(입력 SWC → 요구 SWC → 중재 SWC → 통신 SWC, RTE 위 연결).
- 같은 SWC를 겹쳐 그리지 않는다.

### 2-4. 관측점(프로브) 미션 문장화
각 실행 전에 할 일을 한 줄로 준다.
1. 입력값 인가 확인
2. 비교할 관측점 고르기: 입력 쪽 1개 이상 + 출력 쪽 1개 이상
3. 실행
4. 처음 갈라진 신호 지목

**관측점은 정해진 수만큼만 꽂을 수 있다**(예: 3개). 그래서 어디를 볼지 고르는 것 자체가 추리가 된다.

### 2-5. 퍼즐과 겹치지 않나?
겹치지 않게 역할을 나눈다.
- **퍼즐:** 요구사항에서 **기대 동작을 정의**한다(시험의 판정 기준 = 오라클).
- **시뮬레이션 검증:** 그 기준으로 **실행·비교**한다.

화면에서도 이 연결을 보여 준다. 시뮬레이션의 "정상 설계" 쪽에 "퍼즐에서 만든 로직" 표시를 붙인다.

## 3. 원인 역추적 재설계 (제안하신 방식 반영: 평가 = 좋음)

**화면 구성:** 한 판에 E/E 아키텍처(센서 → 제어기 → CAN → 부품 → 차량)를 펼치고, 왼쪽에 증상 폴라로이드를 둔다.

**진행 순서**
1. **틀린 그림 찾기:** 정상 기준 폴라로이드와 이번 주행 폴라로이드를 나란히 보여 준다. "출력이 어디서 잘못됐는지 찾으세요." 다른 곳(예: 가속 그래프의 꺾임)을 누르면 E/E 판의 출력 부품에 표시가 붙는다.
2. **거꾸로 도미노 밀기:** 출력에서 도미노를 뒤로 밀면, 그 출력과 연결된 앞 흐름만 E/E 판에서 켜진다. 연결되지 않은 부품은 흐려진다. 이게 후보 범위가 된다.
3. **카드로 좁히기:** 켜진 후보가 카드로 나온다. 측정하면 정상 카드는 뒤집혀 회색이 된다. 기준과 다르고 더 먼저 달라진 카드는 남는다. 지금의 시간 단서 규칙을 그대로 쓴다.
4. **의심 구간:** 남은 카드의 입력이 모두 정상이면 그 구간을 확정한다. 마지막 화면은 경계 카드 하나 + 쓰러진 도미노 + 버튼만 둔다. 정보를 줄인다.

**작업량:** E/E 판(`EeBlueprint`)과 도미노·카드 로직을 재사용해서 화면 구성 위주로 바꾼다.

## 4. 차고 재설계 (단계형)
| 단계 | 화면 | 플레이어가 하는 일 |
|---|---|---|
| 1 | 전체 차량(도메인 나란히) | 도메인 하나 고르기 (탭 강조, 다른 버튼은 잠김) |
| 2 | 그 도메인 3D | 기능 하나 고르기 |
| 3 | **3분할 동기 화면**: 3D(부품 위치) · E/E(배선·통신) · Control SW(ECU 안 계산) | 단계 번호 하나로 세 화면이 함께 이동한다. ◀ ▶로 직접 넘긴다(자동 재생 없음). 지금 단계의 부품·선·블록이 동시에 켜진다. |
| 4 | 확인 한 문제 | "이 단계의 출력 단위는?" 같은 짧은 확인 → 정비 노트에 카드 저장 |

- 빼 보기·범인 찾기 탭은 숨겼다(코드는 보존).
- 비유 표현을 쓰지 않는다(센서 = 물리량을 측정해 전기 신호로 출력하는 부품 등).
