# TraceBack contest/v3 설계 결정 기록

이 문서는 contest/v3 작업 중 사용자와 합의한 **설계 기준**을 한곳에 모은 것입니다. 앞으로 고장 시나리오를 추가하거나 단계를 고칠 때 "왜 이렇게 되어 있는지"의 기준으로 씁니다.
작업 이력은 `CONTEST_V3_HANDOFF.md`, 원 요구 명세는 `CONTEST_V3_MASTER.md`, 도메인 구조 초안은 `EV_DOMAIN_SPEC_DRAFT.md`, GPT 교차 검토 자료는 `CROSSCHECK_STEP01.md`에 있습니다.
기록 시점: 2026-11-14 (STEP01~04 구현 완료).

---
## 1. 게임 목적과 단계 역할
사내 공모전용 EV 검증 교육 게임입니다. 목표는 두 가지입니다.
1. 자동차 도메인의 동작 원리 학습 (기능, 부품·E/E, SW 구성, SW 로직)
2. 검증 엔지니어의 사고방식 습득 (증상 → 기준 위반 → 격리 → 가설 → 시험 설계 → 원인 제거 확인 → 수리·재시험)

| 단계 | 이름 | 역할 | 사용자가 정한 포인트 |
|---|---|---|---|
| STEP01 | 정비소 | 도메인별 동작 원리를 4개 층으로 학습 | 도메인은 가로 내비, 층은 세로 "깊어짐" |
| 레이싱 | 주행 | 운전자 입장에서 고장을 체감 (주행 중, 정차, 출발 전 모두 포함) | 레이싱 비율을 높일 것 (후순위) |
| STEP02 | 도미노 추적 | 첫 편차를 찾고 가설 세우기 | 단계 축소, 증상은 기준 위반으로 |
| STEP03 | 퍼즐 | 요구사항에서 정상 동작을 만들고 시험 기준으로 바꾸기 | 고장 종류에 따라 UI가 달라져야 함 |
| STEP04 | 실험대 (전 "검증") | 가설 원인을 제거해 정상 복귀를 확인하고 재시험·비교 | 이름은 "실험대" |
| 엔딩 | 해적선 | 보상 | 후순위 |

기술 검토 기준은 EV 아키텍처, 자동차 공학, AUTOSAR, ASPICE, ISO 26262입니다. 수치는 "예시 파라미터"이며 특정 OEM 사양이 아닙니다.

## 2. 사용자 규칙 (모든 작업에 적용)
**UI 검수**
- 모든 탭·층·조합을 하나도 빠짐없이 순회해 검수합니다. 비용이 크면 단계별로 마친 뒤에 합니다.
- 박스 밖으로 나가는 글, 가려진 버튼, 짧은 라벨이 두 줄로 접히는 것, 버튼 겹침이 남아 있으면 완료로 보고하지 않습니다.
- 글은 띄어쓰기 위치에서만 줄바꿈합니다. 문구는 짧고 핵심만 씁니다.
- 폰트는 가능하면 12px 이상. 레이아웃이 크기 변화에도 깨지지 않아야 합니다 (1600×900 고정 캔버스를 통째로 축소).
**작업 방식**
- 추리 단계(STEP02~04)의 레이아웃 변경은 **먼저 상세히 설명하고 승인 후 적용**합니다. (STEP01은 A안 승인 후 진행)
- 단계 수와 질문 수는 꼭 필요한 만큼만 둡니다. 소단계마다 맞춤 UI를 새로 만들지 않습니다.
- 고칠 때는 제대로 고칩니다. 부분 땜질보다 데이터와 시각화를 함께 정리합니다.
- 화면과 문서에 "교육용 단순화", "실제 아님" 같은 문구를 넣지 않습니다. 이모지 금지. 답은 버튼으로 고르게 합니다(서술형 금지).
**내비게이션**
- 상단 로드맵 칩은 **뒤로는 자유, 앞은 도달한 곳까지만** 이동합니다.
**DEV 도구**
- DEV 박스는 레이아웃에 영향을 주면 안 되고 최종 빌드에서 제외합니다. 정답 팝업 같은 형태는 금지.
**에셋**
- 이미지는 사용자가 ChatGPT로 로컬에서 만듭니다. 프롬프트는 **한 번에 한 이미지**, 파일명 명시, 저장 폴더 명시. 규칙은 `ASSET_REQUEST_EV_2026-11-14.md`.

## 3. 공통 레이아웃 계약 (1600×900 캔버스 기준)
- `src/entry.tsx`의 `ScaledFrame`이 1600×900 iframe을 화면에 맞춰 통째로 축소합니다. `?noscale`로 우회.
- 작업 영역은 그리드이며 모든 단계가 같은 골격을 씁니다.

| 영역 | 크기 | 비고 |
|---|---|---|
| 상단 MISSION 바 | 높이 56px | `MissionBar` |
| 우측 패널 | **폭 360px** | 황금비 절충. 스테이지:우측 ≈ 1 : 0.32 |
| 하단 도크 / 흐름 영역 | STEP01 150px, STEP02 150px | 한 단계에서 한 질문만 |
| 다음 버튼 | 우측 360px 열 바로 아래, 우측 끝 정렬 | STEP01·02에서 적용, STEP03·04도 동일 |

- STEP01 추가: 도메인 내비 64px(3묶음), 왼쪽 층 레일 84px.
- 그리드 영역에 `grid-area` 이름만 쓰면 열 개수 변경 때 옛 열 범위가 남을 수 있어, 푸터·내비는 `grid-column: 1 / -1`을 명시합니다.
- 레거시 CSS가 `!important` 절대 위치를 많이 씁니다. 새 레이아웃은 컨테이너 그리드로 감싸고 옛 위치를 무력화합니다.

## 4. STEP01 정비소
### 4.1 구조 (승인)
- 도메인 11개 × 기능 4개 = 44기능, 3묶음: 파워트레인(구동·고전압 전원·충전·열관리), 섀시(제동·조향·현가·변속·주차), 차량 제어(차량 통합·통신·진단·운전자 지원·HMI).
- 기능마다 분류 태그: 요구 해석 / 제어·배분 / 실행·보호.
- 층 4개(왼쪽 세로 레일, 아래로 갈수록 깊어짐): ① 기능 흐름(3D 차량) ② 부품·E/E(2D 연결도, 실제 부품은 클릭/모드로 3D·사진) ③ SW 구성(`SwcView`, 제어기 안 SWC) ④ SW 로직(블록도, 7블록까지 한 줄).
- 3D 모델은 ①과 ②에서만 보입니다(원래도 그랬음). SW 층은 물리 형상이 없어 2D입니다.
- 전체 보기 = 시스템 관점 아키텍처 (`ArchitectureOverview.tsx`): 왼쪽 입력, 가운데 3묶음 도메인, 오른쪽 출력, 아래 차량 네트워크 띠. 협조 신호 칩(9종)을 누르면 점선 화살표가 그려집니다. 이전 3D 전체 차량은 `3D 차량` 토글.
### 4.2 데이터 (`src/features/garage/evData.ts`가 단일 출처)
- `EV_DOMAINS[id].features[i]` = `{ name, category, summary, layers: [기능 흐름, 부품·E/E, SW 컴포넌트, SW 로직] }`.
- `OVERVIEW_IO`(전체 보기의 입출력), `COORD_SIGNALS`(협조 신호)도 같은 파일.
- 층 이름 규칙: 1층 노드 라벨은 `partModelFor`(experiences.tsx)가 정규식으로 3D 모델·이미지와 연결하므로, 새 부품 라벨은 기존 정규식과 맞거나 정규식을 추가합니다. 2층은 AUTOSAR SWC 명명(`DriverRequest` 등). 3층은 `blockKind()` 키워드(맵·MIN·PI·상태·조건 등)로 블록 아이콘이 정해집니다.
- **기능 인덱스를 다른 화면이 번호로 참조합니다.** 순서를 바꾸면 안 됩니다: 구동 0(운전자 토크 요청), 열관리 0·1·3, 제동 1(오픈북·퍼즐 노트), 구동 3은 인버터(`OWNER_OVERRIDE "drive-3"`).
- 퍼즐 블록·시험 관련 L3 이름(구동 0, 열관리 0·1·3, 제동 1)은 시나리오와 맞물려 있어 바꿀 때 STEP03 블록 이름도 같이 확인합니다.
### 4.3 도메인/기능 추가 체크리스트
1. `evData.ts` `DomainId`, `DOMAIN_ORDER`, `EV_DOMAINS`에 추가(기능 4개, 층 4개).
2. `experiences.tsx`의 `DOMAIN_ICON`, `domainHardware`, `DOMAIN_SYMPTOM`, `INPUT_MISSION`, `INPUT_ACTION`, `NORMAL_RESPONSE`, `READY_RESPONSE` (타입 검사가 빠진 곳을 알려 줌).
3. 전체 보기: `OVERVIEW_IO`, 필요하면 `COORD_SIGNALS`.
4. 부품 이미지가 생기면 `partModelFor`에 라벨 연결, `scripts/image-prompt-data.mjs`에 프롬프트.
5. `npm run crosscheck`로 GPT 검토 자료 재생성.
6. 11도메인 × 4기능 × 4층 순회 검수.
### 4.4 GPT 교차 검토
`CROSSCHECK_STEP01.md`: 공통 지침 + 도메인별 블록(한 번에 하나씩). 답은 "기능 번호 | 층 | 문제 | 심각도 | 수정 제안" 표만. 결과는 문서 끝 기록표에 쓰고 Claude에게 전달. GPT 답은 후보이며 대조 후 반영합니다.

## 5. STEP02 도미노 추적 (v4, 구현 완료)
### 5.1 흐름 (3단계)
1. **증상 확인**: 기준 값과 이번 값이 다른 출력을 아래 카드에서 고릅니다(운전자 증상). 증거 폴라로이드는 우측 패널 `증거` 탭.
2. **역방향 추적**: E/E 판의 후보 노드를 누르면 측정과 비교가 `측정` 탭에 나옵니다. 판단은 "먼저 달라짐 / 같거나 늦음" 두 버튼. 모든 후보를 판단해야 다음 출력으로 넘어갑니다. 최초 편차(`data.first`)에서 멈춥니다.
3. **가설 정리**: 의심 구간 선택 → 가설마다 반박/보류 → (보류가 여러 개면) 먼저 시험할 가설 선택 → 다음.
### 5.2 설계 이유
- 이전 5단계 중 증상 확인·출력 선택은 증거에 답이 있어 정답 고르기였고, 후보마다 재생·측정·도장 3동작이라 클릭이 많았습니다.
- 실무의 "요구 위반 확인 → 격리 → 반증 증거로 가설 판단"과 맞춥니다.
- **측정 횟수 제한·별점 연동은 넣지 않았습니다**(난이도 피드백). 나중에 넣으려면 `measure()`에 횟수 상한 검사와 별점 계산만 추가하면 됩니다.
### 5.3 데이터 계약 (`features/board/DominoTrace.tsx` `CASES`, `game/scenarios.ts` `SCENARIO_META`)
- `CASES[case]`: `start`(증상 출력), `first`(최초 편차), `doms[]`(`id,label,zone,ref,run,unit,status,t,causes,ev`), `section{name,choices[]}`, `zoom{...}`, `req`.
- `status`: bad(기준과 다름, 시점 `t` 필요) / ok / tol. 함정 노드는 bad이지만 대상 출력보다 `t`가 늦은 것(결과).
- `SUBSYS`(EeTrace.tsx): 구간 탭의 안쪽 들여다보기 데이터.
- `SCENARIO_META.hypotheses[]`: `label`, `stage1`(반박 근거, 없으면 보류 대상), `truth`.
### 5.4 정답 힌트 방지 규칙 (모든 사건에 적용)
- 의심 구간 선택지는 형식과 길이를 맞춥니다("<제어기> <내용>" 형태, 20~30자). 정답 위치는 사건마다 달라야 합니다(현재 1/3/2번째).
- 참 가설이 항상 "보류"에 있지 않도록 시나리오마다 섞습니다. 가설 문구 길이·구체성을 맞춥니다.
- 증상 카드는 같은 형식의 기준 vs 이번 값만 보여 줍니다(해설 문구 없음).
- 세 사건이 모두 "제어기 SW 경계"가 답이면 요령으로 풀립니다 → 사건별 고장 종류를 다양화합니다(아래 7절).

## 6. STEP03 퍼즐 (설계 승인·구현 완료 2026-11-14)
### 6.1 3단계
1. **정상 기준 구성**: 요구사항을 읽고 빈칸에 조각을 넣어 정상 동작을 조립.
2. **연결·값 확인**: "연결 확인"으로 구성 검증 → 예시 입력 슬라이더로 칸마다 값 확인(기존 연결 확인+시험 조건 통합).
3. **시험 설계 확정**: 요구사항에서 입력 조건·기대값·허용 오차·관측 지점을 자동으로 가져온 시험 설계서 초안을 보고 "기준 확정". 직접 숫자 입력 없음.
- 시험 레벨·방법 선택은 STEP04 첫 단계(중복 방지).
### 6.2 레이아웃 (승인)
- 왼쪽 요구사항 열 제거. 우측 360px 패널 하나에 탭 `요구사항 / 정비소 노트 / 설계서`.
- 퍼즐 판은 넓은 스테이지. 하단 도크 150px(고양이 한 줄 + 예시 입력 슬라이더 + 연결 확인/기준 확정). 다음 버튼은 우측 360px 아래.
- 설계서는 모달 대신 패널 탭. 블록 `?` 도움말 버튼은 조각을 놓은 뒤에도 눌리게(겹침 순서 수정). 로드맵 칩 3개, 뒤로 자유·앞은 도달 후(현재 STEP03은 칩 이동 미연결 → 이번에 연결).
### 6.3 고장 종류별 UI (구조만 준비)
- 퍼즐 UI는 고장 종류에 따라 다릅니다. 현재 세 사건은 모두 SW 로직 → 기존 블록 조립 UI.
- E/E 구조 고장(통신 타임아웃, 신호 경로 오류 등)은 센서→제어기→버스→구동기 **신호 경로 선택 UI**로 설계합니다. 해당 사건을 추가할 때 함께 구현합니다.
- 사건 데이터에 `ref.kind`("logic" | "path") 같은 UI 분기 값을 둡니다.

## 7. 고장 시나리오 추가 가이드
### 7.1 다양화 원칙
세 기존 사건(구동 보정계수, 열관리 팬 PWM 어댑터, 제동 I/O 스케일)은 모두 제어기 SW 경계가 답입니다. 새 사건은 아래 범주를 섞습니다.
입력 처리(센서 필터·범위) / 출력 어댑터(PWM·스케일) / 통신(스케일·타임아웃·E2E) / 상태 전이(인터록·모드) / 파라미터·캘리브레이션 / 진단·보호(임계·복귀) / E/E 구조(전원·접지·커넥터) 등.
증상의 모습도 다양화합니다(주행 중, 정차 중, 출발 전/READY 불가, 충전 불가 등).
### 7.2 사건 하나를 추가할 때 손댈 곳 (검색 기준 `propulsion`)
| 파일 | 내용 |
|---|---|
| `game/runtime.ts` | `CaseId` 추가, 흐름 전이 |
| `game/scenarios.ts` | `SCENARIOS`(증상·증거·가설), `SCENARIO_META` |
| `features/board/DominoTrace.tsx` | `CASES`(노드·측정값·시점·구간 선택지) |
