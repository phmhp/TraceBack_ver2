## 0. 한눈에 보는 핵심 결론

1. **한 판에서 실제로 발생하는 고장은 2개**(구동 → 열관리). 제동 사건은 UI에서 진입하는 이벤트(`OPTIONAL_PROMPT`·`OPTIONAL_BRAKE`)를 보내는 코드가 없어 정상 플레이로는 나오지 않는다(`src/game/runtime.ts:333,337`, 호출처 없음).
2. **안내가 같은 화면에 4~5곳으로 흩어져 있다**: 단계 진입 모달(StageIntro) + 상단 폴더 줄(52px) + 하단 질문 dock + 고양이 한 줄 + (STEP04는) 상단 정보 바(83px). 위치·글자 크기·톤이 단계마다 다르다.
3. **질문 글자가 설명 글자보다 작다**: STEP02 질문 12.5px, STEP04 질문 13px인데 고양이 한 줄은 14px(STEP02·03)·12.5px(STEP04). STEP04 결과 표 본문은 **8.8px**.
4. **STEP01에는 완료 판정이 없다**: `다음 →`(`START_RACE`)이 항상 활성이고, `completedLessons`(`experiences.tsx:965`)는 기록만 하고 어디에서도 읽지 않는다. 아무것도 조작하지 않고 바로 주행으로 갈 수 있다.
5. **개발용 `정답 보기` 버튼 13곳이 운영 빌드에도 남아 있다**(`.secretSolve`, 화면 좌하단 2px 지점, 투명도 0.1). 전시 환경에서 우발적으로 눌릴 수 있다. DEV 조건 없이 렌더링된다(`experiences.tsx:2343,2635,2786`, `EeTrace.tsx:301,443`, `RefPuzzle.tsx:368,650`, `VerificationLab.tsx:468,875,1188,1404,1935`, `DominoTrace.tsx:405`). 이 중 현재 화면에 쓰이는 것은 `EeTrace.tsx:301`, `RefPuzzle.tsx:650`, `VerificationLab.tsx:1935`.
6. **STEP04의 화면 문구 2건이 실제와 다르다**: ①입력 조건 선택 안내문이 "관찰 신호를 비교하고 고르세요"라고 하는데 카드에는 관찰 신호 줄이 없다(오늘 카드 줄을 줄이면서 생긴 불일치). ②구동 사건의 SW 단위 시험이 **판정 불가(INCONCLUSIVE)**로 표시되는데, 같은 화면에서 가설은 '지지' 판정이 난다.
7. 전부 **문서 스크롤 0**(두 해상도). 국소 클리핑은 4곳(5.3절).

### 1.1 추격 격차(HUD) 값이 바뀌는 곳 — 실제 코드 기준
- 추리 단계(고장 대화·STEP02~04·수리): 매초 0.2m 감소(`main.tsx:141`, 오늘 0.08 → 0.2로 올림)
- STEP04 결과: `BENCH_RESULT`에서 최종 판정이 맞으면 +20m, 틀리면 −20m(`runtime.ts:305~314`)
- 정비소 노트(퍼즐 힌트) 첫 사용 −5m(`HINT`, `runtime.ts:410`)
- 구동 수리 후 최소 105m, 열관리 수리 후 최소 115m로 보정(`APPLY_REPAIR`)
- 첫 두 사건 완료 전에는 10m 아래로 내려가지 않음(`pursuitFloor`, `runtime.ts:199`)

### 1.2 플레이어가 다음 행동을 스스로 이해하기 어려운 지점
1. **STEP01 → 주행**: STEP01이 몇 개를 해야 끝나는지 알 수 없다. `다음 →`은 처음부터 눌린다. 무엇이 다음 단계(STEP02~04)에서 쓰이는지 STEP01 안에서 설명이 없다.
2. **주행 첫 화면**: 조작 안내가 4곳에 중복(도주 준비 카드, StageIntro 3줄, 하단 키캡 바, 화면 중앙 `브레이크 밟고 4를 눌러 D로!`). 반면 **"추월 구간에서 가속을 끝까지 밟으면 고장이 난다"**는 안내는 110m 지점의 표지판 카드 한 줄뿐이다.
3. **구동 사건 뒤 R 키**: 적색 신호 정지(550~612m) 후 **R 키를 눌러야 다시 달릴 수 있다**. 안내는 우상단 카드 한 줄 `정차 후 READY 재인가 · R 키로 재시동`과 키캡 바의 `R READY`뿐. 놓치면 차가 멈춘 채 움직이지 않아 막힌 것처럼 보인다(`experiences.tsx:1766` — `driveMission === "restart"`이면 속도를 0으로 고정).
4. **STEP02 로그 재생 전제**: `측정하기`는 `고장 당시 로그 재생`을 먼저 눌러야만 동작한다(`EeTrace.tsx` `measure`). 안내는 첫 사건에만 켜지는 코치 강조(`data-coach`)와 눌렀을 때 뜨는 말풍선뿐이다.
5. **STEP02 → STEP03**: STEP02 끝에서 고른 가설이 STEP03 상단에 `이전 결과: … | 의심 구간: …`으로 한 줄 표시되지만, STEP03에서 무엇을 만들고 그것이 STEP04에서 무엇이 되는지는 StageIntro 3줄과 설계서 모달에서야 나온다.
6. **STEP04 입력 조건 4종**의 차이: 오늘 카드 문구를 정리했지만(경계값 시험 · 입력 상한 등) 어떤 입력이 "고장 경로를 지나고 지나지 않는지"는 카드에 직접 드러나지 않는다(PASS가 나와야 알게 됨).
7. **수리 화면(REPAIR)**: 3초 자동 카운트다운. 플레이어 행동이 없고, 무엇이 수리됐는지는 한 줄(`repairLabel`)뿐이다.

  - STEP02~04에서 쓰는 지식 연결: 퍼즐 조각의 `정비소에서 본 곳: …` 문구(`RefPuzzle.tsx` `from` 필드)와 정비소 노트(퍼즐에서만) 외에 STEP01 내용이 되돌아오는 곳이 없다.

## 6. STEP 04 검증 — 코드 기준 구조와 정확성 점검

### 6.1 시험 입력 ↔ 정상 모델 ↔ 결함 모델 ↔ PASS/FAIL ↔ 가설 판정 ↔ 시각화
1. **입력**: `CASE_DERIVS`(583)의 카드 → `INPUT_EXEC`(605)가 STEP03 계약 실행(`execution`)의 자극·초기 상태를 바꾼다. 기대 출력은 `contractForInput`(615)이 **같은 입력으로 정상 모델을 돌려** 만든다.
2. **모델**: `simulate(caseId, tech, fixed, execution)`(`simModel.ts:191`)가 같은 모델 함수를 **두 번** 실행: `ref` = 고장 없는 정상 설계, `run` = 고장 주입(구동 `proc×0.45`, 열관리 `pwmOut=0`, 제동 `cmdOut×0.19`) 또는 수정 후. 두 모델에 **같은 입력·초기 상태·시간축**이 들어간다.
3. **PASS/FAIL**: `assessContractRun`(`simModel.ts:211`)이 계약의 수준별 관찰 신호가 정상과 2% 이상 다르거나 기대 출력이 허용 오차 밖이면 FAIL, 그 수준에 필요한 신호나 기대 출력이 없으면 INCONCLUSIVE, 아니면 PASS. **요구사항 판정이며 원인 판정이 아니다.**

### 9.3 STEP02·03 데이터가 실제 계산에 쓰이는가 (요청 5번)
- **STEP03 정상 기준**: 계약은 사건별 **상수**(`BASE`)다. 퍼즐에서 어떤 조각을 어디에 놓았는지, 예시 입력 슬라이더 값은 계약에도 계산에도 들어가지 않는다. `confirm`(`RefPuzzle.tsx` `buildVerificationContract`)은 **정답 배치일 때만** 계약을 만들고, 이때 가설 ID·가설 이름·의심 구간 **문자열**과 기대값 **문자열**(`spec.expect`)만 표시용으로 담는다. 따라서 STEP03은 "정상 기준을 만든다"는 학습 경험이지 STEP04 수식에 영향을 주지 않는다.
- **STEP02 고장 기록**: 자료함의 `최초 편차 신호`·`의심 구간`·핵심 신호 표는 STEP02 진행 저장(`tb-step02-progress-*`)과 `DominoTrace.tsx`의 사건 데이터(`CASES`, 각 노드 `ref/run/t`)를 **표시**한다. 시뮬레이션에는 들어가지 않는다. 표의 숫자(예: 60%→27%, 204→92 Nm, 가속 2.8→1.2)는 모델 계산이 아니라 **손으로 맞춘 상수**로, 현재 모델 값(60→27%, 204→92 Nm, 2.79→1.09 m/s²)과 일치하지만 일치를 자동 검증하는 테스트는 없다(`SCENARIO_META.review`에 "수치 일치 확인" 메모만 있음).

**(7) 같은 조건 반복 실행 시 일관성** — 위 11개 입력을 각각 2회 실행해 `levels` 전체(JSON)가 같은지 비교: **전부 동일**. 난수·시계 의존이 없다(`Math.random` 없음, dt 고정 5 ms). 재현성은 문제 없다.

**(8) 가설 선택이 모델을 바꾸는가** — **아니다.** `simulate`에는 가설 인자가 없고 결함은 사건별 **하나로 고정**(정답 원인)이다. 가설은 (a) 어떤 신호를 강조하는지(`lookAt`), (b) `judgeRun` 규칙표의 어느 줄을 볼지, (c) 질문 문구만 바꾼다. 즉 "가설을 검증하는 시험"은 **정답 결함 하나를 실행해 두고, 플레이어의 해석이 규칙표와 맞는지 채점**하는 구조다. 오답 가설(예: 팬 상태 전이 SW)을 **주입해 보는** 실험은 할 수 없다.

**(9) 시험 수준별 관측 신호와 판정 기준의 일치** — 오늘 추가한 테스트(`feedback-1112.test.mjs`)가 "보류가 나는 수준 = `hold` 데이터가 있는 수준, 판정이 나는 수준 = `decideAt`"을 사건·가설 8개에 대해 실제 모델로 검증한다(일치). 불일치 1건은 **표시**다: 구동 SW 단위 시험은 요구사항 판정이 `INCONCLUSIVE`(기대 출력 `mot`이 그 수준 신호표에 없음)인데 가설 규칙은 `proc`로 판정한다.

**(10) 정상·결함 비교의 기술적 타당성** — 교육용 **골든 모델 vs 변이 모델(back-to-back)** 비교로는 타당하나 다음 한계가 있다:
1. **기대값(오라클)이 정상 모델에서 나온다.** 사건 기본 입력의 204 Nm 등은 요구사항 숫자와 일치하지만, 다른 입력에서는 `contractForInput`이 정상 모델의 출력으로 기대값을 다시 만든다. 즉 PASS/FAIL은 "요구사항 대비"가 아니라 "정상 설계 대비"다. 요구사항을 모델과 독립된 식(예: `토크 = min(3.4·페달, 260)`)으로 두면 정상 설계 자체의 오류도 시험할 수 있다.
2. **시험 수준은 서로 다른 시험 환경이 아니라 같은 모델의 신호 보기(`VIEW`)다.** SW 단위/제어기 I/O/시스템 통합이 해상도·타이밍·버스 지연으로 다르게 계산되지 않는다.
3. **열관리는 폐루프가 끊겨 있다.** 계약 입력이 있으면 냉각수 온도를 입력 곡선으로 고정(`s.tc = rampInput(...)`)해서 팬이 멈춰도 온도·모터 온도·출력 허용이 변하지 않는다(실측: `tm` 85→85, `der` 동일). "팬 정지 → 온도 상승 → 출력 제한"이라는 증상 사슬은 시험 화면에서 재현되지 않는다(계약 없이 돌리는 옛 경로에는 폐루프 식이 있음, `simModel.ts:66~68`).
4. 차량 속도·가속도는 상수식(기어비 9, 바퀴 0.33 m, 질량 1800 kg)이고 제동 모델에는 ABS·접지 한계가 없다. 구동 한계(260 Nm)는 고정값이다.
5. 결함은 단일·상시·고정 크기이고 노이즈·지터·간헐 오류·통신 타이밍이 없다.
6. 열관리 시간 "8분(압축)"은 모델 시간 8 s에 이름만 붙인 것이다.

결론: **STEP04에는 실제 수치 계산이 있고, 입력 변경·반복 실행·PASS/FAIL이 계산에 의존한다.** 다만 ①가설이 모델이 아니라 규칙표만 바꾸고, ②수준별 가시성은 표로 정해지며, ③3D 시각화는 계산과 분리되어 있고, ④STEP02·03 데이터는 표시용이다. "시뮬레이션"이라는 표현은 "교육용 수치 모델 + 규칙 기반 판정"이라고 쓰는 것이 정확하다.

## 10. 추격 및 게임오버 규칙

### 10.1 현재 실제 구현
- **거리 계산(레이싱 중)**: 프레임마다 `gap += (플레이어 속도 − 경찰 속도)·dt/3.6`, `경찰 속도 = 속도<4km/h면 24, 아니면 clamp(68 + 0.12·속도, 68, 88)` km/h. 하한 `floor`(첫 두 사건 완료 전 10 m, 이후 0), 상한 220 m(`experiences.tsx:1841~1849`). 약 77 km/h(= 68 ÷ 0.88) 이상이면 격차가 벌어지고 그 이하면 줄어든다. 경찰차가 합류하는 조건은 주행 3초·45 m 이후(`policeHasJoined`).
- **고장 발생 후**: `FAULT_CUE`에서 레이스 화면이 내려가고(자차는 정지 상태, 상태값 거리·격차를 저장), 이후 STEP02~REPAIR 동안 **자차는 움직이지 않고** 격차만 줄어든다(`main.tsx:138~141`, `TICK_PURSUIT`: 초당 0.2 m — 오늘 0.08에서 상향).
- **체포 조건**: `policeGapMeters ≤ 0`이면 `CAUGHT`(`runtime.ts:248`, 레이스 중에는 `experiences.tsx:1900` 근처 `sim.gap <= 0`). 해수 추락도 `CAUGHT`. `pursuitFloor`는 `completedCases.length < 2`일 때 10 m(`runtime.ts:199`).
- **추리가 길어지면 게임오버 가능한가**: **정상 플레이에서는 불가능하다.** 첫 두 사건을 해결하기 전에는 하한 10 m라 `TICK_PURSUIT`로 0이 되지 않는다. 두 번째 수리(`APPLY_REPAIR`)가 끝나야 하한이 0이 되는데, 그 이후에는 추리 화면이 없다. (제동 사건은 진입 경로가 없다.) 따라서 현재 구조는 "학습 중 체포 방지 최소 거리 보장"을 이미 만족한다.
- **수리 후 복귀 복원**: `APPLY_REPAIR`가 `policeGapMeters = max(구동 105 / 열관리 115, 현재값)`로 올리고 같은 `raceDistance`·`raceElapsedSeconds`를 유지한 채 `CHASE_RESUME`(체크포인트 `harbor_entry`/`dock_approach`)로 이동한다. 속도는 복원하지 않고 0에서 시작(카운트다운 후 출발), 열은 사건별 초기값(구동 36, 열관리 66)으로 리셋(`experiences.tsx:1672`).
- **R 키·필수 조작**: 구동 수리 뒤 550~612m 적색 신호 미션: 612m에서 정지 후 `R`을 눌러야 속도 고정이 풀린다(`experiences.tsx:1766, 1860~1864`). 첫 주행은 P에서 시작해 `↓+4`(D단) 필요, 주행 중 P/R 변속 금지(인터락).
- **성공·실패 판정**: 성공 = 갑판 도착 후 `FINISH_ESCAPE`→`ENDING`(WANTED), 실패 = `CAUGHT`(체포 기록) → `RETRY_CHECKPOINT`(격차 최소 35/18 m 보장 후 체크포인트 장면으로).
- **STEP04 판정과의 연결**: `BENCH_RESULT`가 최종 원인 판정이 맞으면 +20 m, 틀리면 −20 m(`runtime.ts:305~314`). 정비소 노트 −5 m.

### 10.2 문제
1. 추리 중 격차 변화가 **수리 때 `max(105, 현재값)`으로 거의 지워진다.** 현재 격차가 105 m 미만이면 추리 시간과 STEP04 ±20 m가 결과에 영향을 못 준다(예: 격차 80 m에서 추리 → 수리 후 105 m).
2. 격차가 하한(10 m)에 닿아 있는 동안에는 "더 줄어든다"는 긴장감이 없다(HUD 숫자 10 m에 고정).
3. 하한 규칙은 `completedCases` 개수에 묶여 있어 사건 순서·개수 변경(신규 시나리오)에 민감하다.
4. 속도는 복원되지 않아 복귀 직후 경찰차가 24 km/h로 접근하는 구간이 생긴다(복귀 카운트다운 중 `allowed=false`라 격차는 고정).

### 10.3 권장
- 학습 중 체포 방지: **현행 유지**(하한 10 m). 하한 값을 상수화(`PURSUIT_FLOOR_DURING_INVESTIGATION`)하고 `completedCases`가 아니라 "추리 장면 여부"에 연결하면 신규 시나리오에도 안전하다.
- 긴장감: 하한 근처에서 HUD를 경고색으로 바꾸고 소리(오늘 추가한 사이렌)를 연결, 수리 후 복귀 최소값을 "현재값 + 유예"처럼 완화(아래 11장 보상과 함께 설계).
- **2일 내 가능**: 상수화·표시·경고색(낮음). 복귀 최소값 규칙 변경(중간, `runtime.test.mjs`·`feedback-1112.test.mjs` 확인 필요).

| 요구 | 구현 방식 | 근거·위험 |
|---|---|---|
| ③ DOM 기준 커서·클릭·드래그 표시 | 최상위 오버레이(`position: fixed`, `pointer-events: none`) 위에 커서 SVG를 두고 **프레임마다 `getBoundingClientRect()`로 대상 중심을 읽어** 보간 이동. 클릭은 대상 위 물결 효과, 드래그는 출발→도착 경로 선+조각 복제 이미지 | 해상도·레이아웃이 바뀌어도 매 프레임 다시 읽으므로 고정 좌표가 필요 없음. 대상 DOM이 없으면 그 단계 건너뛰고 말풍선만 표시 |
| ④ 화면 크기·레이아웃 변화 | `ResizeObserver` + 매 프레임 측정(rAF). 스크롤 컨테이너 안이면 `scrollIntoView` 후 측정 | 3D 캔버스 안 요소(정비소·주행)는 DOM이 아님 → 대상 제외(STEP02~04만 대상) |
| ⑤ 해설 단계 ↔ 정답 데이터 연결 | 해설 스크립트를 **사건 데이터에서 생성**: STEP02 = `DominoTrace.CASES[case]`(`start`, `first`, 각 노드 `t/status`, `section.choices`)와 `SCENARIO_META` 가설 규칙에서 "시점이 더 빠른 후보 = 유력" 순서를 계산(홍보 스크립트가 같은 방식), STEP03 = `REF[case].board/gaps/spares/req`, STEP04 = `QUESTIONS`·`LV_ANSWER`·`decideAt/hold`·`judgeRun` 정답키 | 사건을 추가해도 데이터에서 자동 생성되고 정답과 어긋나지 않음. 고정 영상·고정 좌표 불필요 |
| ⑥ 해설 중 입력 차단·중단·다시 보기 | 해설 레이어가 화면 전체를 덮는 투명 `pointer-events: auto` 막. `Esc`/`중단` 버튼 → 즉시 해제. 다시 보기 = 스크립트 인덱스 0부터. **해설은 컴포넌트의 상태 핸들러를 호출하지 않는다**(클릭 시늉만) | 정답 제출·`setStamps`·`putIn` 등 호출 금지 → 규칙을 코드 리뷰·테스트(상태 스냅샷 전후 동일)로 보장 |
| ⑦ 저장·복원·다시 풀기 | 오답 횟수 `wrongByKey`를 단계 진행 저장에 같이 저장(STEP03 `fails`도 저장 추가 필요), 해설 **열람 여부**는 저장하지 않는다(매번 다시 볼 수 있음). `resetStage` 시 `wrongByKey` 초기화 | STEP03 `fails` 미저장이 현재 결함(새로고침으로 오답 횟수 초기화) |
| 활성화 규칙 | `wrongByKey[현재 문제 키] ≥ 2` → `[해설 보기]` 버튼 활성(자동 실행 없음) | 버튼 위치: 질문 줄 오른쪽(공통 규칙) |

### 15.3 구현 난이도와 2일 내 최소 범위 (구현 검토 8)
- **공통 엔진(오버레이·커서·보간·말풍선 연동·중단/다시)**: 약 1일(중간). 대상 지정은 `data-demo="..."` 속성을 핵심 요소에 추가하는 것이 안전(현재 `data-node`는 도미노 노드 2곳뿐, 나머지는 클래스·텍스트로 찾음 → 클래스 변경에 취약).

- 이후 확장: STEP02(측정·도장 순서, 규칙이 있어 스크립트 생성 가능, 약 0.5일), STEP04(시험 수준·입력·판정 선택, 약 1일). 3개 사건 모두 **데이터 기반**이라 사건별 별도 제작 불필요.
- **2일 최소안**: 엔진 + STEP03 시범 + 오답 키 저장(`wrongByKey`, STEP03 `fails` 저장 포함). STEP02·04는 후속.

### 16.3 CSS 중복·충돌 위험 (실측)

- 권장: 새 공통 규칙은 **`/* tb-common */` 블록 한 곳**에 모아 마지막에 두고, 기존 규칙은 지우지 않는다. 수정 때마다 1440×900·1428×800 측정 스크립트를 실행(이번 감사에서 쓴 `audit.mjs`류).
