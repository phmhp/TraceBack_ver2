# 고장 사건 규칙 (R1~R15)

대상: 신입 사원 교육용 EV 검증 게임. 어렵게 꼬지 않되 실무에서 새 사건을 만나도 당황하지 않을 만큼 현실적이어야 합니다.

## R1 선택지 (정답 외)
- 오답은 **한 가지 이유로 분명히 틀려야 합니다.** "어쩌면 맞을 수도 있는" 선지를 두지 않습니다. 오답마다 반박 근거 문장(데이터로 확인되는 이유)이 있어야 합니다.
- 그렇다고 엉뚱한 선지(현실에서 말이 안 되는 것)도 금지입니다. 오답은 **실무에서 실제로 의심해 볼 만한 후보**여야 하고, 신입이 "아, 이건 이 값 때문에 아니구나"를 배우게 합니다.
- 정답과 오답은 **형식·길이·구체성을 맞춥니다**(예: 모두 "<제어기> <내용>" 20~30자). 정답 위치는 사건마다 다르게 둡니다.
- 비슷한 선지가 둘 이상 있으면 구분 기준(어떤 신호로 가르는가)이 화면에 드러나야 합니다.
- 적용 위치: STEP02 증상 카드, 의심 구간, 가설, STEP03 남은 조각과 함정 조각, STEP04 가설 판정, 최종 원인 카드, 수리 선택지.
## R2 하드웨어
- **진짜 원인은 SW(또는 SW 설정·통신·시퀀스)여야 합니다.** HW 원인 사건은 만들지 않습니다(수리하고 다시 달리는 스토리와 맞지 않음).
- HW 가설은 "SW 시험으로 무죄를 확인(반박)하거나 이 수준에서는 판단 보류"가 되는 **오답 후보로만** 사건당 0~1개 둡니다.
## R3 말투·표기
- 해요체 또는 합니다체. 반말, 감탄, 유아어, 이모지 금지. 한 줄은 짧게. 단어 중간 줄바꿈 금지.
- 캐릭터 대사도 같은 규칙(질문은 "~인가요?").
- "교육용 단순화", "실제 아님" 같은 문구 금지. 답은 버튼으로 고르게(서술형 금지).
## R4 증상
- 운전자가 **체감하거나 계기판에서 보는** 것이어야 합니다. 시점·트리거·지속성을 한 문장으로 적습니다(`FAULT_CASE_SELECTION_V3.md` 4절 분류).
- STEP02 증상 카드는 `기준 vs 이번` 값만 같은 형식으로 보여 줍니다. 카드 3장 = 실제 증상 1 + **영향 없는 출력 2**(기준=이번). 결과로 따라 달라진 출력(계기판 등)을 오답 카드로 쓰지 않습니다(모호함).
## R5 수치 일관성
- 숫자는 사건 시트에서 한 번만 정의하고 모든 화면이 같은 값을 씁니다. 관계식으로 검산 가능해야 합니다(예: 60% × 0.45 = 27%).
- 단위, 소수 자리, 허용 오차를 시트에 적습니다.
## R6 시점과 트리거
- 고장이 항상 같은 방식(추월 구간 가속 등)이어야 한다는 편견을 두지 않습니다. 시동 전, 정차, 출발, 순항, 제동, 조향, 연속 부하, 환경, 시간 경과, 이벤트 연쇄, 무작위·간헐, 트리거 없음 중에서 고릅니다.
- 지속성: 영구 / 래치 / 간헐. 간헐이면 "재현 입력을 고르는 것"이 학습 요소가 되도록 STEP04에서 재현 조건을 다룹니다.
## R7 STEP02 노드·가설
- 최초 편차 노드와 진짜 원인 가설은 서로 일치해야 합니다.
- **함정 노드**(비정상이지만 원인보다 늦게 달라지는 결과)를 사건당 1~2개 둡니다.
- 가설은 3~4개, 진짜 원인 1개, 참 가설이 항상 같은 위치·같은 판정(보류)에 있지 않게 섞습니다. 사건마다 고장 범주(분류 A~L)가 달라야 합니다.
- 반박 근거(`stage1`)는 측정값으로 확인되는 문장이어야 합니다.
## R8 STEP03 퍼즐 UI
- 고장 범주에 맞는 UI를 씁니다: SW 로직 → 블록 조립. 통신·E/E 구조 → 신호 경로 선택(설계 예정). 상태 전이 → 상태 전이도 채우기(설계 예정).
- 남은 조각의 함정은 "같은 블록, 다른 표 값" 또는 "다른 기능 블록"처럼 **값을 비교하면 구분되는** 것이어야 합니다.
- 요구사항 문장은 정상 기준 한 문장 + 수치. 시험 설계서의 기대값은 요구사항에서 자동으로 나옵니다.
## R9 STEP04 시험 수준
- 사건마다 가설을 "결정적으로 가르는 수준"이 다르게 분포해야 합니다(`decideAt`). 다른 수준에서 못 가르면 `hold`에 이유와 다음 수준을 적습니다.
- 시험 결과(통과/실패/판정 불가)와 가설 판단(지지/반박/보류)은 별개로 표시합니다.
## R10 수리 선택지
- 3개: 원인 제거(정답) / 증상만 가리는 조치(왜 새 문제가 생기는지 근거) / 무관한 조치(왜 효과가 없는지 근거). 정답 위치는 섞습니다.
## R11 진단 채널
- 사건 시트에 "진단 채널"을 적습니다(DTC, 경고등, 프리즈 프레임, 진단이 못 잡은 이유). 경고등이 안 켜지는 것도 정보이며 "경고등 없음 = 정상"이라는 오해를 학습 요소로 쓸 수 있습니다. 상세는 `DIAGNOSTICS_AND_FUTURE.md`.
## R12 안전·표준 예약 필드
- 지금 게임은 기능안전 관점을 다루지 않지만, 사건 시트의 "확장 필드"(안전 목표, 심각도 등급, FTTI, 안전 메커니즘, 안전 상태, 관련 AUTOSAR 모듈)를 비워 두지 말고 아는 범위에서 적습니다. 후속 게임(ver2 등)에서 그대로 씁니다.
## R13 정비소 학습 연결
- 사건마다 관련 정비소 기능(도메인·기능 번호, 4층 중 어느 층)을 시트에 적고 오픈북 노트(`BOOK`)와 연결합니다. 사건이 끝나면 "배운 원리"가 정비소 내용과 이어져야 합니다.
## R14 에셋
- 새 부품 이미지·증거 사진은 사건 시트에 목록으로 적고, 이미지 프롬프트 규칙(한 번에 한 장, 파일명·폴더 명시)을 따릅니다. 기존 에셋을 우선 재사용합니다.
## R15 검수
- 구현 후 `CHECKLIST.md`의 화면별 대조를 모두 합니다. 숫자·문구가 시트와 다르면 시트를 고치거나 화면을 고쳐 한쪽으로 맞춥니다. UI 전수 검수(가려짐·잘림·줄바꿈)는 `DESIGN_DECISIONS_V3.md` 10절 절차를 따릅니다.

## R16 차량 거동 영향 (2026-11-14 추가)
- 고장은 도주 상황에서 **차량 거동(주행·제동·조향·출력·시동)을 바꿔야** 합니다. 표시·편의 기능만 틀리고 달리는 데 지장이 없는 사건은 만들지 않습니다(예: 속도계 오표시는 `fault-cases/speedo.md`에 보관만).
- 같은 고장 범주(구성·수치·단위 등)를 가르치고 싶으면 거동에 영향을 주는 사건으로 설계합니다(`FAULT_CASE_SELECTION_V3.md` 5.0절).

## R17 레이싱 영향·추격 연동 (2026-11-14 추가)
- 사건 시트는 고장이 **레이싱에서 플레이어가 할 수 있는 일**을 어떻게 바꾸는지 정의합니다: 이동 가능 여부, 가능한 방향, 속도 상한, 조작 가능 범위(가속·제동·조향), 시동 상태, 충돌 위험.
- 이 영향은 추격차 변화와 연결합니다(`../RACING_DESIGN_IDEAS.md` 연동표). 예: 정지하면 추격차가 줄고, 후진만 가능하면 경찰 쪽으로 이동하며, 제어 불가 가속이면 충돌 위험이 커집니다.
- 추리(STEP02~04) 중에는 시간 배율을 낮춰(슬로 타임) 플레이어에게 충분한 생각 시간을 줍니다(배율은 레벨 난이도로 조정).

## R18 수치 표기 (2026-11-15 추가)
- 화면의 모든 수치·단위는 코드 표기(`code`)로 보여 준다. 기준은 회색, 이번 값은 붉은 계열로 구분한다.

## R19 디렉션 3요소 (2026-11-15 추가)
- 단계 전환·단계 시작 안내는 `Directive`로 3문장을 따로 보여 준다: 방금 한 일 / 이번 단계에서 할 일 / 하는 방법. 말하듯 쓰고 AI 말투(정의형 나열)를 피한다.

## R20 한 화면 한 결정 (2026-11-15 추가)
- 한 화면의 선택지는 3개 이하, 입력은 항상 하단, 우측 패널은 읽기 전용 기록이다. 같은 단계 안의 레이아웃은 통일한다.

## R21 용어 통일 (2026-11-15 추가)
- 도미노: 영향을 줬어요 / 영향을 주지 않았어요, 후보에 올려요 / 후보에서 빼요.
- 실험대: 원인으로 보여요 / 원인이 아니에요 / 아직 몰라요. 시험 결과는 통과 / 실패 / 판정 불가. "지지·반박·보류"는 화면에 쓰지 않는다.
- 실험대에는 수리 고르기·재시험 단계가 없다. 원인 제거 확인이 통과하면 수리를 적용하고 주행으로 돌아간다.

## R22 가설 태그 (2026-11-15 추가)
- 모든 가설 카드에 원인 종류 태그를 단다: `SW 로직`, `SW 설정`, `통신`, `센서`, `HW` (`HYP_TAG`).

## R23 퍼즐 유형 (2026-11-15 추가)
- 사건 시트 7절에 UI 유형(블록 조립 / 신호 경로 선택 / 상태 전이도 채우기)과 정비소 연결 영역(시스템·E/E·도메인·기능 중 어디인지)을 적는다. 세 유형이 모두 최소 한 사건에 쓰이도록 사건을 배분한다.

## R8 보충: 퍼즐 UI 유형 배분 (2026-11-15)
| 유형 | 모드 | 쓰는 사건 | 수준 |
|---|---|---|---|
| 블록 조립 | `ui` 없음(기본) | 구동·열관리·제동·회생 | SW 로직 |
| 신호 경로 선택 | `ui: "path"` | C04 변속 폴백(`gear`) | 시스템·E/E |
| 상태 전이도 채우기 | `ui: "state"` | C01 시동 불가(`ready`) | SW 상태기 |
- 새 사건을 만들 때 위 표에서 가장 맞는 유형을 고르고, 시트 7절에 적는다. 도메인 수준 사건은 아직 없다(다음 후보: 충전 또는 열관리 도메인 간 협조).
