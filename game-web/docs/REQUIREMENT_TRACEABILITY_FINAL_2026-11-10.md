# 원문 요구사항 전수 추적표

## 사용법과 상태

첨부 프롬프트의 PART A~K를 원문 순서대로 항목화했다. 같은 의미의 세부 문장은 하나의 행 안에서 세미콜론으로 모두 보존했고, 충돌 시 최신 PART H와 K를 우선했다. 원문은 삭제하지 않으며 구현 시 각 ID를 테스트·캡처·커밋에 연결한다.

- `설계 반영`: 현재 설계 문서에 반영됨.
- `구현 대기`: 사용자 승인 후 구현/검증 필요.
- `조사 완료`: 현재 구현 상태 확인됨.
- `보존·대체`: 원문 보존, 최신 결정으로 활성 범위에서 대체됨.
- `제외 확정`: 최신 결정으로 게임 독립 경로에서 제외됨.

### 최신 피드백과 원본의 충돌·해결

1. **M-02 vs A-2.5/B-6/K-5.2의 ‘우측 독립 스크롤’**: 최신 사용자 요청인 *스크롤 금지*를 우선한다. 중앙 도미노·우측 증거·하단 메모판은 유지한다. ‘사건/증거 3열’은 **우측 증거 영역 안의 카드 3열**로 해석한다. 카드가 넘치면 내부 스크롤 대신 페이지 없는 단계별 카드 교체/필터/확대 팝업을 쓴다. 만약 사용자가 ‘화면 전체 3열’을 뜻했다면 이 항목만 재배치 검토한다.
2. **M-03 vs 도미노 물성·재생 연출 요구**: 역추적의 교육 핵심과 도미노 보드 자체는 유지. **별도 재생 팝업과 가짜 기울기 애니메이션만 제외 제안**. 원본 기능 삭제 금지 원칙상 실제 제거는 사용자 승인 후. 품질 있는 역방향 재생은 선택적 후속 과제이지 P0 전제 아님.
3. **M-07 vs B-7.4/K-7.3의 좌 조건·중 모델·우 결과·하 그래프**: **동일한 네 기능을 보존하되 항상 동시에 펼쳐 두지 않는다.** 조건/결과는 접힘·단계 교체, 그래프는 모니터링 탭에서 크게 제공. 원본 배치와의 차이는 의도적 최신 UX 변경이며 구현 전 승인 대상.
4. **M-12 vs 이전 77:23 폭 제안**: 77:23 삭제. 3:4는 **조작 캔버스의 가로/세로 비율**, 화면 전체 폭 점유율이 아니다. 1054×723에서 가로 3:세로 4인 캔버스의 실제 폭은 화면 높이에 의해 제한되므로, 나머지 공간에 맥락·조작·결과를 둔다. 모든 3D/그래프의 픽셀 프레임을 무조건 3:4로 강제하는 것은 가독성 손해 가능성이 있어 **주요 직접 조작 영역**에 우선 적용하고 다른 데이터 뷰는 사용자 승인으로 정한다.
5. **SW-only 정책 L-3.1~3**: 모든 근본 원인은 SW. 이전 대화에 있었던 팬 모터 고착·유압 누설 근본 원인 설명은 **현행 활성 시나리오로 사용 금지**. 열관리=PWM 출력 SW 실행 순서, 제동=I/O 이중 스케일링이라는 원본 추적표 기준 유지. 물리 부품은 반응/관찰 대상으로만 사용한다.

## M-1. 공통 UI 계약

- 화면은 한 번에 한 행동 중심. 고정 헤더·단계 표시·도메인/탭·핵심 캔버스·짧은 피드백. 화면 전환 시 상태 보존(L-6.3). 완료 단계 복귀, 미해금 잠금(L-6.1~2).
- 세 관점의 **외부 프레임은 완전히 동일**(A-2.1~3). 관점마다 내부 그림만 교체. `전체보기`는 도메인 탭의 최초 상태이지 네 번째 관점이 아니다.
- 공통 버튼 크기·위치·번호·잠김/가능/진행/완료 상태를 고정. OFF에서 시작해 조건 충족 후 순차 활성, HV/LV/CAN/센서·제어/기계 토크 구분. 실제 모델·시각 모델·교육용 연출을 구별.
- **3:4 상호작용 캔버스**: CSS 예 `aspect-ratio: 3 / 4; height: min(약 65vh, 사용가능높이); width: auto; max-width: 100%`. 수치는 예시이며 실제 높이는 헤더·푸터를 뺀 available height에서 계산. 박스 바깥에 질문/짧은 버튼/상태를 배치. 화면 전체/내부 스크롤 금지 요구는 STEP02·04에 절대 적용.
- 사용자가 직접 조작한 증거·퍼즐·시험 조건·실행 기록은 탭/팝업 이동 후 복원. 오픈북은 현재 도메인/관점/노드에 맞춰 Vehicle·E/E·SW·요구사항을 보여주되 정답 공개 금지.
- 표준은 교육 참조: SWE.4/5/6, SYS.4/5, VAL.1 구분. 임베디드·SIL/PIL/HIL은 검증 수준이 아니라 실행 환경/방식. HW 전용 탭·독립 HW 검증 수준/퍼즐 금지. 기법과 수준은 별도 축. 준수/인증 도구로 홍보 금지.
- **UI-RULE-01 최신 설계 보완(구현 순서 불변)**: 1536×960(16:10) 게임 영역을 기준으로 헤더는 `로고 10% | 단계명·진행도 30% | 여백 40% | 추격 거리 20%`를 Grid/Flex로 배치한다. 헤더 아래에는 폴더 본문과 이어지는 `이전 | 다음` 단계 이동 탭을 나란히 두며, 활성 탭은 앞면·비활성 탭은 뒷면처럼 보이게 한다. 탭과 최대 2줄 소제목 본문은 배경·테두리·그림자·연결부 토큰을 공유하되 첨부 노란 폴더의 **형태만** 참고하고 색상·패턴은 현재 화면 토큰을 유지한다. 본문은 남은 높이를 최대로 쓰고, 하단은 고양이 안내 80%와 완료 조건 기반 `다음으로` 20%로 고정한다. 상단 탭은 단계 이동, 하단은 현재 단계 진행으로 역할을 분리하며 float/absolute로 본문을 덮지 않는다. 1054×723에서는 같은 상대 구조를 반응형으로 축소하되 잘림·과도 여백·스크롤을 허용하지 않는다.
- **소제목 데이터 계약**: 1줄은 현재 행동, 2줄은 `이전 단계 산출물 | 현재 집중 대상`이다. STEP01 `차량 기능이 어떤 부품과 신호를 거쳐 동작하는지 확인하세요.` / `학습 대상: {도메인} | Vehicle/System · E/E · Control SW`; STEP02 `관찰한 이상 증상에서 출발해 고장 원인 후보를 좁히세요.` / `출발 증거: {실제 증상} | 추적 대상: 신호·제어 경로`; STEP03 `고장 원인을 구별할 시험 조건과 정상 기준을 완성하세요.` / `이전 결과: {STEP02 추적 결과} | 의심 구간: {실제 선택 후보}`; STEP04 `의심한 SW를 시험·수정하고 정상 차량과 결과를 비교하세요.` / `이전 결과: 테스트 설계서 | 비교: 정상 기준선 ↔ 수정 후 차량`. 중괄호 값은 실제 상태·저장 기록에서만 가져오며, STEP03의 기존 3~4줄 설명은 이 두 줄로 압축하고 상세 설명은 고양이 안내/기존 도움말로 이동한다.

## M-2. STEP 01 — 차량 도메인 원리

**최초 진입 상태: `[전체보기]` 선택, 차량 OFF.** 전체 차량과 도메인 위치 핀을 표시. 도메인 선택 시 해당 기능만 강조하되 외부 레이아웃은 불변. 원본 구동 대표 경로 OFF→READY→인터록/HV→D→페달→APS→VCU→인버터→모터→바퀴의 조건·신호를 보존한다.

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ 차고 · 차량 도메인 원리                       단계 01   [오픈북]     │
├─────────────────────────────────────────────────────────────────────────┤
│ [● 전체보기] [구동] [제동] [조향] [전원] [변속·주차] [열관리] [현가]│
├──────────────┬───────────────────────────────┬──────────────────────┤
│ 관점         │      전체 차량 3D             │ 선택한 도메인·기능    │
│ [Vehicle]    │      (처음엔 전체 도메인 핀)   │ 전체보기: 도메인 안내 │
│ [E/E]        │      도메인 선택 후 강조      │ 도메인 선택 후 기능  │
│ [Control SW] │      [논리/물리/겹쳐]         │ 현재 기능 짧은 설명  │
├──────────────┴───────────────────────────────┴──────────────────────┤
│ [① 전원] [② READY] [③ D단] [④ 페달]   잠김/가능/완료 고정 슬롯 │
│ [정상 입력] → [신호 전달] → [제어 판단] → [부품·차량 반응]     │
└─────────────────────────────────────────────────────────────────────────┘
```

- **Vehicle/System**: 차량 위치·직접 조작·실제 모델 반응. **E/E**: 포트 앵커, 논리/실제/겹쳐 보기, 물리적 합리성, 선행 조건 후 전달. **Control SW**: 쉬운 한글 입력→판단→출력, 선택 기능의 관련 블록만. 동일 상태와 값 공유.
- 초기 화면에서 `전체보기`로 돌아오면 도메인 강조만 해제; 진행 중인 입력/학습 상태 초기화 금지.
- P2는 기존 3D의 위치/크기/회전/피벗·배선 정밀화; 신규 모델 제작보다 재사용 우선.

- **3열 카드**는 고정된 보이는 슬롯. 증거가 6장 초과하면 `다음 증거 묶음`으로 **내용 교체**하고 슬롯 크기는 고정. 내부/페이지 스크롤 0. 카드 상세는 한 화면 내 팝업, 긴 텍스트는 줄이거나 단계별 펼침.
- 카드 Hover 정상/이상 짧은 설명, 클릭 시 메모 추가. 증거→출력 요소→상류 후보 활성화→측정→동일 시간 비교→근거 도장→최초 편차 구간→경쟁 가설 보류. 미측정 값을 생성하지 않음.
- **도미노 재생 팝업은 이번 안에서 제외**. 대신 보드 위에서 출력→상류 방향의 `역추적 경로 강조`(방향 화살표·순차 색 변화)만 사용. 장식적 좌→우 도형 넘어짐 금지. 기존 보드·메모·실 연결은 유지.
- 최초 편차 ≠ 확정 원인. SW 내부와 입력 경계 등 경쟁 가설은 STEP04까지 유지. HW 자체를 최종 근본 원인 후보로 확정하는 흐름은 L-3 SW-only 정책에 맞춰 재검토해야 함. 기존 데이터의 가설 명칭과 교육적 반례는 보존하되 최종 활성 정답은 SW.

## M-6. STEP 04 — 스크롤 0, 질문 중심의 하나의 검증 작업대

### M-6.1 전체 프레임

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ 시뮬레이션 검증  사건명                [시험 계약 다시 보기] [도움말]│

│ [SW 로직] [제어기 I/O] [부품·차량] [모니터링]                        │
├──────────────────────────┬───────────────────────────────┬───────────────┤
│ 현재 행동 카드           │      3:4 직접 조작 캔버스     │ 이번 행동 결과 │
│                          │                               │               │
│ ① 지금은 무엇을 확인?    │       [동일 도식/3D/        │ 실행 전: 대기 │

│                          │                               │ 값 1~3개      │
│ [조건 바꾸기]            │                               │               │
│ [측정점 고르기]          │                               │ [자세히 보기] │
```

- **오른쪽에 범위·조건·관찰·실행을 한꺼번에 나열하지 않는다.** 처음에는 `질문+추천 행동`만, 클릭하면 필요한 선택지만 등장. 시험 범위는 쉬운 행동 카드(예: “SW만 실행해 보기”, “연결된 시스템에서 확인”)로 선택하며 기술적 수준/환경은 `왜 이 시험?` 도움말에 작게 설명.
- 자유 탐색은 허용하되, 튜토리얼은 한 행동씩 권유. 무효 시험을 선택해도 즉시 실패 처리 대신 **“이 시험으로는 이 값을 볼 수 없어요. 무엇을 바꾸면 될까요?”** 안내.
- 정상/사건 실행은 동일 입력 조건을 유지하고, 조건을 바꾸면 비교 기록을 새 시험으로 분리. 입력·관찰·실행·결과는 탭 이동 후 유지. **스크롤은 페이지·패널·팝업 모두 금지**: 넘치는 설명은 요약+다음 카드로 전환.
- 중앙의 직접 조작 박스는 **가로:세로 3:4**. 시각화 유형상 필요한 3D 뷰/모니터링은 동일 외곽 3:4 박스 안에서 맞춤/확대/탭 전환으로 처리. 가로로 긴 그래프가 필요하면 내부 차트만 넓게 사용하되 외곽 조작 영역 비율 유지.

|---|---|---|---|

- **SW 탭은 STEP03 퍼즐의 같은 블록 이미지, 같은 순서, 같은 연결, 같은 위치**를 기본값으로 사용. STEP03은 빈 슬롯/정상 기대, STEP04는 읽기 전용 완성도식 위에 실제 실행값/편차 표시. UI를 새로 그려서 학습 연속성을 끊지 않는다.
- 질문은 사건 데이터에 따라 교체: 열관리 “팬을 켜라는 조건에서 SW가 출력 명령을 만들까?”, 제동 “브레이크 요청이 출력 포트까지 올바른 크기로 전달될까?”, 통신 “보낸 명령이 정해진 시점에 수신될까?”. 질문 자체는 정답을 암시하지 않음.

### M-6.3 모니터링 탭: 세 표현 모두 지원하되 데이터 기반으로 단계 구현

| 관찰 데이터 | 기본 시각화 | 적합한 고장/질문 | 구현 접근 |
|---|---|---|---|
| 연속 수치(토크·속도·온도·압력 요청) | **선그래프**, 정상/사건 동일 시간축·단위 | 계산/보정/스케일링 | 기존 `OverlayGraph` 재사용, 타입별 축/범례 개선 |
| 이산 상태(READY·D·팬 ON/OFF·제어 모드) | **계단형 타임라인** 우선, 필요 시 작은 상태 전이도 | 조건/경계/상태 전이 오류 | 기존 시간 샘플을 계단 그래프로 표시. 복잡한 상태 전이도는 후순위 |
| 통신·인터페이스 이벤트(CAN 송신/수신·누락·지연) | **이벤트 타임라인** 우선, 필요 시 송수신 시퀀스 | 메시지 누락·지연·순서 오류 | 실제 모델의 이벤트 타임스탬프·송수신 ID가 있을 때만 표현. 데이터 없으면 허구 이벤트 생성 금지 |

**왜 세 가지를 다 쓰나?** 그래프 하나로는 상태 전이의 순간, 이벤트의 순서·누락을 충분히 보여주기 어렵기 때문. **정답 유출 때문이 아니라 표현과 데이터의 문제**다. 비교 시 최초 편차 지점을 표시하더라도 원인 확정은 가설/시험 범위/추가 관찰을 거쳐야 한다. 구현 난이도는 선그래프(기존 재사용) < 계단 타임라인(상대적으로 작음) < 실제 이벤트 모델/시퀀스(데이터 구조에 따라 큼). 우선 기존 사건에 필요한 표현부터 추가하되 세 유형을 **요구사항에서 삭제하지 않는다**.

```text
[모니터링]  질문: 어느 지점부터 달라졌을까?
┌───────────────────────────────────────┐
│ 보기: [연속값] [상태] [통신 이벤트]    │
│                                       │
│ 연속값: ┄ 정상  ━ 사건                │

│   27 ┤━━━━━━━                        │
│      └────────→ 시간                 │
│                                       │
│ 상태: READY ───┐  D ─────────       │
│                └───────              │
│                                       │
│ 이벤트: 송신 ●──●──●                 │
│         수신 ●──×──●  (누락 예시)    │
└───────────────────────────────────────┘
※ 위 값/이벤트는 표현 예시. 실제 사건 데이터와 다르면 표시하지 않는다.
```

### M-6.4 초보자용 F5~F9 통합 플레이 루프 (한 번에 하나씩)

**장면 1 — 질문을 받는다.**

```text
🐱 “페달은 제대로 들어오는데, SW 계산이 잘못된 걸까?”
[SW만 실행해 보기]   [다른 방법 살펴보기]
```

- 추천 카드를 누르면 STEP03 계약의 입력/초기 상태가 **미리 채워진다**. 플레이어는 바로 실행하거나 입력을 바꿀 수 있다. 기술 용어는 작은 `왜 이 시험?`에서 설명.

**장면 2 — 무엇을 볼지 고른다.**

```text
🐱 “어디를 보면 둘을 구분할 수 있을까?”
[입력값 ●] [SW 처리값 ●] [토크 명령 ○]
선택한 곳은 STEP03과 같은 도식에 핀으로 표시
[이 값으로 실행 →]
```

- 선택 불가능한 값은 잠금+이유 표시. 너무 많은 신호를 한꺼번에 요구하지 않는다.

**장면 3 — 정상과 사건을 실행한다.**

```text
[▶ 정상 실행] → “기준값을 저장했어요.”
[▶ 사건 재현] → “같은 조건으로 다시 돌려볼게요.”
```

- 버튼은 같은 자리에서 상태가 바뀐다. 모델 실행 중 시각적 진행 표시, 실제 결과만 표시. 정상과 사건을 서로 다른 조건으로 돌리면 비교 불가 이유 안내.

**장면 4 — 결과를 쉬운 말로 읽는다.**

```text
┌──────────── 이번 시험 ────────────┐
│ 입력 페달: 정상 60% / 사건 60%   ✓ │
│ SW 처리: 정상 60% / 사건 27%    ! │
│                                  │
│ “같은 입력인데 SW 처리부터 달라졌어요.”│
│ [왜 다를까?] [모니터링에서 보기]    │
└──────────────────────────────────┘
```

- 시험 자체의 결과는 **PASS / FAIL / INCONCLUSIVE**로 기록. 관찰할 수 없는 값은 0이 아니라 **측정 불가**. 데이터의 첫 편차는 설명하되 원인 확정으로 표현하지 않음.

**장면 5 — 가설을 판단한다.**

```text
🐱 “이 결과가 어느 가설을 더 뒷받침할까?”
[가설 A: 지지 / 반박 / 아직 모름]
[가설 B: 지지 / 반박 / 아직 모름]
[근거로 선택한 관찰값: SW 처리 60% ↔ 27%]
[추가 시험] [판단 제출]
```

- 가설은 **HIGH / LOW / OPEN**으로 별도 기록. ‘시험 FAIL’이 ‘가설 A 정답’이라는 뜻이 아님. **아직 모름**은 정당한 답. 근거 부족이면 추가 시험으로 돌아가며 이미 얻은 증거 보존. 오답에는 이유와 수정 행동 제시.

**장면 6 — 수리 카드를 고른다.**

```text
🐱 “어디를 어떻게 고치면 될까?”
[실제 SW 원인 후보] [다른 조치] [증거 더 모으기]
[결정적 근거 선택] → [수리 요청]
```

- STEP02에서 남은 가설과 STEP04 측정 근거를 연결해 최종 원인 선택. 정답 카드는 시나리오 데이터에서 오며 **SW 근본 원인**으로 한정. 수리 카드 선택은 근거를 갖춰야 활성화.

**장면 7 — 같은 조건 재시험과 차량 회귀.**

```text
🐱 “고친 뒤에도 같은 조건에서 제대로 될까?”
[수리 전 조건 자동 불러오기] [▶ 같은 시험 재실행]
[정상 기준 vs 수리 후 비교]
[▶ 차량 전체 회귀 주행]
[고객에게 결과 보여주기 →]
```

- 로컬 SW 계산 복구와 **차량 전체 요구사항 회복**을 구분. 최종 한 장 고객 카드에는 `증상/선택 가설/결정적 근거/조치/동일 조건 결과/회귀 결과/남은 한계`만 자동 요약. 사용자가 직접 쓰는 보고서 숙제 금지.

### M-6.5 탭 이동과 데이터·검증 계약

```text
NormalReference
    ↓
InvestigationResult  (증거·최초 편차 구간·경쟁 가설)
    ↓
ExperimentPlan / VerificationContract
  (목적·근거 요구·초기/입력·기대·관찰·반례·비교 조건·한계)
    ↓
VerificationRun[]
  (범위/환경·정상·사건·동일 시간축·관찰 가능성·결과)
    ↓
HypothesisAssessment[]  (HIGH / LOW / OPEN, 근거)
    ↓
RepairAction → RetestRun → SystemRegression → ResolutionSummary
```

- STEP02에서 관찰하지 않은 증거를 STEP03/04가 소급 생성하지 않는다. STEP03 계약의 조건·기대값을 STEP04가 임의 변경하지 않는다. 시험마다 새 입력을 선택할 수 있으나 원본 계약과의 차이를 기록한다.
- 정상 기능, 요구사항, 경계값, 조건 조합/전이, 지연·누락·범위 초과, 인터페이스, 가설 분리, 수리 후 회귀를 데이터 기반 시험 행동으로 다룬다. **독립 신규 미니게임은 만들지 않는다.**
- 실제 근본 고장 위치에 주입하고 내부→I/O→시스템 출력으로 전파한다. 최종 출력값만 위조해 원인을 흉내 내지 않는다. 시간·단위·관찰 범위와 실행 환경을 표시한다.
