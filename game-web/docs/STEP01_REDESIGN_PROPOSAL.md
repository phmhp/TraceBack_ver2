### 2.4 박스 최소화 규칙
- **카드 표면(크림 배경+테두리)은 3곳에만**: MISSION 카드(D), 팝업, 결과/영수증형 표. 나머지(여정 점, 레일, 라벨, 값 칩)는 **무대 위에 직접** 그린다(잉크 라벨 + 약한 스크림).
- 우측 정보 패널·하단 설명 패널처럼 **상시 열린 읽기 전용 박스는 없앤다**. 정보는 조작 후 공개(§2.5).

### 2.5 점진적 공개 (행동 → 정보)
정보는 `행동 직전에는 숨기고, 행동 결과로 연다`: 예) 신호 이름·값은 입력을 넣은 뒤에야 노드에 나타남. 기능 설명은 `?`(기본 접힘).

### 2.6 질문 카드(플립카드)
```
  [MISSION 02 · 3/4]  ●●○○                 ← 점 = 현재 기능의 질문 수, ✓ = 완료
  Q. 페달 신호를 받아 CAN으로 내보내는 제어기는 어디일까?
  ─ 조작: 도면에서 노드를 눌러 확인 ─
  [힌트 ?]                    [다음 질문 →]  ← 완료 시 활성
```
- 전환: 카드가 **세로축으로 180° 플립 0.25 s**(prefers-reduced-motion이면 페이드). 페이지 전환 없음.
- 완료 질문은 카드 헤더 점에 ✓. **이전 질문으로 돌아가 다시 풀기 가능**(저장).
- 질문 1개 = 조작 1개(클릭/길게 누르기/드래그/선택 중 하나).

### 2.7 이정표 2단계
- **LEVEL 1 (A 바)**: 5노드 점 — `STEP01 · STEP02 · STEP03 · STEP04 · 복귀`. 현재 8단계 레일(정비소·범행도주·주행·도미노·퍼즐·검증·수리·해적선)을 **학습 5단계로 통합**하고 서사 단계(범행·주행)는 점 사이 작은 아이콘으로 [결정 D2].
- **LEVEL 2 (B 줄)**: STEP 내부 칩. STEP01은 `필요성 → 차량 동작 → 신호 추적 → SW 판단 → 통합` (§3).
- 둘은 **한 컴포넌트**(`JourneyRail`)가 `level` prop으로 그린다. 기존 `journeyRail`/`stageHistoryNav` 2종과 STEP04 내부 로드맵을 대체 [기존: 2종 병존].

### 2.8 고정 비율 기술 방침 [가설 → 선행 스파이크 WP0]
`transform: scale()`을 일괄 적용하지 않는다. 후보 3개를 **0.5일 스파이크**로 R3F 포인터·퍼즐 드래그·SW 뷰 확대로 비교:

2. CSS `zoom`(Chrome 전용, 입력 좌표 동작 확인 필요).
3. `transform: scale()`+ R3F `Canvas`에 보정 `onPointer` 좌표 변환(비권장).
- 기본 추천: **1안**. 기존 `vw/vh` 160곳·`@media` 65개는 STEP별로 단계 이관(STEP01은 신규 CSS라 처음부터 `--u`) [결정 D1].

| Vehicle/System · E/E · Control SW 3관점이 적절한가 | **교육용 렌즈로 적절. 유지**. 표준의 공식 3계층은 아님 | `AUTOMOTIVE_CONCEPT_AUDIT.md` §2.1(기존). ISO 26262 Part 4(시스템)·Part 6(SW) 개념에서 착안 [근거: 공개 목차 확인, 본문 보류] |

| E/E와 SW의 경계 | E/E = 부품·제어기·네트워크 **배치와 연결**, SW = 제어기 **내부 판단**. 경계 = 제어기의 I/O(핀·CAN 포트). 현재도 이 경계로 구분됨 | `featureFlows.layers[1]` vs `[2~3]` [코드] |
| HW↔SW 관계 표현 | E/E 렌즈에서 **논리 신호(요청·값)** 와 **물리 연결(배선·CAN)** 을 구분 표시: 노드 사이 선 위에 `신호명(단위)`, 선 종류로 물리(analog/digital/CAN/전력). 레지스트리 `FlowType` 재사용(P3) | 현재는 구분 없음 [기존] |
| 도메인 vs 시스템 관점 혼동 | 도메인=**어떤 기능 묶음**(탭/핫스팟), 관점=**어떤 추상 수준**(세그먼트). 둘을 **다른 UI 요소**로 분리(도메인=무대 위 핫스팟, 관점=작은 세그먼트 컨트롤) | 현재 둘 다 "탭"으로 보임 [캡처] |
| 누락 기능·도메인 | 사건 연결 3기능(drive f0 · thermal f1 · brake f1) **필수 완성**, 나머지 25기능은 템플릿 미션. **충전·네트워크/진단 도메인은 STEP01에 없음**(이미지 프롬프트만 존재 `docs/image-prompts/09~10`) → 이번 범위 외 | `STEP01_DOMAIN_FUNCTION_AUDIT.md` §6 |

| 기술 주의 | 계산 호출은 슬라이더 변경마다 약 660 스텝×2(수 ms) — 디바운스 불필요 [가설: 측정 필요]. `simulate`가 내부 모델 함수를 export하지 않아 **정상 상태 계산 래퍼**가 필요할 수 있음 |

## 6. 입력·신호·출력 연결 구조 (데이터 설계)

### 6.1 정규 단계(Canonical Stage) — 세 관점을 하나의 레일로
현재: Vehicle 5, E/E 4, SW 2단계로 **관점마다 레일이 다름**(`step01-07/10/12` [캡처]). 제안: 기능마다 정규 단계 `S0..Sn`을 정의하고 각 단계가 세 관점 요소를 가리킨다.

```ts
type StageMap = {                       // [제안] 기능당 1개
  stages: { id: string; label: string;   // 예 "pedal_in" "가속 페달 조작"
    vehiclePart?: number;                // getFeatureLayer(d,f,0|1)의 인덱스
    eeNode?: number;                     // layer 1 인덱스 + (선택) componentId
    swBlock?: number[];                  // layer 3 인덱스
    signal?: { id: string; name: string; unit: string; flow: FlowType; modelSrc?: string }  // 레지스트리/모델 id
  }[];
}
```
- 3개 사건 기능(drive f0·thermal f1·brake f1)은 **직접 작성**(신호 id를 `simModel` 신호·`components.ts` 포트와 맞춤 = M9 최소안).
- 나머지 25기능은 기존 `layers`에서 **자동 생성**(현재 `flowSignals` 방식) + 화면에 "예시 흐름" 배지.
- 관점 전환 시 **같은 `stageId`가 유지**되고 각 관점이 해당 요소를 하이라이트 → "하나의 기능을 서로 다른 수준에서 관찰".

### 6.2 구동 f0 정규 단계 예시 (확정 전 — 실제 신호 정의 확인 후 [결정])
| 단계 | Vehicle | E/E | SW | 신호(모델 id) |
|---|---|---|---|---|
| S0 | 가속 페달 | APS 센서 → VCU 입력 | A/B 상관성·입력 필터 | `aps`(%) |
| S1 | — | VCU | 입력 필터 → 처리값 | `filt`·`proc`(%) |
| S2 | — | VCU | 페달 맵 | `req`(Nm) |
| S3 | — | VCU | 가용 토크 MIN·램프 | `arb`(Nm) |
| S4 | 인버터·모터 | CAN → 인버터 | 토크 출력 | `can`(Nm) → `mot`(Nm) |
| S5 | 차량 가속 | — | — | `acc`(m/s²) |
- 위 예시는 **`simModel.propulsion` 신호 흐름 그대로**(`aps→filt→proc→req→arb→can→mot→acc`)라 STEP04와 직접 대응(M9). `구동 허용(permit)`·`A/B 상관성`은 모델에 없으므로 "모델 미반영 블록"으로 표시.

### 6.3 SW 입력·출력·상태·파라미터 태그 (SW 관점)
| 역할 | 표시 | 예(drive f0) | 출처 |
|---|---|---|---|
| 입력 | 파랑 칩, 값·단위 | 페달 60 % | 슬라이더 → `aps` |
| 파라미터 | 회색 칩(상단) | 맵 3.4 Nm/%, 한계 260 Nm, 필터 τ 40 ms | `simModel.ts:46~50` 상수 |
| 내부 상태 | 블록 내 배지 | 램프 진행, (thermal) 히스테리시스 ON/OFF | 모델 상태 |
| 판단 결과 | 블록 아래 문구 | "한계 이내 → 통과" | 규칙 문자열 |
| 출력 | 보라 칩 | CAN 토크 204 Nm | `can` |
| 하위 시스템 명령 | 끝 화살표 | → 인버터 | E/E 노드 |

## 7. 학습 미션과 완료 조건

### 7.1 구조 (기능 1개 = 미션 1개)
`학습 미션(Q) → 직접 조작 → 신호 관찰 → 결과 확인 → 핵심 개념 정리(고양이 요약) → 완료`

### 7.2 기능 완료 판정 (신규, 저장)
| # | 조건 | 비고 |
|---|---|---|
| a | 전제조건 충족 + 입력 선택(기존 `conds`·`inputSelected`) | 기존 상태 사용 |
| b | 신호가 **마지막 단계까지** 도달(수동 스텝·자동재생 모두 인정) | 현재는 자동재생만 [P2] |
| c | 질문 Q1~Q3(3개) 완료 | 각 1조작 |
| d | (지원 기능만) 필요성 체험 Q4 완료 | W5 목록 |
- 기능 완료 = a·b·c(+d). 도메인 칩 진행 링 = 완료 기능 수/4.

### 7.3 STEP01 완료(= `다음 →` 활성)
- **필수 3기능**: 구동 f0(운전자 토크 요청) · 열관리 f1(펌프·팬 제어) · 제동 f1(회생·마찰 협조) — **사건 STEP02~04가 실제로 사용하는 기능**. 나머지 25기능은 선택(보너스, 진행 링·뱃지).
- 이전에 완료한 저장이 있으면(재플레이) 항상 활성.
- 허브 통합 미션(W6)은 필수 아님(권장 별 획득) [결정 D4].

### 7.4 저장·복원 [코드 검토]
- `Campaign`(localStorage `traceback-v16-save`)에 `garage: { done: string[]; q: Record<string, boolean>; wrong: Record<string, number>; step: Record<string, number> }` 추가. `hydrateCampaign`이 `base`와 병합하므로 **구버전 저장은 기본값**으로 복원됨 [코드 `runtime.ts:83~101`]. 기능 전환 시 입력·조건 유지(§P1 보완)는 `GarageExperience` 상태를 **기능별 맵**(`conds[feature]`)으로.
- 다른 관점으로 이동해도 `stageId`·입력·질문 진행이 유지된다(현재도 유지됨 [코드 P1]).

### 7.5 템플릿 질문(25기능, 자동 생성)
Q1(Vehicle) "이 기능은 어떤 입력에서 시작될까?" · Q2(E/E) "신호는 어떤 부품을 거쳐 출력될까?(순서 선택)" · Q3(SW) "SW는 어떤 조건을 확인한 뒤 출력할까?" — `layers`의 role에서 자동 생성, 오답 후보는 같은 도메인의 다른 노드. **"템플릿 질문"임을 데이터에 표시**하고 품질 검수는 후속 [결정 D5].
