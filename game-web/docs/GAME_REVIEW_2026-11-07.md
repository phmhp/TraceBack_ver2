# TraceBack 다각도 평가 · 페이지별 개선안 (2026-11-07)

대상: 자동차 SW 검증 기업 신입사원 교육용 게임 (실무자도 플레이)
범위: 현재 빌드 전 화면 직접 확인 + 레이싱·메모판·퍼즐·벤치 로직 코드 확인 + 제네시스 GV60(2024) 디지털 취급설명서 "경고등 & 심볼" 확인
원칙: 텍스트보다 그래픽, 틀린 내용 금지, 특정 OEM 용어·독자 기술 지양

**가장 먼저 고칠 5가지 (P0)**
1. 고장 직후 수치 노출 제거 → 수치는 플레이어가 "측정"해서 얻게 만들기 (§2-6, §3-3)
2. 레이싱의 1~3단 수동 변속(Q/E) 제거 → 전기차에 맞는 P·R·N·D + 회생 단계 + 미션 구간 (§2-5, §3-1)
3. 고장을 "거리 도달 시 속도 상한"이 아니라 시뮬(`vehicleSim`의 고장 훅)로 재현 → 특정 조작에서만 증상이 드러나게 (§3-1)
4. 벤치에 "테스트 케이스 카드"와 "회귀 시험" 단계 추가 (§2-9)
5. 열관리 사건 데이터 불일치 수정: 증거는 "Derate flag ON", 벤치 SW 로직은 "DERATE STATE LEVEL 0" (§4)

## 1. 사용자 고민 3가지에 대한 답

### 1-1. "레이싱이 그냥 가속만 해서 고장이 실감나지 않는다" → 맞습니다
- 현재: W(가속)·S(감속)·A/D(조향)·Q/E(1~3단)·빨간불 정지 1회. 고장은 210 m 지점에서 속도를 31 km/h로 묶는 방식.
- 문제: 고장이 "조작과 무관하게" 일어나므로 플레이어는 원인을 추리할 단서(언제·어떤 조작에서 생겼나)를 얻지 못함. 실무의 첫 단계인 **재현 조건 파악**을 배울 기회를 놓침.
- 해결 방향: **"미션 구간 = 재현 조건"**. 코스를 구간별 미션으로 나누고, 고장은 특정 조작에서만 드러나게 함. 플레이어가 "어느 구간에서 이상했는지"를 메모판 단서로 가져감. 상세는 §3-1.

### 1-2. "고장 전 차량 도메인 학습이 '이런 게 있네~'로 끝난다 / 고장 도메인만 보여주면 정답이 보인다"
- 고장 도메인만 보여주는 건 말씀대로 범위를 알려주는 스포일러라 비추천.
- 추천: 도메인 설명을 **"출발 전 점검(프리드라이브 체크)" 미니게임**으로 바꾸기. 실제 차량도 시동 시 경고등이 켜졌다가 약 3초 뒤 꺼지는 자가 점검을 합니다(취급설명서의 ABS·EPS·EPB 경고등 설명과 같은 원리). 이것을 게임으로:
  1. 시동 → 전원 모드 OFF → ON → READY 단계를 플레이어가 직접 진행 (프리차지·접촉기 순서 학습)
  2. 계기판 경고등 점등 확인 → 3초 뒤 꺼지는지 체크 (진단 개념 학습)
  3. 브레이크 밟고 D 변속, 크리프 출발, 회생 단계 바꿔 보기, 핸들 좌우 (구동·제동·조향 "정상 기준값" 기록)
- 효과: 모든 도메인을 고르게 만지므로 스포일러가 없고, 이때 기록한 **정상 기준값(골든 레퍼런스)**이 나중에 고장 비교의 근거가 됨. "그냥 보고 넘기기"가 "나중에 쓸 기준을 내가 측정해 둔다"로 바뀜.
- 도메인×기능×레이어(3관점)가 한 화면에 겹쳐 복잡한 문제 → 기본은 **하나의 신호 사슬 그림(센서→제어기→액추에이터→차량 거동)**만 보여주고, 레이어는 "확대해서 보기"로 필요할 때만 열기. §2-3 참고.
- 아직 안 녹인 관점 중 추천도 순:
  1. **전원 모드 상태도** (OFF/ACC/ON/READY, 프리차지, 충전 중 주행 금지) — 모든 고장의 전제 조건이고 검증 실무에서 상태 전이 테스트가 매우 많음
  2. **진단·고장 대응 관점** (DTC 저장 조건, 경고등, 비상 운전/출력 제한 같은 안전 상태로의 전환) — "고장이 나면 차가 어떻게 스스로 보호하는가"
  3. **E/E 아키텍처 관점** (도메인 제어기 vs 존(Zonal) 구조, 게이트웨이, CAN/CAN FD/이더넷) — 지금 "E/E Architecture" 뷰가 있으나 부품 배치 위주. 통신 경로·메시지 주기·타임아웃을 보여주면 실무자에게도 의미 있음
  4. 기능 안전 관점(ISO 26262의 안전 목표·안전 상태 개념만, 규격 세부는 X)

### 1-3. "메모판 → 퍼즐 → 검증 흐름이 연결되고, 검증 사고를 배우며, 재미·추리성이 있는가"
- 연결성: 흐름 자체는 "현상 관찰 → 원인 가설 → 수정 → 검증"으로 실무 순서와 맞음. 다만 퍼즐(경로 복원)이 **수정**이고 벤치가 **검증**인데, 실무에서는 "검증 실패 → 원인 분석 → 수정 → 재검증(회귀)" 순서가 많아 첫 벤치 실행이 "고장 재현"이라는 점이 화면에서 더 분명해야 함.
- 검증 사고: 가장 중요한 두 가지가 아직 약함.
  - **경계 나누기(반분 탐색)**: 입력·명령·출력 중 어디서 값이 처음 틀어지는지 좁혀 가는 사고. 벤치 문구("값이 처음 갈라진 곳을 찾자")에 이미 있음 → 이것을 메모판의 핵심 메커닉으로 끌어올리기.
  - **반증**: 가설을 "지지하는 증거" 2개를 고르는 방식은 확증 편향을 연습시킴. 다른 가설을 **반박하는 증거**를 고르게 해야 함.
- 재미·추리성: 현재 정답 수치가 미리 노출되고 가설이 3개뿐이라 추리라기보다 확인 작업. §3-2·§3-3의 "측정 예산", "반박 카드", "증언 vs 로그" 메커닉 추천.
- 난이도: 실패 시 가이드 진단이 전체 정답을 보여줌 → 힌트를 3단계(방향 → 경계 → 정답)로 나누고 단계마다 추격 격차를 소모하게.

## 2. 페이지별 평가와 개선안

각 항목: **지금 보여주는 것 / 문제 / 추가할 정보 / 표현 방식**

### 2-1. 타이틀
- 지금: 로고, 새 게임 시작, 차고 일러스트, 두 캐릭터.
- 문제: 교육 목적(무엇을 배우는지)이 전혀 안 보임. 이어하기·난이도 선택 없음.
- 추가: "이번 플레이에서 배우는 것" 아이콘 3개(신호 사슬·고장 추적·검증), 난이도(신입/실무자), 이어하기.
- 표현: 아이콘 + 한 단어 라벨. 실무자 모드는 힌트 비용 증가, 수치 정밀도 증가.

### 2-2. 프롤로그 (영광의 과거 → 몰락)
- 지금: 컷신 + 대사.
- 문제: 왜 "SW 검증"이 이 둘에게 중요한지 동기 연결이 약함.
- 추가: 몰락의 원인을 "검증 안 된 SW 업데이트로 레이스에서 패배" 같은 사건으로 → 게임 전체 주제(검증의 가치)와 연결. 프롤로그에서 고장 한 번을 짧게 체험(튜토리얼).
- 표현: 컷 1장을 "레이스 중 계기판 경고등 점등" 장면으로 교체.

### 2-3. 차고 (Vehicle/System · E/E Architecture · Control Software)
- 지금: 7개 도메인 탭 × 도메인별 3~4개 기능 × 3개 관점. 3D 리그, 오른쪽 기능 목록, 하단 단계 흐름, "학습 미션(예측 퀴즈)".
- 잘한 점: 같은 기능을 물리→E/E→SW로 내려가며 보는 구조는 실무 관점과 정확히 맞음. 예측 퀴즈는 능동 학습으로 좋음.
- 문제:
  - 정보 밀도가 가장 높은 화면. 3D 위 라벨, 작은 글씨(10~11px), 영어 블록명(Signal Adapter 등) 혼재.
  - 도메인 7개를 다 보라고 하지만 탐색 동기가 없음(점수·기록과 연결 안 됨).
  - "기어" 도메인이 별도 탭: 전기차는 변속기 단수가 없고 P/R/N/D 선택(시프트 바이 와이어)과 주차 잠금이 핵심 → "구동" 하위 기능이나 "주행 허용(인터록)"으로 합치는 편이 정확.
- 추가할 정보:
  - 기능마다 **정상 기준값 1개**(예: APS 60% → 요청 토크 약 200 Nm 수준, 브레이크 55% → 감속 약 3 m/s²) — "학습 미션"의 정답으로 쓰고 이후 고장 비교에 재사용.
  - **고장 시 차량의 보호 동작**(출력 제한, 비상 운전, 경고등) 한 줄 그림.
  - 통신 관점: 신호가 어느 버스·주기로 가는지(예: 10 ms 주기 CAN 메시지) 작은 배지.
- 표현 방식:
  - 기본 화면은 "센서 → 제어기 → 액추에이터 → 차량 반응" 4칸 사슬 하나. 칸을 누르면 그 부품의 3D·SW 블록이 확대(줌인)되는 구조로 바꿔 레이어를 "깊이"로 표현.
  - §1-2의 "출발 전 점검" 체크리스트로 전환하면 이 화면의 체류 이유가 생김.

### 2-4. 도주 브리핑
- 지금: 컷 + 미션 카드(경찰 출발 3초 뒤 합류, 고장은 특정 지점 발생, 목표 해안선 갑판까지).
- 문제: "고장은 코스의 특정 지점에서 발생"이라고 미리 알려 줌 → 긴장감 감소, 재현 조건 추리 기회 상실.
- 추가: 코스 지도 + 미션 구간 아이콘(신호 정지, 언덕, 슬라럼, 추월, 터널, 충전소). 조작 키 안내 그림.
- 표현: 미니맵 한 장 + 구간 아이콘 6개, 문장은 1줄.

### 2-5. 레이싱 (일반·보조·재개·선박)
- 지금: W/S/A/D, Q/E 1~3단(단마다 최고속 78/124/172 km/h), 빨간불 정지 미션 1회, 가드레일·일반 차량 충돌, 추격 격차 바, 속도계.
- 문제:
  - **정확성**: 전기차에 1~3단 수동 변속은 틀린 개념(대부분 단일 감속기). 실무자에게 바로 지적받을 부분.
  - 고장 재현이 거리 기반 속도 상한이라 조작과 무관.
  - 렌더 부하: 측정값 약 85만 삼각형, 1,900 드로우콜, 프레임당 약 17 ms(개발 PC 기준) → 사내 노트북에서 끊길 위험.
- 추가할 정보(HUD):
  - P·R·N·D 표시, READY 표시등, 회생 단계(0~3), 배터리 잔량·출력 게이지(파워 미터: 가속 시 +, 회생 시 −), 경고등 영역.
  - 고장 발생 시 수치 대신 **경고등 + 몸으로 느끼는 증상**(가속 둔화, 핸들 무거움, 제동 거리 증가)만.
- 표현: 미션 구간 진입 시 상단에 아이콘 배너("정지선까지 정차", "후진으로 주차 칸 진입"). 증상은 화면 흔들림·소리·계기판 경고등으로.
- 상세 설계는 §3-1.

### 2-6. 고장 감지 (FAULT_CUE)
- 지금: "주행 이상 감지" + INPUT 60% / COMMAND 27% / ACTUAL 91 Nm + 루의 대사.
- 문제: **정답이 그대로 노출됨**. 실무에서도 처음 받는 것은 고객 증상(VOC)뿐이지 내부 신호가 아님.
- 추가: 계기판 사진(경고등), 고객 증상 문장 한 줄, "언제·어디서" (방금 지나온 미션 구간), 재현 여부.
- 표현: "정비 접수증(작업 지시서)" 형태 카드 1장 — 증상·발생 조건·경고등 그림. 수치 칸은 "?"로 비워 두고 메모판에서 측정해 채우게.

### 2-7. 메모판 (BOARD)
- 지금: 관찰된 현상·계측 단서 카드(왼쪽), 가능 원인 가설 3개(오른쪽), 가운데 코르크판에 끌어다 놓고 실로 연결. 성공 조건: 가설 1개 + 지지 단서 2개.
- 잘한 점: 탐정 보드 연출, 단서 종류(주행 현상·입력 계측·제어 명령·물리 응답)가 신호 사슬 순서와 일치.
- 문제: 단서가 이미 모두 공개되어 있고 종류 라벨이 답을 암시. 지지 증거만 고르므로 반증 연습이 없음.
- 추가할 정보:
  - 단서마다 **측정 위치**(사슬 위 어느 지점)와 **기준값 대비 차이**.
  - 가설별 "이 가설이 맞다면 보여야 할 것"(예측) 칸.
- 표현 방식:
  - 코르크판 위에 **신호 사슬 지도**를 깔고, 단서 카드를 측정 위치에 꽂게 함 → 정상(초록)과 이상(빨강)이 처음 갈리는 경계가 시각적으로 드러남 = 반분 탐색 학습.
  - 가설 카드에 "반박" 도장 메커닉: 오답 가설마다 그 가설과 모순되는 단서 1개를 찍어야 진행(§3-2).

### 2-8. 경로 복원 퍼즐 (WIRING)
- 지금: 입력(APS)과 출력(인버터) 사이 빈칸 2개에 SW 블록(Signal Adapter, Driver Torque Map, CAN Torque Command, 함정 블록 Legacy Scale 45%, Trace Logger)을 끼우기. 오른쪽에 요구사항 흐름(IF/THEN).
- 잘한 점: 요구사항 문장(IF/THEN)과 블록을 나란히 둔 것, 함정 블록(Legacy Scale)이 실제 원인과 연결된 점.
- 문제: 블록 이름이 영어 약어 위주라 신입에게 의미가 안 읽힘. 왜 그 순서인지(데이터 흐름·단위 변환)가 안 보임.
- 추가: 블록마다 입력 단위→출력 단위(%, Nm), 블록을 꽂으면 실시간으로 값이 흐르는 미리보기(60% → 60% → 204 Nm).
- 표현: 블록 사이 선 위에 값 말풍선. 요구사항 줄과 블록을 같은 색으로 묶어 **추적성**(어떤 요구가 어떤 블록에 구현됐나) 시각화.

### 2-9. 검증 벤치 (TWIN_BENCH: SW 로직·ECU I/O·시스템 통합·차량 시나리오)
- 지금: 정상(Reference)과 내 설계를 좌우 비교. 요구사항 배지(REQ-DRV-01), 사건 재현 입력 3종, 관찰 경계 3종 선택 후 시뮬레이션 실행.
- 잘한 점: 4개 탭이 실무의 MIL/SIL·HIL·시스템 통합·실차(VIL) 단계와 대응되는 구조. "값이 처음 갈라진 곳을 찾자"는 핵심 메시지.
- 문제:
  - 탭 이름이 실무 용어와 연결되지 않음 → 실무자 입장에선 아쉬움, 신입은 나중에 현업 용어와 매칭 못 함.
  - 테스트의 4요소(사전 조건·자극·기대 결과·판정 기준)가 한 장으로 보이지 않음.
  - 수정 후 **다른 기능이 망가지지 않았는지(회귀)** 확인 단계가 없음.
- 추가할 정보:
  - 탭에 보조 라벨: "SW 로직(MIL/SIL)", "ECU I/O(HIL)", "시스템 통합", "차량 시나리오(실차)".
  - **테스트 케이스 카드**: 사전조건(READY, D단, 0 km/h) · 자극(APS 0→60%, 0.2 s) · 기대(요청 토크 ≥ 200 Nm, 0.3 s 이내) · 판정(PASS/FAIL).
  - 경계값 케이스 1~2개(APS 0%, 100%, 두 센서 값 불일치 시 토크 제한).
  - 회귀 체크: "브레이크 동시 입력 시 토크 차단" 같은 다른 요구가 여전히 PASS인지.
- 표현: 시간축 그래프(자극·기대·실제 3줄)와 PASS/FAIL 도장. 텍스트 표 대신 그래프 하나.

### 2-10. 검증 실패 → 가이드 진단 (VERIFY_FAIL)
- 지금: 기대 204 Nm ≠ 실제 92 Nm, 4단계 해설 카드가 순서대로 열림.
- 문제: 실패하면 정답이 다 보임 → 실패에 대한 학습 비용이 0. 텍스트 위주 카드.
- 추가: 플레이어가 틀린 지점(어느 경계를 잘못 봤는지) 표시.
- 표현: 신호 사슬 그림에서 "내가 고른 경계"와 "실제 갈라진 경계"를 두 색으로 겹쳐 보여주기. 힌트 3단계(방향 → 경계 → 정답), 단계마다 추격 격차 감소.

### 2-11. 수리 적용 (REPAIR)
- 지금: 3D 벤치에서 입력→ECU→출력 정상 응답, OTA 문구, 카운트다운 후 레이스 복귀.
- 추가: "무엇을 바꿨는가" 전/후 비교(보정값 45% → 100%, SW 버전 1.0.3 → 1.0.4), 배포 전 체크(회귀 PASS 수).
- 표현: 버전 태그 2개와 화살표, 체크 아이콘 줄. OTA는 일반 용어라 문제없음.

### 2-12. 재개 주행·선박 탈출
- 지금: 두 번째 고장(열관리) 후 선택 사건(제동), 부두 램프 점프 연출.
- 추가: 수리한 기능을 **실제로 써야 통과하는 구간**(예: 수리한 가속으로 오르막 추월, 수리한 제동으로 램프 직전 감속) → 검증이 결과로 체감됨.

### 2-13. 엔딩 (WANTED / 수감 기록)
- 지금: 그래픽 사건 요약(부품 사슬·고장 위치·정상 vs 고장 막대·4단계·한 줄 교훈).
- 추가: 플레이어 개인 기록(첫 가설 정확도, 사용 힌트, 측정 횟수 대비 효율), 실무 용어 대응표(이번에 한 일 = 실무에서 무엇).
- 표현: 작은 "검증 역량 레이더 차트"(관찰·가설·경계 탐색·테스트 설계·회귀) 한 개.

## 3. 핵심 메커닉 개선 설계

### 3-1. 레이싱: "미션 구간 = 재현 조건"
| 구간 | 조작 | 정상일 때 | 이 구간에서 드러나는 고장 예 |
|---|---|---|---|
| 출발 | 브레이크 밟고 D, 크리프 출발 | 천천히 움직임 | 변속 인터록 이상(D 거부) |
| 신호 정지 | 정지선에서 완전 정지 | 회생+마찰로 부드러운 정지 | 회생/마찰 협조 이상(제동 거리 증가) |
| 언덕 재출발 | 정지 후 오르막 출발 | 밀림 없음(경사 밀림 방지·오토 홀드) | 주차 브레이크·홀드 이상 |
| 슬라럼 | 좌우 연속 조향 | 가벼운 핸들 | 조향 보조 이상(핸들 무거움, 경고등) |
| 추월 | 풀 가속 5초 | 즉시 가속 | APS 처리 오류, 출력 제한(파워다운) |
| 터널·야간 | 전조등 | — | 12 V 저전압 연쇄 증상 |
| 후진 주차 | R단으로 칸에 넣기 | — | R 인식 이상 |
| 충전소(피트스톱) | 제한 시간 내 충전 | 충전 속도 정상 | 배터리 온도 관리 이상(충전 지연) |

- 구현 메모: 이미 있는 `src/sim/driverInput.ts`(Enter 시동, W/S, A/D, Space)와 `vehicleSim.ts`의 고장 훅(pedalScale·fanStuck·brakePressureGain)을 레이스에 연결하면 됨. 1~3단 기어는 P·R·N·D로 교체.
- 주행 기록기: 레이스 동안 속도·페달·토크 명령을 기록 → 메모판에서 플레이어가 "로그를 열어 측정"하는 단서가 됨.

### 3-2. 메모판: 반분 탐색 + 반증
- 신호 사슬 지도 위에 측정 지점(●) 5~6개. 측정할 때마다 시간(=추격 격차) 소모 → **측정 예산**.
- 정상 기준값(차고에서 기록한 값)과 비교해 초록/빨강으로 칠해짐 → 처음 빨개진 지점이 고장 경계.
- 가설 카드 4~5개(오답에 그럴듯한 함정 포함). 오답 가설마다 "반박" 도장 = 모순 단서 연결.
- 함정 예: "배터리가 출력을 제한했다" → 반박 단서: BMS 출력 한계는 정상 범위(측정 시 초록).

### 3-3. 추리 재료를 "증언 vs 로그"로 분리
- 증언(루의 체감, 고객 증상)은 부정확할 수 있음 → 로그로 확인해야 함.
- 예: 루 "브레이크가 안 들었어!" ↔ 로그상 제동 명령은 정상, 캘리퍼 압력만 낮음 → 원인은 출력 장치.

## 4. 정확성·보편성 점검 (틀리면 실무자에게 신뢰를 잃는 부분)

| 위치 | 현재 내용 | 문제 | 수정 제안 |
|---|---|---|---|
| 레이싱 | Q/E로 1~3단 변속, 단별 최고속 | 전기차는 대부분 단일 감속기, 수동 변속 없음 | P·R·N·D + 회생 단계(0~3) + 주행 모드 |
| 열관리 사건 | 증거: "Derate flag ON", 벤치 SW: "DERATE STATE LEVEL 0" | 같은 사건에서 서로 모순 | 벤치를 LEVEL 1 이상으로 통일 |
| 열관리 사건 | 모터 온도 78.4 °C에서 출력 제한 | 모터 권선 보호 제한은 보통 이보다 훨씬 높은 온도에서 시작 → 실무자에게 어색 | 수치를 "냉각수 온도"로 바꾸거나 제한 시작 온도를 높게(정확한 값은 차종마다 달라 "예시값" 표기) |
| 구동 사건 | APS 60% → 204 Nm 고정 | 실제 토크 요청은 차속·모드에 따라 달라짐 | "이 조건(정지, 노멀 모드)에서의 기준값"이라고 전제 조건 명시 |
| 차고 | "기어" 도메인 탭 | 전기차에서는 변속 = P/R/N/D 선택·주차 잠금 | "주행 허용·변속(PRND)"으로 이름 변경 또는 구동에 통합 |
| 전반 | ECU를 Thermal ECU, Chassis ECU 등으로 표기 | 일반 용어지만 영어 혼용 | 한글 병기: 열관리 제어기, 샤시 제어기 |
| 고장 감지 화면 | 내부 신호 수치 즉시 공개 | 실무 흐름과 다름(먼저 고객 증상, 다음 계측) | 경고등·증상만 |

**OEM 종속 용어 체크**: 현재 코드·화면에서 특정 OEM 고유 명칭은 확인되지 않음(VCU, MCU, BMS, APS, CAN, OTA, SWC 모두 업계 공통). 제네시스 매뉴얼을 쓸 때 아래처럼 바꿔야 함.
- "블루핸즈", "직영 하이테크 센터" → "정비 센터"
- "i-Pedal" 같은 상표성 기능명 → "원페달 주행"
- "스마트 크루즈 컨트롤" → "차간 거리 유지 크루즈"
- "AUTO HOLD"(여러 OEM 공용이나 표기 차이) → "오토 홀드(정차 유지)"
- 매뉴얼 문장·그림은 그대로 복제하지 말고 증상·원리만 재서술(저작권).

**추가하면 좋은 핵심 제어 기능(업계 공통)**: 크리프 토크, 회생제동 단계·회생/마찰 협조, 토크 제한(디레이팅), APS 이중 센서 타당성 검사, 프리차지·절연 감시, 전원 모드 전이, 충전 제어(충전 중 주행 금지), ABS/ESC/TCS, 경사로 밀림 방지·오토 홀드, 조향 보조 맵, 12 V 보조 전원(DC/DC), 배터리 온도 관리(컨디셔닝).

## 5. 제네시스 EV 취급설명서 활용 방안

확인한 자료: GV60 2024 디지털 취급설명서 → "경고등 & 심볼" (EV 관련: 파워다운, 주행 가능(READY), 구동용 배터리 잔량, 충전 경고등, 배터리 컨디셔닝 모드, ABS, 브레이크, EPS, EPB, ESC, TPMS, 오토 홀드 등)

### 5-1. 쓰는 방법 — "고객 증상 언어"의 출처로
1. **사건의 첫 화면(정비 접수증)을 매뉴얼의 경고등·증상 표현으로** 작성 → 신입이 실제 고객·정비 현장에서 듣는 언어로 시작.
   - 예: 매뉴얼은 파워다운 표시등이 켜지는 상황으로 "고전압 배터리 잔량·전압 저하, 배터리 온도 과고/과저, 구동 시스템 온도 상승으로 보호 필요"를 제시 → **같은 경고등에 원인이 여러 개** = 추리 재료로 최적.
   - "주행 가능 표시등이 깜빡이면 비상 운전 상태" → 비상 운전(limp-home) 개념을 자연스럽게 도입.
   - ABS·EPS·EPB 경고등은 "켜졌다 약 3초 후 꺼지면 정상" → §1-2 출발 전 점검 미니게임의 근거.
2. **경고등 도감(수집 요소)**: 사건을 풀 때마다 경고등 카드 획득. 카드 뒷면 = 그 경고등 뒤의 신호 사슬과 원인 후보. 엔딩·메뉴에서 열람.
3. **증상 → 도메인 매핑 표**를 차고 학습과 연결: 경고등을 누르면 관련 도메인의 사슬이 하이라이트.
4. 표기 원칙: 화면에는 "출처: 일반적인 전기차 취급설명서의 경고등 설명을 재구성" 정도로 쓰고 특정 브랜드명·로고·원문은 넣지 않기.

### 5-2. 추가 고장 시나리오 제안 (매뉴얼 경고등 기반, 모두 일반 기술)

| # | 고객 증상(경고등) | 도메인 | 실제 원인(정답) | 그럴듯한 함정 가설 | 결정적 단서 | 레이싱 구간 | 검증 포인트 | 난이도 |
|---|---|---|---|---|---|---|---|---|
| 1 | 파워다운 표시등 + 추월 시 가속 약함 | 전원·구동 | 저온으로 배터리 방전 출력 한계 감소(정상 보호 동작) | 모터 고장, 페달 고장 | BMS 출력 한계값이 낮음, 배터리 온도 낮음 | 추월 | **"고장이 아니라 사양"** 판별 → 정상 동작 확인 테스트 | 중 |

## 10. 기능안전(ISO 26262) — 게임 반영 방안과 학습 지도

### 10-1. 이번 주에 할 수 있는 범위
| 단계 | 내용 | 규모 | 상태 |
|---|---|---|---|
| A | 엔딩 "안전 관점" 토글(위험 → 감지 → 안전 상태 + 인사이트) | 작음 | **완료** |
| B | 벤치에 **고장 감지·대응 시간 막대**: 고장 발생 → 감지 → 안전 상태 진입이 허용 시간(FTTI) 안에 끝나는지 PASS/FAIL로 보여주기 | 중간 | 제안 |
| C | 고장 주입 테스트 케이스 1개: "APS 한쪽 센서 끊김 → 토크 제한으로 전환되는가" | 중간 | 제안 |
| D | 위험 평가(HARA) 미니 퍼즐: 상황 카드의 심각도·노출·제어 가능성을 골라 ASIL 표를 따라가 보기(학습용 예시라는 표기 필수) | 큼 | 마감 후 |

ASIL은 차량·회사마다 HARA 결과로 정해지므로 게임에는 특정 ASIL을 확정해서 쓰지 않았음(틀린 정보 방지).

### 10-2. 실무 학습 지도(요약)
- **전체 흐름**: 아이템 정의 → HARA(위험 분석·위험 평가) → 안전 목표 → 기능 안전 개념(FSC) → 기술 안전 개념(TSC) → HW·SW 개발 → 통합·검증 → 안전 확인(평가·감사) → 생산·운영
- **ISO 26262(2018) 파트 구성**: 1 용어 · 2 안전 관리 · 3 개념 단계 · 4 시스템 · 5 HW · 6 SW · 7 생산·운영 · 8 지원 프로세스(형상 관리, 도구 신뢰성 등) · 9 ASIL 지향 분석(분할, 종속 고장 분석) · 10 가이드라인 · 11 반도체 · 12 이륜차
- **HARA**: 심각도 S(0~3) × 노출 E(0~4) × 제어 가능성 C(0~3) → QM 또는 ASIL A~D
- **시간 개념**: FTTI(고장 발생부터 위험 사건까지 허용 시간) 안에 감지 시간 + 대응 시간이 끝나야 함
- **고장 종류**: 무작위 HW 고장(확률로 관리, 지표 사용) vs 체계적 고장(설계·SW 오류, 프로세스와 테스트로 관리) → 이 게임의 구동 사건(보정값 오류)은 **체계적 고장**의 좋은 예
- **HW 지표 목표(Part 5)**: 단일점 고장 지표 SPFM — ASIL B ≥ 90%, C ≥ 97%, D ≥ 99% / 잠재 고장 지표 LFM — B ≥ 60%, C ≥ 80%, D ≥ 90%
- **SW(Part 6) 실무 포인트**: 요구사항 기반 테스트, 경계값·동등 분할, 고장 주입 테스트, 구조 커버리지(ASIL이 높을수록 MC/DC까지 권장), 간섭 배제(메모리·실행 시간·통신)
- **대표 안전 메커니즘**: 타당성 검사, 이중화, 워치독, 범위 검사, 통신 보호(CRC·카운터·타임아웃), 성능 저하 모드
- **SOTIF(ISO 21448)와 구분**: 고장이 없어도 성능 한계(센서 인식 한계 등)로 생기는 위험은 SOTIF 영역

## 11. 이번 주 일정·자원 계획 (마감: 화~수)

남은 토큰 양은 제가 직접 확인할 수 없어서, 작업을 작게 나누고 효과가 큰 순서로 진행하는 기준으로 잡았습니다. 사용자 검수 후 수정 요청을 위해 약 30%를 남겨 둡니다.
