# TraceBack 검증 흐름 기준 (v1 · 2026-11-08)

이 문서는 단계 순서와 각 단계의 역할을 고정하는 기준이다. 이후 피드백은 이 기준에 비추어 판단한다.

## 0. 원칙
1. **한 단계 = 한 질문 = 한 산출물.** 다음 단계는 앞 단계에서 *확정된* 산출물만 받는다.
2. **오답은 그 자리에서 교정한다.** 잘못 고르면 이유를 듣고 비용(추격 거리·별)을 낸 뒤 다시 고른다. 오답이 다음 단계로 넘어가는 분기는 만들지 않는다. 마감 안에 만들 수 있고, 학습에도 더 낫다.
3. **추리 = 단서로 후보 지우기.** 단서는 측정값, 시간 순서, 요구사항이다. 사전 지식을 묻는 퀴즈는 쓰지 않는다.
4. **말투:** 동료 엔지니어가 쓰는 해요체로 쓴다. 감탄사와 유아어는 쓰지 않는다. 대상은 20대 후반 신입부터 40~50대 시니어까지다.

## 1. 단계 순서 (실무 현장 이슈 대응 순서)

| # | 게임 단계 | 실무 이름 | 플레이어가 답할 질문 | 산출물 |
|---|---|---|---|---|
| 1 | 레이싱 | 증상 발생·기록 | 무엇이 언제 이상했나 | 증상 + 주행 기록 |
| 2 | 도미노 추리판 | **원인 역추적** (범위 좁히기) | 차량 → 도메인 → 기능 → 경계 중 처음 어긋난 구간은? | **의심 구간** (예: "VCU 토크 요청 계산: 입력 정상, 출력 비정상") |
| 3 | 퍼즐 | **요구사항 기반 정상 동작 복원** | 이 구간이 정상이라면 무엇을 어떻게 계산·전달해야 하나 | 기준 모델 + 칸마다의 기대값 |
| 4 | 벤치 | **시뮬레이션 검증** (정상 vs 고장 비교) | 어느 검증 레벨에서 어떤 기법으로 원인을 확정하나 | 확정 원인 → 수정 → 재실행 PASS → 회귀 |
| 5 | 수리·재주행 | 조치·확인 | 고친 차가 실제로 정상인가 | 주행 재개 |

**지금과 다른 점**
- 순서를 **퍼즐 → 도미노**에서 **도미노 → 퍼즐**로 바꾼다. 범위를 좁힌 뒤에야 볼 로직이 정해지기 때문이다. 이렇게 하면 "고장 직후 바로 서울을 콕 찍는" 문제와, 퍼즐 제목이 정답을 알려 주는 문제가 함께 사라진다.
- 도미노는 정확한 부품까지 가지 않고 **의심 구간**에서 멈춘다. 정확한 원인 확정은 벤치가 맡는다. 그래야 단계마다 추리가 하나씩 나뉜다.
- 도미노 끝의 "영향 받는 기능 목록"이 **영향도 분석**이다. 이 목록이 벤치의 회귀 시험 목록이 된다.

## 2. 퍼즐 깊이: 로직만 맞추나?
아니다. 퍼즐판은 **도미노가 좁힌 의심 구간 전체**를 다룬다. 고장이 E/E·통신·부품 쪽일 수도 있기 때문에 SW 블록만으로는 부족하다.

| 사건 | 의심 구간 | 퍼즐판 구성 |
|---|---|---|
| 구동 | VCU 안 토크 요청 계산 | SW 블록 중심 (지금과 같음) |
| 열관리 | 냉각 팬 구동 경로 | 온도 → 히스테리시스 → 팬 목표 → PWM(SW) → 릴레이·전원(E/E) → 팬 모터(HW) → RPM 피드백 |
| 제동 | 마찰 제동 경로 | 잔여력 → 압력 명령(SW) → 유압 모듈(E/E·HW) → 캘리퍼(HW) |

**퍼즐 규칙**
- 빈칸은 흩어 둔다. 연속은 최대 2칸이다. 양옆 고정 블록이 "들어오는 값·나가는 값" 단서가 되어 추론할 수 있게 하기 위해서다. 3칸 이상 연속이면 순서 맞추기가 운이 된다.
- 끼워도 선이나 값은 생기지 않는다. ▶ 실행하면 표시창에 값이 흐르고, 첫 불일치에서 멈춘다.
- 차고 노트는 순서 없이 블록 카드만 보여 준다. 실행에 1번 실패한 뒤 열 수 있고, 추격 거리 5m를 쓴다.

## 3. "어느 검증 레벨이 필요한가?" 질문의 위치
이 질문은 벤치 **시작**에 둔다. 지금은 끝에 있다. 답은 도미노 산출물(의심 구간의 종류)에서 추론한다.

**두 축을 구분한다(표준 근거).** 검증 레벨(무엇을) = ISO 26262-6 9절 단위 검증, 10절 SW 통합 검증, 11절 임베디드 SW 시험, ISO 26262-4 7절 HW·SW 통합 → 시스템 통합 → 차량 통합. 시험 환경(어디서) = MIL/SIL/PIL/HIL/차량. 게임 탭은 레벨 4개(단위 / SW 통합 / 임베디드 SW 시험 / 시스템·차량 통합), 탭마다 환경 칩. 임베디드 SW 시험까지 센서·부하·차량은 HIL이 시뮬레이션하므로 실제 부품 고장(열관리 팬, 제동 유압)은 시스템·차량 통합(실부품 연결)에서 처음 관찰된다. 시험 방법(요구사항 기반·인터페이스·고장 주입·모델-코드 비교)과 테스트 케이스 도출(요구사항 분석·동치 분할·경계값 분석·오류 추정·운용 사용 사례 분석)은 별도 질문으로 고른다.

레벨은 범위가 넓어지는 순서로 둔다: **단위 → SW 통합 → 임베디드 → 차량** (ISO 26262-6의 단위 검증 → SW 통합 검증 → 임베디드 SW 시험, 이후 시스템·차량 통합).

| 레벨 | 대상 | 보이는 것 | 부품 |
|---|---|---|---|
| 단위 (MIL/SIL) | SW 블록 하나 | 블록 입출력 | 자극(입력)으로 대신 |
| SW 통합 (SIL) | 여러 SW 컴포넌트 | 컴포넌트 사이 인터페이스 | 모델 |
| 임베디드 (HIL) | 실제 ECU + 부품 | 핀 전압, PWM, 버스, 실제 부품 응답 | HIL에 붙인 실부품 |
| 차량 | 여러 ECU · 실차 | 차량 거동, 로거 | 실차 |

단위·SW 통합에서는 부품이 모델이라 HW 고장이 보이지 않는다. 이게 레벨 선택의 핵심 학습이다. 사건별 정답: 구동 = 단위, 열관리 = 임베디드, 제동 = 임베디드.

벤치의 신호 모니터는 **탭(레벨)마다 다른 신호 목록**을 보여 준다. 값은 사건별 수치 모델(`src/features/verification/simModel.ts`)이 정상 설계와 현장 대상을 같은 입력으로 계산한 결과다.

**E/E와 기계 부품의 차이**
- E/E는 전기·전자다. 센서, ECU, 배선, CAN, 전원·릴레이처럼 **신호와 전기**를 다룬다.
- 기계 부품은 **힘과 움직임**을 전달하는 것이다. 모터 축, 기어, 캘리퍼, 팬 날개가 여기에 속한다.
- 벤치 탭에서는 기계 부품을 따로 두지 않고 HIL 부하·실차에 합친다. 탭은 4개로 고정한다: SW / ECU·HIL / 시스템 통합 / 실차.

## 4. 벤치(시뮬레이션 검증) 재설계
1. **레벨 선택:** 3절 질문으로 시작한다.
2. **시험 기법 선택:** 밍이 "어떻게 시험할까요?"라고 묻는다. 기법은 기능안전 SW 검증 기법을 따른다.

   | 기법 | 언제 맞나 |
   |---|---|
   | 요구사항 기반 시험 | 요구 입출력이 명확할 때 |
   | 현장 기록 재생 | 사건을 그대로 재현할 때 |
   | 경계값 시험 | 임계·한계 근처가 의심될 때 |
   | 지속 부하(초과 유지) | 열·누적 문제 |
   | 고장 주입 | 부품·배선 고장 가설을 증상 재현으로 확인할 때 |

   사건별 정답과 이유는 다음과 같다.

   | 사건 | 기법 | 확인하는 것 |
   |---|---|---|
   | 구동 | 요구사항 기반 + 현장 기록 재생 | 페달 맵 칸에서 첫 불일치 |
   | 열관리 | 지속 부하 → 고장 주입(팬 단선) | 팬 RPM 0, 같은 증상 재현으로 원인 확정 |
   | 제동 | 요구사항 기반 + 경계값(배터리 가득 → 회생 0) | 압력 부족 |

3. **정상 vs 고장 비교:** 같은 입력을 **정상 시나리오(퍼즐에서 만든 기준 모델)**와 **현장 기록·시험 대상**에 함께 넣는다(back-to-back 비교). 신호 모니터에서 점선은 기준, 실선은 이번 실행이다. 빨간 세로선은 처음 갈라진 시각이다. 플레이어가 얻어야 할 정보는 "**가장 먼저 갈라진 신호 = 고장이 시작된 경계**"다.
4. **레벨마다 다른 정보:** 프로브는 그 레벨에서 보이는 신호에만 꽂을 수 있다. 그래서 레벨을 고르는 이유가 체감된다.
5. **실제 시뮬레이션:**
   - 지금은 미리 그린 곡선과 재생 애니메이션이다.
   - 사건마다 작은 수치 모델을 매 프레임 계산하는 방식으로 바꾼다. 모델은 퍼즐 블록 체인에 차량 가속·온도·유압 1차 모델을 붙인 것이다.
   - 입력이나 기법을 바꾸면 그래프와 3D가 실제로 달라진다.
6. SW 탭은 퍼즐과 같은 조각 UI를 쓴다.

## 5. 도미노 시각화
- **추리 중:** 증상 도미노에서 출발한다. 측정으로 "먼저 넘어진 것"을 찾아 뒤로 간다.
- **확정 후:** 원인 → 결과 순서로 도미노가 실제로 쓰러지는 장면을 재생한다. 같은 원인에 영향을 받는 다른 기능은 옆 갈래로 쓰러진다(영향도 분석). 이 갈래가 회귀 시험 목록이 된다.

## 6. 마감(화~수) 안 범위
- **필수**
  1. 순서를 도미노 → 퍼즐 → 벤치로 바꾸고, 도미노가 의심 구간에서 멈추게 한다.
  2. 열관리·제동 퍼즐판을 의심 구간 기준으로 바꾼다(E/E·HW 블록 포함).
  3. 벤치 시작에 레벨 질문과 기법 선택을 넣고, 정상 vs 현장 기록 비교로 바꾼다.
  4. 벤치 SW 탭을 퍼즐 UI로 바꾼다.
- **가능하면:** 구동부터 수치 모델 시뮬레이션, 도미노 쓰러짐 애니메이션, 시스템 통합 3D 재정비.
- **보류:** 오답 분기 스토리, 새 고장 시나리오.
