# 추리 단계 계획 재평가와 개선안 (2026-11-08 3차)

평가 기준(사용자 지정, 우선순위 순):
1. **자동차 도메인·핵심 제어 습득**: 기능 흐름(입력 → 제어 → 통신 → 구동 → 차량)과 핵심 제어(맵, MIN 한계, 히스테리시스, PI)를 이해하는가.
2. **검증 사고 흐름 획득**: 가설 → 시험 설계(레벨·입력·관측점) → 실행 → 판정 → 회귀의 순서를 스스로 밟는가.
3. **원인 파악·근거 제시 능력**: 검증은 고치는 일이 아니다. 고객사 대응을 위해 "왜 문제가 있는지 / 왜 문제가 없는지"를 시험 근거로 설명할 수 있는가.

보조 기준: 게임 흐름, 흥미·재미, 추리게임다움, 메시지 전달.

## 1. 직전 계획(DEDUCTION_LAYOUT_PLAN) 평가

| 기준 | 점수(5) | 근거 |
|---|---|---|
| 도메인·핵심 제어 | 3 | 퍼즐에서 맵·MIN·히스테리시스·PI를 다룬다. 하지만 퍼즐에서 만든 로직이 검증에서 기대값으로 다시 쓰이는 장면이 약하다. |
| 검증 사고 흐름 | 3 | 가설 → 레벨 → 입력 → 시험 순서는 맞다. 다만 결과 해석(지지·반박)을 **게임이 자동으로** 해 준다. 플레이어는 버튼만 누른다. |
| 원인 파악·근거 제시 | **2** | 마지막에 근거를 정리해 설명하는 장면이 없다. "SW는 문제없다"는 것을 무엇으로 말하는지 플레이어가 직접 묶어 보지 않는다. |
| 추리게임다움 | 2.5 | 단서를 고르는 것까지는 플레이어 몫이지만 **해석은 자동**이다. 추리의 핵심(이 증거가 무엇을 뜻하나)을 플레이어가 하지 않는다. |
| 게임 흐름 | 3.5 | 공통 가설 줄로 세 단계가 이어진다. |
| 시각화 | 2.5 | 왼쪽 시각화를 하나만 띄우면 "이 레벨에서는 무엇이 실물이고 무엇이 모델인가"를 비교하며 배울 기회가 없어진다(사용자 지적). |

### 마지막 단계는 추리게임인가?
지금 형태로는 **절반만** 추리다.
- **추리인 부분:** 어떤 레벨·입력·관측점을 고를지 정하는 것. 정보를 모으는 선택이다.
- **추리가 아닌 부분:** 결과를 보고 "이 가설은 반박됐다"고 판단하는 것. 지금은 게임이 자동 판정해서 플레이어가 생각할 필요가 없다.
- **빠진 부분:** 결론을 근거와 함께 설명하는 것. 추리물의 "해결 장면"이자, 실무의 고객사 회신에 해당한다.

## 2. 개선안: "예측 → 관찰 → 판정 → 설명"을 플레이어가 한다

### 3단계 시뮬레이션 검증 (가장 중요)
1. **시험 설계(유지):** 레벨 → 입력값(실제로 인가되는 기법만) → 관측점 3개.
2. **왼쪽 시각화는 탭으로(복원):** SW 로직 / 제어기·I/O / 부품·차량.
    - 같은 시험 결과를 관점만 바꿔 본다.
    - 그 레벨에 연결되지 않은 부분은 "이 레벨에서는 모델로 대체"라고 표시한다. 그래서 레벨마다 무엇이 실물이고 무엇이 모델인지 비교된다.
3. **판정은 플레이어가 한다(신규).**
    - 실행이 끝나면 "판정 노트"가 뜬다.
    - 아직 결론이 안 난 가설마다 지지 / 반박 / 이 시험으로는 판단 불가 중 하나를 고른다.
    - 게임은 판정 규칙(레지스트리)으로 맞는지 확인한다. 틀리면 이유를 알려 준다. 예: "이 레벨에서는 팬이 모델이라 팬 가설을 가를 수 없어요".
    - 맞게 판정한 것만 가설 카드에 도장으로 남는다.
4. **원인 확정 조건:** 참 가설이 플레이어 판정으로 지지되고, 나머지가 모두 반박된 뒤 처음 갈라진 신호에 깃발을 꽂는다.
5. **검증 결과 보고서(신규):** 고객사 회신용 한 장.
    - 결론: "원인: 냉각 팬 모터(고착)".
    - 문제 있음 근거: "시스템 통합 시험 · 장거리 고속 열 부하 · 팬 회전 0 rpm(기준 1850)".
    - 문제 없음 근거: "SW 단위 시험 PASS → 팬 제어 SW는 요구사항대로 동작", "팬 커넥터 PWM·12 V 도착 → 출력단·배선 정상".
    - 보고서 줄은 플레이어가 도장 찍은 증거로만 채워진다.
6. **조치 요청 → 재시험:** 검증은 고치지 않는다. "수정 담당에 요청할 조치"를 고르고, 같은 시험으로 재확인한 뒤 회귀 시험을 한다.

### 1단계 원인 역추적
- 같은 판정 방식으로 바꾼다. 측정값 카드(예: "페달 센서 60%, 기준과 같음")를 플레이어가 가설에 대고 반박 / 판단 보류를 고른다(지금은 자동).
- 끝에서 판단 보류 가설 2개 이상을 넘긴다.

### 2단계 로직 퍼즐
- 완성하면 **기대값 카드**(사건 입력에서 칸마다 나와야 할 값, 예: 60% → 204 Nm)를 만든다. 이 카드가 3단계 모니터의 점선(기준)과 보고서의 "기대값"으로 그대로 쓰인다.
- "연결 확인"과 "요구사항 판정"은 분리한다(직전 계획 유지).

## 3. 개선안 예상 점수

| 기준 | 직전 | 개선 |
|---|---|---|
| 도메인·핵심 제어 | 3 | 3.5 (퍼즐 기대값이 검증 기준으로 재사용) |
| 검증 사고 흐름 | 3 | 4 (해석을 플레이어가 함) |
| 원인 파악·근거 제시 | 2 | 4 (판정 근거 + 보고서) |
| 추리게임다움 | 2.5 | 4 (관찰한 증거로 가설을 직접 지우고 해결 장면이 있음) |
| 시각화 | 2.5 | 4 (탭 비교 복원) |

## 4. 구현 순서
1. 3단계: 왼쪽 시각화 탭, 판정 노트(플레이어 판정), 원인 확정 조건, 검증 결과 보고서, "조치 요청" 문구 — **이번에 바로 진행**
2. 1단계: 측정 카드로 가설 판정(같은 판정 노트 재사용)
3. 2단계: 기대값 카드 → 3단계 기준선·보고서 연결, 연결 확인 분리
4. 공통 가설 줄·차고 노트·도움말 정리, 세 크기 화면 점검, 두 사건 통합 플레이
