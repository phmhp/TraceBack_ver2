## 읽는 대신 이렇게 검수

화면 문구를 한 줄씩 읽고 감으로 판단하지 않습니다. 한 기능을 고른 뒤, **운전자 입력 → 센서/제어기 → 통신 신호 → 액추에이터 → 차량 거동**을 하나의 시스템 경로로 따라가며 그 경로를 다른 화면과 모델에서도 대조합니다.

1. 카탈로그에서 기능과 플레이어 조작을 고릅니다. 기능 흐름, 부품·E/E, SW 구성, SW 로직의 네 계층을 같은 기능 기준으로 연결합니다.
2. 각 경계에서 송신자·수신자·신호 이름·단위·조건을 기록합니다. 예를 들어 VCU가 만든 토크 요청이 어떤 통신 연결로 MCU에 들어가고, 어떤 출력으로 모터/차량 거동에 반영되는지 추적합니다.
3. 같은 기능을 아키텍처 개요, 상세 도메인, 차량 3D, 하단 흐름, 입력 시뮬레이션, 시나리오의 증거/시험/수리 데이터에서 교차 확인합니다. 화면마다 따로 그럴듯한지만 보지 않고 앞 단계의 신호와 다음 단계의 결과가 같은 원인·단위·방향으로 이어지는지 봅니다.
4. 각 문제 후보를 브라우저에서 재현할 조작 순서로 씁니다. 정적 코드에서 확인한 사실과 실제 화면 관찰을 분리합니다.
5. 결론은 아래 분류 중 하나로 남깁니다. OEM/ISO/AUTOSAR 등 외부 규격 적합성은 정확한 공식 문서·판본·절 근거가 없으면 판정하지 않습니다.

### 판정 분류

- **확인된 내부 불일치**: 저장소 안의 데이터, 신호 계약, 원인/판정 로직끼리 모순됨. 소스 위치와 연결 논리를 제시합니다.
- **교육상 모호성/모델 범위 차이**: 코드가 단순화되어 있거나 용어/경계가 설명되지 않아 플레이어가 시스템 범위를 오해할 수 있음. 단순화 의도 확인 전에는 결함으로 단정하지 않습니다.
- **검증 대기**: 화면 렌더링, 실제 3D 에셋, 상태별 노출, 외부 기술 규격 등 실행·설계 의도·공식 근거가 더 필요함.

각 finding에는 `주장 → 정확한 근거(파일/줄/상태) → 같은 시스템 내 영향 → 재현·반증 방법 → 범위/반대 근거 → 상태`를 씁니다. 정적 근거만 있는 내용을 “브라우저에서 확인했다”고 쓰지 않습니다. 에이전트 간 동의도 근거 대신 사용하지 않습니다.

## 독립 검토의 경계

두 검토자는 같은 체크리스트를 공유하지 않고 각각 정비소 상호작용 표면과 시스템 신호/원인 일관성을 정적 소스에서 살폈습니다. 본 문서의 항목은 결과를 그대로 채택한 것이 아니라 현재 소스와 대조한 내용입니다. 에이전트 검토는 탐색 범위를 넓히는 수단이지, 독립된 검증 증거 또는 실제 화면 검수의 대체물이 아닙니다. 이 검수에서는 브라우저에서 모든 버튼을 눌러보거나 3D를 직접 관찰하지 않았습니다.

## 확인한 기술 논점

### GARAGE-FLOW-001 · 구동 E/E 단계의 신호 의미/단위 연결

**주장:** 구동의 부품·E/E 인스펙터는 차량 의미 레이어의 다섯 단계를 E/E 노드 수에 맞춰 보간합니다. 그 결과 E/E 노드의 입·출력 신호가 실제 경계 신호와 일치하지 않을 수 있습니다.

**근거:** [evData.ts:29](../src/features/garage/evData.ts#L29)에는 차량 흐름 `가속 페달 조작 → 가속 의도 → 가용 토크 판단 → 전륜 추진력 → 차량 가속`과 별도의 10개 E/E 노드가 있습니다. [experiences.tsx:764](../src/experiences.tsx#L764)는 차량 의미 배열을 E/E 단계 수로 균등 재표본화하고, [experiences.tsx:785](../src/experiences.tsx#L785)는 그 값을 현재 E/E 단계의 입력/출력으로 노출합니다. 반면 [components.ts:37](../src/sim/components.ts#L37) 및 [components.ts:129](../src/sim/components.ts#L129)는 BMS/VCU 포트와 VCU→MCU `Torque_Request` 연결을 정의하며 출력 단위는 `Nm`입니다. 차량 의미 배열에서 E/E 배열로 보간된 `가속 의도`는 퍼센트 계열 신호라 두 표현이 같은 경계 계약이 아닙니다.

**시스템 영향:** 플레이어가 VCU가 만든 토크 명령이 MCU로 전달되는 경계에서 페달 의도(%)를 전달한다고 오해할 수 있습니다. 따라서 기능 흐름, E/E 연결, 시뮬레이션 trace를 하나로 연결하는 학습 경로가 끊깁니다.

**재현/반증:** 구동 → 운전자 토크 요청 해석 → 부품·E/E에서 VCU, CAN 토크, MCU를 차례로 선택합니다. 화면에 표시되는 입력·출력 신호와 단위를 포트 연결 계약과 대조합니다. 이 단계가 신호 의미를 표시하지 않는 설계라면 라벨/범위를 명확히 해야 합니다.

**상태:** 코드 내부 매핑 불일치 확인. 실제 브라우저 렌더링과 다른 기능의 영향 범위는 미확인.

### GARAGE-IO-002 · 차량 제어 입력 라벨과 썸네일 대응

**주장:** 차량 제어 영역 입력의 이름과 이미지 모델이 인덱스로 짝지어져 있지만 같은 장치를 가리키지 않습니다.

**근거:** [evData.ts:411](../src/features/garage/evData.ts#L411)의 입력 라벨은 `진단 장비`, `전방 카메라·레이더`입니다. [ArchitectureOverview.tsx:93](../src/features/garage/ArchitectureOverview.tsx#L93)는 이에 대응하는 모델 ID를 `generic_ecu`, `imu_sensor`로 선언하고, [ArchitectureOverview.tsx:108](../src/features/garage/ArchitectureOverview.tsx#L108)는 같은 인덱스의 라벨과 이미지를 표시합니다.

**시스템 영향:** 그림이 실제 부품 사진처럼 보일 경우 진단 장비와 카메라·레이더의 하드웨어를 잘못 식별할 수 있습니다.

**재현/반증:** 브라우저의 차량 제어 입력 카드 두 개를 보고 썸네일이 실제로 무엇을 나타내는지 확인합니다. 대표/장식 이미지라면 그 사실이 화면에 전달되는지 확인합니다.

**상태:** 배열 대응 불일치 확인. 이미지가 상징용이라는 의도 및 실제 그림은 브라우저 확인 대기.

### GARAGE-COORD-003 · 도메인 협조 신호와 페달 시뮬레이션 경계

**주장:** 아키텍처에는 BMS 방전 한계와 열 디레이팅이 VCU로 연결되어 있지만 공통 차량 모델의 토크 제한 계산은 해당 연결 입력을 사용하지 않습니다.

**근거:** [components.ts:37](../src/sim/components.ts#L37), [components.ts:129](../src/sim/components.ts#L129), [components.ts:151](../src/sim/components.ts#L151)는 VCU 한계 입력 및 BMS/열 ECU 연결을 선언합니다. 그러나 [vehicleSim.ts:103](../src/sim/vehicleSim.ts#L103)에서 열 디레이팅은 모터 온도로 로컬 계산되고 [vehicleSim.ts:117](../src/sim/vehicleSim.ts#L117)–[vehicleSim.ts:121](../src/sim/vehicleSim.ts#L121)에서 로컬 출력 제한을 계산합니다. BMS 한계는 trace에 기록되지만 제한 계산 입력으로 사용되지 않습니다. [PedalLab.tsx:6](../src/features/garage/PedalLab.tsx#L6)–[PedalLab.tsx:14](../src/features/garage/PedalLab.tsx#L14)는 운전자 입력과 상태로 이 모델을 호출합니다.

**시스템 영향:** 아키텍처 그림은 도메인 간 협조가 출력에 영향을 주는 것처럼 설명하지만 페달 데모는 그 신호 경계를 실행하지 않습니다. 플레이어가 차량 전체 모델이라고 생각하면 신호가 실제 계산에 반영된다고 오해할 수 있습니다.

**재현/반증:** 화면에 있는 입력 조건을 바꿔 BMS 한계/열 상태와 페달 랩 출력을 비교합니다. 단순화 시뮬레이션이라면 제외한 협조 경계를 본문 설명이나 시뮬레이션 조건에서 분명하게 표시합니다.

**상태:** 코드상 모델 경계 차이 확인. 의도된 교육용 단순화인지 결함인지는 설계 의도와 실제 화면 문구를 확인하기 전 판정 보류.

### GARAGE-CASE-004 · 가속 저하 시나리오의 단계 간 원인 ID

**주장:** propulsion 도미노 정답은 `gateway`지만 실험대의 참 가설과 고장 주입 위치는 VCU 페달 처리 SW(`vcu_sw`)입니다.

**근거:** [scenarios.ts:18](../src/game/scenarios.ts#L18)의 시나리오 root는 `gateway`; [scenarios.ts:28](../src/game/scenarios.ts#L28)의 플레이어용 도미노 후보 역시 `gateway`입니다. 별도 기술 메타의 [scenarios.ts:209](../src/game/scenarios.ts#L209)는 `vcu_sw`를 참으로 지정하고 [scenarios.ts:199](../src/game/scenarios.ts#L199)는 VCU 입력 처리 계수 `×0.45`를 주입합니다. [runtime.ts:334](../src/game/runtime.ts#L334)–[runtime.ts:347](../src/game/runtime.ts#L347)는 도미노 정답을 `gateway`로 저장합니다. 실제 페달 scale 적용 위치는 [vehicleSim.ts:112](../src/sim/vehicleSim.ts#L112)입니다.

**시스템 영향:** 원인 식별 단계가 앞서 선택한 `gateway`에서 뒤 단계의 `VCU 페달 처리 SW`로 이동하는 것처럼 보입니다. 다른 시나리오에는 저장 호환 키라는 주석이 있으나 propulsion에 대해 두 키를 연결하는 명시적 매핑은 이 근거 범위에서 찾지 못했습니다.

**재현/반증:** propulsion을 처음부터 완료하며 도미노의 원인 이름/ID, 실험대 각 후보 결과, 실제 적용 fault parameter, 수리 대상 이름/ID를 기록합니다. `gateway`가 과거 저장 호환용 별칭이라면 UI에 노출하지 않는 canonical 원인 ID와 명시적 변환이 있는지 추적합니다.

**상태:** 단계별 코드 식별자와 주입 지점 차이 확인. 호환 별칭 의도 여부 미확인. 재현 화면 관찰 필요.

## 아직 실행 확인이 필요한 영역

정비소 카탈로그는 영역 카드, 도메인 버튼, 기능 목록, 네 관점, E/E 보기 전환, 3D 부품 선택, 입력 인터록과 입력 실행, 자동재생, 협조 신호, 상단 이전 단계 등을 상태·조건과 함께 정리합니다. 다만 소스에 존재하는 컨트롤 목록은 브라우저 노출 완료의 증거가 아닙니다. 전수 화면 확인 시 카탈로그의 각 조작을 실제 화면에서 실행하고 URL/초기 상태, 선택 전후의 본문·하단 흐름·우측 트리, back 경로를 기록해야 합니다. 3D에서는 모든 레이어를 개별 토글하고 배선/부품/차체/액추에이터의 가시성 및 입력 실행 전후 동작을 확인해야 합니다.

물리 차량 spec은 원자료 JSON의 `physicalVehicleSpec`에 전체 저장되어 있습니다. 자체 검사 함수에서 나온 unresolved/missing 수치는 검사 규칙이 참조하지 않는 이름일 수 있으므로 실제 차량 결함 수로 해석하지 않습니다. 기하 위치, 좌우·전후 방향, 모델 의미, 레이어 순서는 실행 화면 또는 에셋 검토가 필요합니다.

## 외부 기술 기준 사용 원칙

현재 기록은 저장소 내부의 신호 계약, 시나리오 정의, 데이터·렌더링 관계만 평가합니다. 차량 안전 설계나 산업 표준 적합성이라고 주장하지 않습니다. 외부 기준을 추가할 때는 공식 발행처의 문서 식별자, 판본/연도, 절 번호와 적용 범위를 finding에 첨부하고 내부 교육 모델에 해당 기준을 적용할 이유도 써야 합니다.
